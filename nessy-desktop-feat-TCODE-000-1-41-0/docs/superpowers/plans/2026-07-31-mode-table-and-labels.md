# The inverted permissiveness table, the triplicated write-mode check, and one source of mode labels

Three tasks out of the permission-modes audit (2026-07-31, adversarially
verified). Task 1 is a **live permission widening** and targets this release;
Tasks 2 and 3 remove the mechanisms that let it exist.

**The finding, verified line-by-line:** `PERMISSION_MODE_PERMISSIVENESS`
(`SessionManager.ts:681-691`) is a second, hand-written strictness table and it
**inverts auto and acceptEdits** relative to the canonical
`PERMISSION_MODE_ORDER` (`mode-types.ts:55`): the table says `auto: 3,
acceptEdits: 4` while the order ranks `acceptEdits` (4) BELOW `auto` (5). Its
consumer `normalizeProjectPermissionMode` is live at `SessionManager.ts:8781`
behind `selectedProject?.trustState === 'trusted'` — so a trusted project's
`config.toml` can move a session with an `acceptEdits` floor up to `auto`,
whose write auto-approval is **unbounded** (`pre-tool-use.ts:2159` passes
`{ autoAllowFileWrites: true }` with no roots; `:986` `if (!roots) return
true;`) where acceptEdits is root-bounded (`:1655`). The table also lacks the
plan/safe incomparability carve-out that `clampPermissionModeToParent` has
(`mode-types.ts:94`), so it ranks two modes the canonical clamp refuses to rank.

## 1. Task 1 — one strictness order, with the carve-out (the widening)

**Commit:** `fix(sessions): the project mode clamp uses the canonical order and the plan/safe carve-out`

- Replace the hand-written `PERMISSION_MODE_PERMISSIVENESS` table with a
  derivation from `PERMISSION_MODE_ORDER` — the index IS the strictness rank,
  and `AGENTS.md` (packages/shared) names a wrong position there a silent
  widening, so there must not be a second spelling of the ranking anywhere.
- Carry the plan/safe incomparability: the canonical clamp refuses to rank
  `safe` against `plan` (`mode-types.ts:75-94` explains why — they differ on
  the write axis, neither contains the other). The project normalizer must
  refuse the same pair the same way: when the two modes are incomparable, keep
  the session's floor and drop the project's request, stating why.
- **Prove the defect before fixing it**: a test on TODAY'S code in which a
  trusted project requests `auto` over an `acceptEdits` floor and is accepted —
  then the fix flips it. And the mirror: a legitimate `auto` → `acceptEdits`
  narrowing that today is refused, accepted after.
- `normalizeProjectPermissionMode` call sites may have drifted (~:8781 at
  verification time; the file is large and recently edited) — locate by name,
  not by line.

**Gate:** with the fix, a trusted project cannot move any session to a mode
ranked above its floor by `PERMISSION_MODE_ORDER`; plan/safe requests over the
other's floor are dropped with a stated reason; every previously-legitimate
narrowing still lands. **Mutation:** restore the inverted literal table → the
widening test goes red.

## 2. Task 2 — the write-mode triple has one spelling

**Commit:** `fix(agent): the interactive-write-mode set is declared once`

The triple `ask | acceptEdits | auto` is written independently in three
production files, and only one of them prompts:

- `mode-manager.ts:2156` — `return { allowed: true }` for the triple;
- `permission-manager.ts:312` — `checkBashCommand` returns null (= allowed) for
  the same triple;
- `pre-tool-use.ts:1621` — the ONLY copy that produces a prompt; a tool call
  admitted by the first two that misses this one falls through to
  `return { type: 'allow' };` (`:1716`) — silent allow-all semantics, with zero
  type errors, because each copy is an independent literal comparison.

- One named, exported predicate (or set) beside `PERMISSION_MODE_ORDER` in
  `mode-types.ts`; all three sites consume it. **Behaviour-identical today** —
  this task changes no decision, it removes the mechanism by which a future
  mode-set change desynchronizes the three.
- Do not widen the export surface beyond the one predicate.

**Gate:** the three sites reference the shared declaration (`grep -a` shows no
remaining independent spelling of the triple in production code); the focused
suites for all three files are green and byte-identical in behaviour.
**Mutation:** make the shared set disagree with the old literal at one site →
that site's test goes red.

## 3. Task 3 — mode labels have one source

**Commit:** `fix(ui): permission-mode labels come from i18n only`

Three text sources exist for the same seven modes: the live i18n keys
(`t('mode.<id>')`, interpolated — `ActiveOptionBadges.tsx:496`), a dead
duplicate key family in the locales (`mode.askToEdit*`, `mode.explore*`,
`mode.execute*` — canonical-name spellings no production site interpolates:
verify with `grep -a`, count before claiming), and hard-coded English
`displayName`/`shortName`/`description` strings inside
`PERMISSION_MODE_CONFIG` (`mode-types.ts:434`) that render **only in the
playground** (`playground/registry/parity-ui.tsx:39-46`) — so the design
surface shows different words than the app and does not translate.

- i18n is the single text source. `PERMISSION_MODE_CONFIG` keeps `svgPath` and
  `colorClass` (structure, not text); the playground reads the same i18n keys
  the composer reads.
- Delete the dead key family from EVERY locale — after proving with `grep -a`
  that nothing interpolates to those spellings (the interpolation pattern means
  a plain grep for the literal key is NOT sufficient: grep for the id values a
  `t(\`mode.${...}\`)` can produce).
- The playground is a design surface — its mode entries must render from the
  new source, and a missing key must be loud there, not a raw key string.
- i18n parity + sorted green in every locale.

**Gate:** one text source; the dead keys are gone from all locales; the
playground renders the same words as the composer; parity + sorted green.
**Mutation:** re-add one dead key to one locale → the sorted/parity pair
catches it, or a dedicated test does.
