# The live Claude session — one process that outlives the turn

## Why this plan exists

Owner decision 2026-08-17, taken after the trade-off was put plainly and
declined: the user should get the native Claude experience in one delivery
rather than in two.

**The one sentence.** Today we start a fresh Claude process per user message and
it dies with the answer. Everything else follows: no background command, no long
task, no multi-step workflow can exist, because nothing is alive to hold them.

**This is the SDK's own preferred shape, not our invention.** The Agent SDK docs
call streaming input the *"preferred way to use the Claude Agent SDK"* and
describe it as letting the agent *"operate as a long lived process that takes in
user input, handles interruptions, surfaces permission requests, and handles
session management"*. The list of what the one-shot form cannot do matches our
complaints item for item, and the levers for background work exist only there.

The design is **not re-derived here**. It was produced 2026-08-16 by a judged
panel of three independent designs and lives in
`docs/superpowers/plans/2026-08-16-clean-runtime-usage.md`, row R7 and its
section. This plan carries it forward with the two findings that panel did not
have, both measured on 2026-08-17.

## What the previous plan settled, and what it changed

**Steps 0 and 1 of the chain are DONE.** Step 0 was full event coverage (R8) and
step 1 was the permission chain (R1+R2+R3). Both landed and both were proven
live — see the 2026-08-17 run in `docs/testing/cdp-live-checklist.md`. The chain
this plan continues is confirmed rather than assumed.

**FINDING 1, and it reshapes step 2.** `SessionManager.sendMessage` processes a
`complete` event and then RETURNS out of the whole function — the comment on the
line says *"Exit function, skip finally block"* — and its `finally` calls
`chatIterator.return?.()`, which unwinds the backend generator. So **the consumer
hangs up at the first completion.** A session that outlives the turn is exactly a
stream that keeps going after one, and today nothing would read it. This is the
first question this plan must answer, before any lifetime change: *who consumes
the stream between turns?* Two rows of the previous plan shipped as done and were
inert for precisely this reason, so the failure mode is not hypothetical.

**FINDING 2.** R7 was once recorded as blocking the model-invoked `/compact`
(R9). It does not, and R9 shipped without it: the SDK's own note admits the
pattern *"in a session with prior turns, for example in streaming input mode or
when resuming a session"*, and our turns are already resumed. Nothing else in
this plan is blocked by R7 either — this is additive.

## The gate, restated for what it can actually prove

The panel's gate was "one live day before this chain is approved". That gate is
circular as written — three of its five probes require the live session to
exist — so it becomes **L0 below: a throwaway spike that proves the shape before
anything is rewritten.**

The claim that most deserves it, in the panel's own words: *"our process closes
the input channel on the first result, so the request shape is load-bearing — a
single imprecision leaves 'live session' one-shot with nothing in the log to say
so."* A spike that cannot tell those two apart is worthless, so L0's acceptance
is a discriminating one.

## P.1 Tasks

### L0 — the spike: prove a streaming session survives, before rewriting anything

**Throwaway code, real evidence.** Stand up one `query()` in streaming-input mode
against a real Claude card and establish, with a control that can fail:

1. The session takes **three turns** through one process — and the process is
   the same one, evidenced by something only a live process could carry, not by
   the absence of an error.
2. The input channel is **still open** after the first result. The discriminating
   control: a build that closes it must FAIL this, so the probe has to send turn
   two through the same channel rather than opening a new one.
3. A model change through `setModel` lands **without** a restart, and the session
   keeps its context — measured by asking for something only the earlier turns
   carry.
4. A permission-mode change through `setPermissionMode` lands the same way.
5. The stream survives a **network cut** and reports it as a turn failure rather
   than a session death — or, if the session does die, that death is observable
   rather than silent.

**Do not touch `claude-agent.ts` in this task.** The spike is a script under
`scripts/` that is deleted when its findings are recorded.

**If any of the five is refuted, STOP and report.** A refuted premise here is
worth more than the whole chain, and this plan has a five-for-five record of
premises that did not survive contact with the code.

### L1 — who reads the stream between turns

The consumer question from Finding 1, answered before the lifetime changes.

Establish what `SessionManager` must do differently for a backend whose stream
outlives a turn, and choose between the shapes: a per-turn view over one long
stream, a demultiplexer keyed by turn, or a consumer that stays attached and
routes by event. Weigh each against the coalescing objection the panel conceded:
the SDK may merge queued messages into one turn, so "one message sent = one
result" is false and a naive matcher will one day wait for a result that never
comes — **worse than today**, where a hang is impossible because the process dies.

**The answer is not a cleverer matcher.** One active turn per session, a watchdog
per turn, and unconditional error-settlement of every waiting turn when the
session dies. The native priority queue comes after coalescing has been watched
on a live rig.

### L2 — the live session itself

One `query()` per agent, strictly one turn at a time. Recovery-and-resume logic
moves into session start.

**Five SDK call sites, not three.** Title generation and structured mini-queries
carry their own system prompt and MUST stay one-shot. Find all five before
changing any.

**State that is clean today only because the process was new starts leaking**:
diagnostic buffers, event-translator state, mode snapshots. Every site must be
found and reset per turn.

**Deleted in exchange:** the hook-injected message workaround and the
source-activation controller stop being needed.

### L3 — an idle policy and a reaper, and the eviction defect

Every open chat becomes a live process — seconds today, hours after — so this is
mandatory rather than optional.

**Agent eviction becomes a defect the moment background work exists.** Today the
oldest inactive agent is killed and that is safe because eviction is hibernation,
not loss. An agent running a background task reads as inactive and would be
killed. **The busy predicate widens before L4, not after.**

### L4 — live settings

Model, permission mode and MCP server set change without a restart; switching
model mid-session stops costing the context.

**What a live session does NOT solve, verified against the whole SDK type file:**
cwd, system prompt, tool set, subagent set and user hooks still require a session
restart — no method exists. Our `explore` mode has no SDK equivalent and stays
ours on top of theirs, permanently. Do not promise these.

### L5 — background work and the native queue

Only after L0–L4 and only with the coalescing behaviour watched live.

## P.2 Rules for this plan

- **Every task is reviewed by an independent agent** before it is committed.
- **L2 cannot be parallelized.** It is a lifecycle rewrite in one large file; two
  agents in one file cross by construction.
- **Verify the premise before building on it.** Five rows of the previous plan
  had a premise that did not survive contact with the code, and each was caught
  by an executor who checked first and said so.
- **Prove non-inertness.** Revert the change, show the tests go red, restore
  byte-identically and verify with sha256. Two rows shipped green-and-dead last
  time because a unit test drains a generator and the session does not.
- **An absence is not evidence until the same rig produces a presence.**
