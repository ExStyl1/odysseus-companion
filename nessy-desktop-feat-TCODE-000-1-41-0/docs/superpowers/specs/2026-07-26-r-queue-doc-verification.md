## R1 — understated (permissions)

### What the check found

The core of R1 is right — Claude really does use `Tool` / `Tool(specifier)` strings, the four Read/Edit anchors are exactly `//path`, `~/path`, `/path`, `path`/`./path`, `Edit` really does govern the other file-editing tools, and a bare-name deny really does remove the tool. But the entry describes roughly a third of the contract, and the part it omits is the part that decides the implementation shape.

(1) It is eight tool-specific matchers, not four rule forms: Bash, PowerShell, Read/Edit, WebFetch, MCP, Agent, `Cd`, plus `Tool(param:value)` on any tool. `Cd` is a *different* matcher from Read/Edit — permissions.md: "Path patterns share the `//`, `~/`, and `/` anchors from Read and Edit rules, but matching is anchored to the whole directory path rather than gitignore-style. `*` matches exactly one path segment and `**` matches across segments." And "Adding any `Cd` allow rule switches `/cd` to allowlist mode."

(2) Read/Edit patterns are gitignore syntax whose depth depends on the rule *type*: "**Allow rules**: `Edit(src/**)` matches only `<cwd>/src` and the files under it... **Deny and ask rules**: `Read(secrets/**)` matches a directory named `secrets` at any depth under the current directory". Also "Bare filenames follow gitignore semantics and match at any depth, so `Read(.env)` and `Read(**/.env)` are equivalent." Our DSL cannot express any of that: `permission-dsl.ts` compiles a `path` matcher to an **absolute-root containment** test — `if (!isAbsolute(root) ...) throw` at :238 and `const rel = relative(root, value); return rel === '' || (!rel.startsWith('..') && !isAbsolute(rel))` at :373-374. A gitignore pattern with rule-type-dependent depth is not a root prefix, so R1 needs a NEW matcher kind, not a string parser onto the existing DSL.

(3) The `/path` anchor is per-settings-source, five distinct anchors, and the user-settings one is a trap: "A deny rule such as `Read(/secrets/**)` in user settings blocks `~/.claude/secrets/**`, not a `secrets` directory in your project."

(4) Symlinks are evaluated as a pair with an allow/deny asymmetry: "**Allow rules**: apply only when both the symlink path and its target match... **Deny rules**: apply when either the symlink path or its target matches."

(5) `Edit` covering Write/NotebookEdit is not a convenience, it is the only spelling, and the other spellings must be accepted-but-inert *with a startup warning*: "A `Write(path)`, `NotebookEdit(path)`, or `Glob(path)` rule is accepted but never matched by those checks, so Claude Code warns at startup for each allow, deny, or ask rule in one of these unmatched forms." The doc even gives the exact warning string. Separately: "A `Read` deny rule also blocks the Edit tool on the same path, including creating a new file there."

(6) Bare-name deny has a documented exception R1 does not carry: "Bare-name removal applies to every tool except `EndConversation`: a deny rule can't remove it while any other tool remains, and an ask rule never prompts for it."

(7) R1's `mcp__srv__*` example hides an allow/deny asymmetry: "Allow rules accept tool-name globs only after a literal `mcp__<server>__` prefix. The server segment must be glob-free... An unanchored allow glob such as `"*"`, `"B*"`, or `"mcp__*"` is skipped with a warning and doesn't auto-approve anything."

R1 is Pi-relevant, not Claude-flag-only — our own gate and hook runner consume these rules.

## R15 — wrong (permissions)

### What the check found

R15's premise does not exist in the documentation. The entry is built on §1's claim that Claude runs "Hooks first (so hook allow can widen)" and therefore treats the work as reversing a security invariant that needs its own threat model. Half of that is right and the load-bearing half is wrong.

Hooks ARE step 1. But a hook `allow` does not widen past deny. `agent-sdk/permissions.md`, step 1 verbatim: "Run hooks first. A hook can deny the call outright or pass it on. A hook that returns `allow` does not skip the deny and ask rules below; those are evaluated regardless of the hook result." `permissions.md`: "Hook decisions don't bypass permission rules. Claude Code evaluates deny and ask rules regardless of what a PreToolUse hook returns: a matching deny rule blocks the call, and a matching ask rule still prompts even when the hook returned `"allow"` or `"ask"`. This preserves the deny-first precedence... including deny rules set in managed settings." `hooks.md` on `permissionDecision`: "`"allow"` skips the permission prompt, except for tools that require user interaction and connector tools your organization set to `ask`... Deny and ask rules are still evaluated regardless of what the hook returns." `PermissionRequest`'s `behavior` field says the same: "a hook returning `"allow"` doesn't override a matching deny rule".

So Claude's deny floor is non-overridable by hooks exactly as ours is. Nothing needs reversing, no threat model is owed, and §3's "deny floor is stronger" is parity on this axis rather than a place we are ahead.

What hooks-first actually buys Claude is the OPPOSITE direction: a hook DENY outranks everything. "hooks run before every other step, and a hook deny applies even in `bypassPermissions` mode" and "A hook that exits with code 2 stops the tool call before permission rules are evaluated, so the block applies even when an allow rule would otherwise let the call proceed." We already have that: `pi-agent.ts:2464` converts a hook `deny`/`block` into a block regardless of what the gate returned, and `:2456` keeps a gate block authoritative. Both directions of the floor are already at parity.

The real residual is two branches, and it is small:
1. `pi-agent.ts:2505-2511` — when the gate returns `prompt` and the hook returns `allow`, we keep the prompt (`decision === 'allow'` at :2517 returns `checkResult` unchanged). Claude's `allow` skips the prompt.
2. `mode-manager.ts:2083-2088` and `:2104-2105` — our `dontAsk` denies at the gate, and a gate block cannot be reopened, so a hook can never approve anything in `dontAsk`. Claude's `dontAsk` explicitly runs "actions matching your `permissions.allow` rules, read-only Bash commands, and calls approved by a PreToolUse hook."

And the mechanism matters: Claude does not give the hook its allow band by reordering the gate. It exposes a separate event, `PermissionRequest`, which "runs when a permission dialog is about to be shown to the user" — i.e. exactly the band, arrived at after the gate has already decided to prompt. That is directly compatible with our gate-first architecture at zero invariant cost, and it is the shape R15 should be planned as.

R15 is Pi-relevant, not Claude-flag-only.

## R6 — wrong (storage-defer-compaction)

### What the check found

Our entry says: "implement `@earendil-works/pi-agent-core`'s public ten-method `SessionStorage` interface … with the documented 3-attempt best-effort emission, a `mirror_error` event, and load-fallback before resume." Those two halves are contracts from two different, incompatible interfaces. ### New facts the audit never carried

- `CLAUDE_CODE_CERT_STORE`: comma list of `bundled`,`system`; default `bundled,system`; `system` requires `tls.getCACertificates` (native install always, npm needs Node >= 22.15); "On older Node versions, only the bundled set and `NODE_EXTRA_CA_CERTS` apply"; no settings.json schema key, env block only. Consequence worth stating in the plan: TLS-inspection proxies (Zscaler, CrowdStrike Falcon) "work without additional configuration when their root certificate is installed in the OS trust store" — which is why Claude needs no per-user CA path in most fleets and we do.
- `NO_PROXY` accepts space- **or** comma-separated lists and `*` for all requests; basic auth goes inline in the proxy URL; "Claude Code does not support SOCKS proxies."
- mTLS rotation contract: files re-read on every settings apply, mid-session included.
- Scope rules (security boundary): proxy + TLS + mTLS vars read only from managed settings and `~/.claude/settings.json` when the app manages the provider connection, ignored in repository settings files (v2.1.217; before that they were ignored in *every* settings file in that mode). In a local/SSH/WSL session signed in through claude.ai the app does not manage the connection and all scopes are read.
- Cloud-session ignore list includes `NODE_TLS_REJECT_UNAUTHORIZED` and `CLAUDE_CODE_OAUTH_SCOPES` alongside the cert vars; each ignored key is logged in the session debug log.
- Background-agent delivery: a per-user supervisor "inherits the environment of whichever shell starts it first, and an OS-installed supervisor receives no shell environment at all" — so shell exports are unreliable and settings `env` is the only reliable channel.
- `processWrapper` (v2.1.210) / `CLAUDE_CODE_PROCESS_WRAPPER` (v2.1.208): absolute path to a launcher run with the Claude command as argv, script must end in `exec "$@"`; env var wins when both set; honored from managed settings, `--settings`, or user settings only. Covers the background service, agent-view terminal hosts and warm spares, post-update relaunches, Remote Control workers, and tmux/iTerm2 teammate panes; does **not** cover an already-installed service unit, a session the user starts by hand, the first process of a `claude-cli://` deep link, `--worktree --tmux` panes, or the Chrome native-messaging host. Ignored on Windows entirely ("the launcher contract depends on `exec`") with only a debug-log warning — count Windows as unwrapped.
- Egress allowlist discipline: `network-config.md` publishes a per-host table with the reason each host is needed, plus `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` to kill auto-updates, telemetry, error reporting, release notes, gateway model-discovery refreshes and availability checks, and `skipWebFetchPreflight: true` for deployments that block Anthropic hosts. Our gateway equivalent (the `code-completion-nestor` host plus Artifactory/registry and update-feed hosts) has no such published table; a bank network team will ask for one.
- Relevance caveat, stated plainly: nothing in R26 is Claude-runtime-specific — proxy, CA and mTLS apply to our own gateway calls, so this entry keeps full value under the Pi/Nestor-only scope. The corporate-launcher half is the weakest part for us, since it is written against the CLI's own supervisor architecture, which we do not have.
