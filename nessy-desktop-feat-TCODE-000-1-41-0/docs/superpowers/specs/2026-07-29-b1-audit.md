## The row itself was wrong in two places

Correct the tracker before planning against it.

**1. "the `.mcp.json` `timeout` the Claude adapter still drops" — stale.** It does
not drop it. `normalizeClaudeMcpServers` reads `rawServer.timeout` through the
shared `mcpToolTimeoutMs` helper (which implements the documented sub-1000 floor)
and emits `PluginCapability.mcp.toolTimeoutMs`, which survives persistence,
candidate build, resolution and pool materialisation to a real reader —
`McpClientPool.callTool` wraps every call in `AbortSignal.timeout(toolTimeoutMs)`.
Verified by running the adapter over a synthetic bundle: `timeout: 600000` came
back as `toolTimeoutMs: 600000`. Landed by `4a5de555`. The refutation agent
attacked it on all three of this series' usual failure axes — reader only on a
non-default backend, reader only reachable from a test, silent drop at a
projection hop — and all three attacks failed.

This is the **third** timeout fix in the series and they are easy to conflate:
the Codex `tool_timeout_sec` fix (`codex.ts:1026`), the Claude hook
`timeout`-in-seconds fix (`claude.ts:781`), and this one. My row named the wrong
one.

**2. "`bin/` on PATH under the hook trust gate" — the premise is wrong.** Claude
does document bin-on-PATH, so the mechanism is real, but the docs attach **no
trust gate**: the only condition is "while the plugin is enabled". More
importantly, our hook trust record (`visibility-state.ts:77`-`:88`) is keyed to
one capabilityId plus one executableHash and **cannot represent a directory whose
file set changes on plugin update** — so the row's premise that this rides the
hook trust gate is itself the thing that would have to be fixed first.

The auditor recommends **not implementing it**, and the argument is strong enough
that I am adopting it pending an owner objection: any installed plugin dropping a
file named `git`, `npm`, `ssh`, `sudo`, `curl`, `node` or `bun` into `bin/` would
have it resolved by bare-name lookup for **every** subprocess the agent spawns,
not just the Bash tool. Full code execution as the user on the next unrelated
command, attributed in the transcript to whatever innocuous thing the user asked
for. Shadowing is the whole attack: the plugin never has to be invoked, only
enabled. We currently detect `bin/` and emit a deferral whose reader is live and
load-bearing — the honest opposite of this series' recurring defect. The cheap
useful slice is one string: tell the user the plugin ships executables we will
not put on PATH, and that its own components can still call them by absolute
path.

## The refuted one, and why it is first in the queue

Path resolution was audited as "partially implemented" and refuted **downward to
absent-but-declared**, by execution rather than inspection. The refuter's case:

- The automatic single-root-skill layout (`:649`) is by its own wording the case
  where there is **no** manifest path. Crediting it toward a custom-path merge
  rule double-counts.
- `input.skills !== undefined` is not a partial implementation but a **contract
  inversion**. `:637` says a declared `skills` can only ADD; our sole reader uses
  its presence to SUBTRACT. Running the docs' own example `"skills": ["./"]` with
  a root `SKILL.md`: Claude loads one skill, we emit zero. **A conforming plugin
  loads strictly less than a non-conforming one.**
- With `commands: ["./specialized/deploy.md"]` we emit `commands/default-cmd.md`
  — the folder Claude does not scan — and drop the file Claude does load. **We do
  not under-load; we load the wrong set.**

Zero of ten merge rules resolved, with observable behaviour inverted rather than
merely missing. The only consumer of the ten `custom-<x>-path` records is a
display string ending in a `partial` badge.

**And the machinery already exists, for the other format.** `normalizeCodexSkills`
(`codex.ts:642`) resolves manifest-declared string/array/record paths, and
`declaresDefaultPath` (`codex.ts:512`) is a working replace-versus-extend
decision. The Claude adapter calls none of it and hardcodes
`const skillsDir = CLAUDE_DEFAULT_SKILLS_DIR`. This is the recurring defect in
its cross-adapter form. Planned as **B1a**
(`2026-07-29-plugin-path-resolution.md`), dispatched.

Two ancillary findings from the same probe: `"lspServers": "./.lsp.json"` — the
docs' own spelling — yields `plugin.format.claude_capability_incomplete`, zero
LSP capabilities, **and** suppresses the `.lsp.json` default, making it absent
*and* undeclared, worse than the other nine. And containment: probe G confirmed
`"commands": ["../../../../etc"]` is classified as a valid override with
`ok=true`. Inert today because nothing resolves it — which is exactly why the
containment check must land **in the same commit** as the resolution, not after.

## `defaultEnabled` carriage — closed 2026-07-29 (`57a8af3b`)

The audit's second slice, done inline because it is small and it unblocks two
subsystems. The chain the audit described reproduced exactly:
`format-adapters/claude.ts` parses the field and re-attaches it after
normalization, then `commitInstall` re-runs `normalizeNessyPluginManifest`, which
**rebuilds the manifest field by field and never copied it**. Repo-wide the field
had zero readers outside the adapter, its type declaration and tests.

The user-visible consequence is not subtle: `plugins-reference.md` § Default
enablement says `defaultEnabled: false` ships a plugin that installs disabled,
"for plugins that add cost or scope a user should opt into, such as one that
connects to an external service". Every such plugin installed **enabled** here —
the precise opposite of what its author asked for, and for exactly the class of
plugin where being wrong costs money or reaches an external service.

Now carried through normalization and read at the install-time enable. Absent
still enables, because the contract reads no opinion as `true`, so only an
explicit `false` suppresses. Mutation-probed: neutralising the guard fails the
new test, restoring it passes. Gate: `packages/shared/src/plugins` 536 pass /
1 skip / 0 fail, `typecheck:shared` clean, `git diff --check` clean.

**Left open, deliberately**, both recorded rather than half-built: a marketplace
entry's own `defaultEnabled` "takes precedence over the value in `plugin.json`",
which needs the marketplace-entry parsing the audit found missing; and the
dependency-requirement rule that writes an explicit `true` at install time, which
needs the dependency graph that does not exist.

## B1b — `userConfig`, closed 2026-07-29

`64005a0d`, `52fcecc4`, `727901df`, `134faa6a`, plus `70b5c146` and `757d7376`.

**The attack test is the unit.** A cloned repository ships both
`.claude/settings.json` and `.claude/settings.local.json`, each planting
`pluginConfigs` entries for a plain and a sensitive option the installed plugin
declares. The test then byte-scans the **entire** plugin data root and the
credential file for the planted markers, asserts the hook option environment is
empty, and asserts the planted files were neither read nor modified. The
restriction is structural rather than filtered: a workspace-resident layer is
dropped **whole**, `PluginUserConfigStore`'s constructor takes no project-root
parameter for a future caller to pass, and the comment names
`resolveRuntimeHookSources`'s project overlay as the pattern *not* to reuse.
Mutation probe: adding `'project', 'local'` to the source list turns it red with
the attacker's values in the environment.

**Six corrections, two of which I would not have caught.**

- **My field list was short.** `title` and `description` are documented as
  **required**, alongside `required` and `default`, none of which my §2 named.
  The executor then *downgraded* the required-ness to a warning with its reason:
  refusing an option because it lacks a caption costs the user a working option.
- **"Widen the MCPB path" was the wrong instruction taken literally.** The
  executor widened the **shared** path — descriptor, normalizer, configure/status/
  clear — and deliberately left `mcpb.ts`'s refusal of `multiple` alone, because
  MCPB's `multiple` is a *repeatable argument inside an `mcp_config`*, not
  Claude's array-of-strings for one option. Lifting it would have meant guessing
  how a joined array substitutes into `env`/`args` for a format whose contract
  does not say. My plan read as though the two were the same field.
- **Two of the three shell-rejection sites do not exist here.** `:585` also
  rejects `${user_config.*}` in MCP `headersHelper`, which my Task 3 omitted —
  and `headersHelper` and monitor commands are parsed nowhere in this repo, so
  those checks have no place to run. Only the shell-form hook check is
  reachable; the other two are category strings rather than dead code.
- **My plan never mentioned the capability generation.** Nothing tied a
  configured value to it, so a reconfigured option could not invalidate a pinned
  snapshot — MCP reaches this through `credentialRevision` and plugin options had
  no equivalent. Fixed with a sha256 **digest** of the option environment in the
  hook's generation material, never the values.

The sensitivity split is Claude-documented for Claude plugins (sensitive →
credential manager, rest → a host-owned file) and **deliberately stricter for
MCPB**, which keeps sending every value to credentials: loosening it would
migrate already-stored secrets into a plaintext file, a regression dressed as
conformance.

Sensitive values **are** exported to hook environments, because `:577` says "All
values" and `:583` names the env export as *the* alternative for the shell-form
case it refuses — which only works if the sensitive value is there. The export
rides `RuntimeHookRegistration.optionEnvironment` rather than
`PluginRuntimeContext`, which is shared with skills, MCP servers and agents;
putting it there would have handed every plugin subprocess the values.

And once more the executor found this audit's own defect in its own diff:
`pluginConfigurationEffectiveValues` was exported with zero external callers, and
was made module-private in a second extra commit.

## B1c — managed activation and plugin output styles, closed 2026-07-29

`a0df2d30`, `e12dc37d`, `b4c19312`, `a3a59286`.

**The carve-out I closed this morning now has its documented subject**, and I
verified that independently rather than taking the report: `areVettedPluginHooksAllowed`
reads `managedForceEnabledPluginKeys`, which is the `true` entries of
`enabledPlugins` and nothing else. My own probe over five policies confirms an
allowlist of two vets nothing, an allowlist plus an empty map vets nothing, and —
the case that catches an implementation reading the map's *keys* instead of its
values — **a map whose only entry is `false` vets nothing**. That last exclusion
is the one worth having: it means an administrator who switches a plugin off
cannot accidentally leave its hooks vetted.

**Three corrections that changed the design, and one that changed this register.**

- **The style id cannot live on the manifest capability.** The store computes the
  plugin key from an origin field an adapter never sees, so a manifest-time id
  would silently disagree with the installed key and strand the selection — the
  declared-but-inert shape again, arriving through my own plan. Composed at
  projection instead, where the key is authoritative.
- **`readdir` order is a real nondeterminism** for every component field, so
  "first file wins" on a style-name collision was whatever the filesystem
  returned. Sorted inside the output-style normalizer only; widening it would
  reorder existing bundles' capability lists, so that is recorded rather than
  changed.
- **My gate list was short by one suite.** Both tasks widened field names pinned
  in a `pi-agent-server` harness fixture, not beside either type — found only by
  the repository-wide run, and the second violation was hidden behind the first
  because those assertions are sequential. Hence the fourth commit.

**A sixth way the register can be wrong, and the first that is not about losing a
row.** Task 2 made **two rows in S11's plan false** — plugin styles no longer
"never reach the picker", and `force-for-plugin`'s first precondition is now met.
The register regenerates from those plan files, so leaving them would have
shipped confidently false rows rather than missing ones. The executor corrected
them at the source.

So the register needs one more discipline: **when a slice lands, re-read the rows
that named it as a blocker.** A row that was true when written is not
self-invalidating, and the generator cannot tell.

For the `false` direction of a managed `enabledPlugins` entry, the **hiding** half
shipped and the **install-time refusal** did not — recorded, because it belongs in
an install service another unit held.

## B1d — authoring tooling, closed 2026-07-29

`809d213f`, `a027d25d`, `aca940b0`, `ea047b8a`.

**The audit's evidence line was true and my inference from it was wrong, and the
executor caught it before it shipped.** This audit recorded
`PluginStore.validateInstalled` as having zero callers, and my plan said "give
the existing one a door". It cannot be that validator: it takes a
`pluginInstanceId` of an **already-installed** plugin and reads the **V1**
`installed.json`, while the documented verb takes a path to an **uninstalled
directory**. It cannot express the argument.

And the shape is worse than the one this audit is named after. The V1 installed
registry has **no production writer** — `PluginStore`/`PluginInstallService` are
off the barrel as retired, and `commitInstall`, its only writer, has zero
production callers. So wiring `validateInstalled` would have returned
`plugin.store.not_installed` for **every genuinely installed plugin**: not a
reader nobody calls, but *a validator on a store nothing writes*. The door was
built over `materializeStagedBundle` instead — the extracted body `install` and
`repair` already share, so there is still exactly one validator and a validate
verdict cannot disagree with what an install would decide.

**My own method rule defeated itself.** I told the executor to find the CLI verb
table rather than trust my list. The table has ten verbs and `validate` is not
among them — it is specified in three other sections, and the only place its
argument appears is a common-issues row. Obeying that instruction alone concludes
the verb does not exist; the plan and the table had to be read against each other.

**A fifth way the register loses half a row**, and the first one found by
measuring the parser's output rather than by hitting it: the 400-character cap
bites the **parsed reason**, not the source line, so a 407-character row parsed
clipped and lost its final clause. All rows now measured against the regex the
script applies.

**A gate gap in my plan**: `bun run typecheck:all` does **not** include
`apps/cli`, which has its own script — so a CLI change ships untypechecked unless
it is run explicitly. R30b hit this too; it is now stated twice and should be in
the gate template.

**And an extension to the known-failing doc's copy-tree warning**: a `git
worktree` that shares `node_modules` cannot give a clean typecheck read here,
because `@nessy-agent/*` resolves back into the live repo and reads a concurrent
agent's uncommitted files. `apps/cli` is the exception, its tsconfig using
relative paths.

Token cost was **costed, not half-wired**: no `count_tokens` caller exists
anywhere in the repo and the CLI holds no model connection, so the documented
character fallback is the only available path — labelled as an estimate in both
output shapes, with the on-invoke figure `null` and named as not computed rather
than shown as a zero.

## The finding that could not wait for a plan

**`allowManagedHooksOnly` was wider here than in Claude, and I closed it in
`93f886f1`.**

`settings.md:606` keeps the carve-out for hooks from plugins **force-enabled** in
managed `enabledPlugins`. We have no force-enable, and R30b's implementation
substituted `allowedPluginKeys` for that set, reasoning it is the only managed key
naming plugins. The audit's objection is right: `allowedPluginKeys` means "these
plugins may be used", so an administrator writing it under that natural reading
would silently grant **in-process hook execution — arbitrary code, every turn —
to every plugin on an organisation allowlist**.

Two lists that differ in meaning must not be merged because they are the only two
we have. `areVettedPluginHooksAllowed` now returns `false`: a locked fleet gets
managed hooks only, which is what the lock's name promises. When managed
activation ships a real force-enable set, the predicate reads that set and the
carve-out reopens with its documented subject. Recorded as
`documented, impossible without managed activation — fail-closed until it exists`.

Note what this says about method. R30b's executor made a reasoned, written,
documented decision, and I verified R30b's headline claim myself and found it
sound. Neither of us asked whether the *substituted* set meant the same thing as
the documented one. It took an adversarial pass over a different row to notice.

## Security notes on the items still open

Each is zero-exposure **today** and becomes the main design constraint of its
own fix. Recorded here so a future plan cannot treat any of them as an afterthought.

- **`userConfig`**: Claude's v2.1.207 fix ignores `pluginConfigs` from project and
  local settings, because a cloned repository could supply values that flow into
  hook commands, MCP configs, LSP commands and monitor commands. We are safe only
  because we read no plugin config at all — and this repo already has a
  project-scoped overlay pattern (`resolveRuntimeHookSources({ projectRoot, projectTrusted })`)
  that is the natural, and wrong, way to implement it here.
- **`outputStyles`**: an output style modifies the system prompt, and
  `force-for-plugin: true` applies it automatically, overriding the user's own
  setting. Wiring it naively hands any installed plugin unattended, user-invisible
  write access to the highest-trust text in the turn. `keep-coding-instructions: false`
  is harder still — it must *subtract* the built-in engineering guidance that
  `prompts/system.ts` composes unconditionally, and our prompt builder has no seam
  for that.
- **`experimental.monitors`**: auto-start means an installed bundle executes an
  unsandboxed shell command at session start with no per-invocation approval.
  Three doc-mandated guards must ship in the same slice or an attacker who gets a
  plugin installed gets unauthenticated shell: project-scope plugins must not load
  monitors (a repository checked into version control would otherwise execute
  shell on every collaborator's machine), `${user_config.*}` must be rejected
  rather than substituted, and mid-session disable must not stop a running
  monitor.
- **`dependencies`**: the exposure is the inverse of Claude's. Nothing is
  auto-installed, so the cross-marketplace threat is unreachable — but a bundle
  whose *safety* component lives in a dependency (a PreToolUse guard hook, a
  permission-narrowing plugin) installs and activates here with that dependency
  absent, showing only a generic `partial` badge, where the contract disables the
  dependent plugin until resolved.

## Slice order
