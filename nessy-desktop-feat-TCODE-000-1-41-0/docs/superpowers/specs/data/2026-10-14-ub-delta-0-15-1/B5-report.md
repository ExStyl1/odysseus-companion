## How we ship the browser tool, and on which runtimes

- **One host-supplied tool, `browser_tool`.** It is a CLI-like command string or array. `packages/shared/src/agent/browser-tool-runtime.ts` `executeBrowserToolCommand` (L493) runs it against `BrowserPaneFns`. `SessionManager.ts` binds those functions per session at about L26225–26442 (`click` → `bpm.clickElement`, `detectChallenge` → `bpm.detectSecurityChallenge`, and so on). They reach `apps/electron/src/main/browser-pane-manager.ts`, which uses `browser-cdp.ts`. `RemoteBrowserPaneManager` (thin-client RPC) and `NullBrowserPaneManager` (headless) implement the same `IBrowserPaneManager`.
- **Claude: yes.** It is an in-process SDK MCP server named `session`: `session-scoped-tools.ts:87` (`CLAUDE_BACKEND_SESSION_TOOL_NAMES`) and `:414` (`createBrowserTools`), gated by `getBrowserToolEnabled()` (default `true`, `config/storage.ts:405`).
- **Pi: yes.** The session-tool proxy def is filtered by the same setting (`pi-agent.ts:2917`). It executes through the same runtime (`pi-agent.ts:8449–8496`).
- **Codex: no.** `browser_tool` is `executionMode: 'backend'` (`session-tools-core/src/tool-defs.ts:1518`) and in `SESSION_TOOLS_REQUIRING_HOST_CALLBACK` (`tool-defs.ts:1902`, set closes at L1946). It is absent from both bridged sets: positive control, 30 quoted entries read in L2029–2160, `'browser_tool'` 0 hits. `session-tools-core/src/browser-tool-codex-projection.test.ts` (P6.27) pins that refutation. Every row below is therefore Pi + Claude, with Codex N/A.
- **Native-first (AGENTS.md).** No runtime ships a mechanism for OUR in-app pane: Claude's `chrome` integration drives an external Chrome, and codex has no browser here. The host is the seam (step 2), and upstream's fixes are host fixes too.
- **Fork specifics that matter to these ports:**
  1. The P6.536 CDP-attach trust gate: `browser-cdp.ts:114–126` `ensureAttached` → `requireBrowserTrustOrThrow` → may raise a per-origin card.
  2. The parser was extracted VERBATIM into `browser-tool-command-parse.ts` so the plan-mode read-only classifier (`browser-tool-names.ts` `isReadOnlyBrowserToolInput`, L174–209) and the executor share one parser.
  3. `Message.rawToolInput` / `rawToolResult` are persisted beside the display pair (`packages/core/src/types/message.ts:337–339`, written at `SessionManager.ts:37108–37109`). Upstream has no such field: `git grep rawToolInput v0.15.1` returns 0, against the control `toolInput` 2.
  4. Workspace-scoped pane matching (`workspaceMatches`).
  5. The P6.360 download policy in the network-handler region.
  6. The UA1.24 share snapshot and the transcript export, both of which read `toolInput`/`toolResult`.
- **Draft 1.43.0 plan** (`work/wi16/plan-1.43.0/plan-upstream-adoption-0-14-0.md`): the only browser row is **UB4.6** (v0.13.6 teardown, R14-23). ## Silent changes (not explained by a release-note item)

Each one is folded into the row named:

1. `\;` is decoded to `;` (`decodeEscapes`). Our doc already promises it and our parser does not do it → B5-06.
2. A trailing `;` is ignored, and separator-only input gives "Missing command"; a single command runs its split form → B5-06.
3. Mid-token quote pairs keep protecting `;` from batch splitting (`div[data-x='a;b']` unquoted) → B5-06.
4. A failed batch keeps the earlier outputs; the failing command is not quoted because it may hold a secret → B5-13 / B5-07.
5. React-safe `fill` (native setter clear plus settle) → B5-12 / B5-01.
6. Native `<select>`: label/prefix/substring match, the option list on a miss, the disabled-option reason → B5-12 / B5-01.
7. `scrollIntoView` with `behavior: 'instant'`: smooth scroll left clicks aimed at a moving box → B5-01.
8. Drag is CDP-first; CDP clicks send `mouseMoved` trajectories and `buttons` → B5-01.
9. Annotation labels on-screen elements only, and the cap counts on-screen ones → B5-04.
