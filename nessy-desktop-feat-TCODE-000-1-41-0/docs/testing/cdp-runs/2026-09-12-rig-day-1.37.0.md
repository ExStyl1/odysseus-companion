### C3.262 — K16 `ultrathink` on claude: the keyword changes nothing, and the budget it would raise is not sent at all

**PASS (measured; the row's `unknown` is settled).** Three live gateway sessions, each its own child, plus
the code reading that explains them.

| arm | prompt | child's `--thinking` | assistant entry `effort` | `usage…thinking_tokens` | a `thinking` block arrived |
| --- | --- | --- | --- | --- | --- |
| keyword | `Please ultrathink about this puzzle. …` | `disabled` | `high` | **0** | yes |
| control | the same puzzle, no keyword | `disabled` | `high` | **0** | yes |
| host level `max` | the same puzzle, `setThinkingLevel('max')` first | `disabled` | `high` | **0** | yes |

Each arm is a fresh session with its own child process; `--thinking` is read off the live child's command
line, `effort`/`usage` off the child's own transcript entry under
`<workspace>/claude-config/projects/<project>/*.jsonl`. The three answers were `300 km` / `300` / `300`, so
every arm really ran.

**Why the budget cannot move on this card.** `resolveClaudeThinkingOptions`
(`packages/shared/src/agent/claude-agent.ts`) takes the `minimizeThinking || !isClaude || !effort` branch
for any model the id heuristic does not call a Claude model — `tgpt/deepseek-v4-flash-0731` is one — and
returns `{ thinking: { type: 'disabled' } }`. The SDK's own argument builder (`sdk.mjs`, read verbatim in
the vendored `0.3.247`) maps that to `--thinking disabled`, and maps the alternatives elsewhere:
`{type:'enabled', budgetTokens:N}` → `--max-thinking-tokens N`, `{type:'adaptive'}` → `--thinking adaptive`.
So `--thinking disabled` on the wire is the same statement as *"no budget was sent"*, and the host's own
thinking-level control cannot change it on a gateway card: the `!isClaude` test short-circuits before
`effort` is ever consulted.

**The keyword has no reader on either side of the seam.** `git grep -a ultrathink -- packages apps` is
**empty** — the host never looks at it. The runtime does carry it: in the packaged app's own vendored
binary, `ultrathink` scores **12 lines / 16 occurrences** (`ultracode` 43/156 as the positive control that
the probe reads the file, `megathink` 0/0 and `nessyNotARealSdkKey` 0/0 as negatives). But a keyword that
raises a thinking budget has nothing to raise when the host has already sent `disabled`.

**One thing NOT to misread.** A `thinking` block *does* arrive on all three arms, and it is not Anthropic
extended thinking: it is the gateway model's own reasoning, turned into an Anthropic `thinking` block by
this app's loopback adapter (`packages/codex-responses-adapter/src/anthropic/outbound.ts`). That is why a
thinking block and `thinking_tokens: 0` sit side by side in the same usage object.

**One observation, product-side, found by running it.** Typing a prompt that STARTS with the keyword put
`Ultrathink …` in the composer — the first character was capitalised before the send. The harness caught it
as `composer-mismatch` and the prompt was re-phrased to carry the keyword mid-sentence. A user who types
`ultrathink` first on the line meets the same capitalisation; on this card it costs nothing, because the
keyword is inert here either way, but it would matter on a card where it is not.

control → dont-ask for exactly that reason, and says so in its own prose.

**Getting there cost three harness faults, and the third one is a product finding.**

1. **The persisted choice was read ONCE, which measures the flush and not the answer** (`ff9067d19`). The
   first pass-two run had all three answers at `1 → 0` and still reported FAIL, because `as-is` and
   `dont-ask` read `reopenCompactChoice=undefined` immediately after the count dropped — and both files
   carried `'as-is'` when the same lines were read again minutes later. `persistSession` does not reach disk
   before `respondToPermission` returns. The `summary` arm passed the one-shot read only because its
   `/compact` turn forces a second persist, which is the worst shape a timing fault can take: it looks like
   a real difference between the answers. `persistedChoiceWithin` now polls for 30 s.
2. **An already-answered session is not a usable arm** (`ff9067d19`). `shouldOfferReopenCompaction` takes
   `answered: managed.reopenCompactChoice !== undefined`, so a session this case has answered is never
   offered the card again — and discovery matching only on the name prefix would pick it on the next run and
   score "no card was raised" over a product behaving exactly as designed. Discovery now skips a session
   whose persisted meta carries a choice, so a re-run seeds NEW sessions and nothing has to be deleted.
3. **`switchRuntime` CLEARS a session's name** (`1ca4411d8`, then `c9bae4774`) — see below. This is what
   made pass two come back with `arms found: []` for two of its four arms, and it is a product finding
   before it is a harness one.

### A product finding found by the harness: a session's NAME is dropped by a runtime switch, silently

Four probes on the release build, in the order that separates the candidates:

| probe | reading |
| --- | --- |
| 1 · immediately after `freshSession(name)` returns | the name READS BACK in `getSessions()`; `session.jsonl` carries **no `name` key** |
| 2 · after ONE `sessionCommand({type:'switchRuntime'})` to the claude card | the same read is **`undefined`** — in memory AND on disk |
| 3 · a rename issued after `freshSession` returns, no turn ever run | takes, and REACHES DISK (`msgs: 0`, name on disk) |
| 4 · a rename after the session's first turn | takes in memory and on disk |

So a rename at creation never reaches disk on its own, a runtime switch drops the in-memory copy, and
**nothing on the wire says either happened** — `sessionCommand` resolves with nothing and an error would
have been swallowed by the caller's `.catch` anyway. That is why six of the twelve sessions RS-13's two runs
created have no `name` key at all while six keep theirs, and why RS-38's first seeding pass named four and
two survived: every loser had a `switchRuntime` immediately after its rename.

It is a user-visible loss, not only a harness one: renaming a chat and then changing its model card loses
the title, with no message. PR-RV-2 below.

The harness half is fixed in two places, with the ordering the probes dictate: `freshSession` keeps its
early rename (the name is what makes a new session ineligible for `NavigationContext`'s auto-delete while
the resync click that follows can land on the wrong row) and now verifies and retries AFTER the pane is
ready, which is where probe 3 shows a rename sticks; and `ensureSessionName(session, key, name)` is a new
export for the case that SWITCHES, because `freshSession` cannot know a switch is coming. `rs-38` calls it
after `waitForConnection` and REFUSES on a name that will not take, since the name is the only thing that
survives the relaunch its two passes are separated by.

One more reading from the same probe, written into the helper: **the app DE-DUPLICATES a name it has seen
before by appending a slug** — a second rename to `CDP RV-NAME after the turn` came back as
`CDP RV-NAME after the turn-tidy-quokka` — so a caller whose names can collide must compare with
`startsWith` rather than equality. Every caller today stamps a time into the name.
