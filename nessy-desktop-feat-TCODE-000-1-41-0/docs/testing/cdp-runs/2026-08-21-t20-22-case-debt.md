### ⚠️ The HANDLER_ERROR reproduced — a PRODUCT finding, not fixed here

Run A, leg 6, the anchored codex → claude return:

```
  · leg 6 switch → claude: {"ok":false,"error":"HANDLER_ERROR","errorDetail":{
      "name":"CodedError","code":"HANDLER_ERROR","message":"pi-session-disposal-failed",
      "keys":["stack","message","code","name"]}}
  FAIL leg 6: the switch onto claude-gateway was accepted — HANDLER_ERROR {…}
--- RTS-14: FAIL (required check failed: leg 6: the switch onto claude-gateway was accepted …)
```

The app's own log, same second:

```
16:00:59.026 INFO  IPC: switchRuntime received for session c9bd6212-… connection: claude-gateway
16:01:00.450 WARN  [session] Failed to dispose agent for c9bd6212-… during runtime switch
                   (connection-cross-runtime): codex-runtime-cleanup-failed
```

**The chain.** The DEPARTING runtime's teardown throws —
`cleanupRuntimeResources` → `AggregateError(failures, 'codex-runtime-cleanup-failed')`
(`packages/shared/src/agent/codex-agent.ts:1941`) — the strict drain collects it
and rethrows as `AggregateError(failures, 'pi-session-disposal-failed')`
(`packages/server-core/src/sessions/SessionManager.ts:11032`), and the RPC layer
flattens that to `HANDLER_ERROR`. Three observability defects for the owner:

1. **The message names the wrong runtime.** A CODEX cleanup failure reports
   `pi-session-disposal-failed`, because the strict-drain wrapper is Pi-named.
   The packaged wave's occurrence was read as a Pi-side fault for that reason —
   and its departing runtime was codex too.
2. **The leaf cause never leaves the process.** `cleanupRuntimeResources`
   collects up to four failures (`client.close`, `manager.kill`,
   `adapter.close`, `rmSync` of the managed `CODEX_HOME`) and only the
   AggregateError's own message is logged, so which one failed is unknown even
   with the full main log.
3. **The user sees `HANDLER_ERROR` and nothing else.**

**Nothing is corrupted.** The switch is atomic in the end — read back
immediately afterwards, the session was still on `codex-gateway`, with the four
earlier markers and none for the failed leg:

```
{ "llmConnection": "codex-gateway", "isProcessing": false, "messageCount": 50,
  "markers": ["runtime_switched:pi:anthropic:{\"carry\":\"native\"}",
              "runtime_switched:anthropic:codex-runtime:{\"carry\":\"native\"}",
              "runtime_switched:codex-runtime:pi:{\"carry\":\"anchor\"}",
              "runtime_switched:pi:codex-runtime:{\"carry\":\"native\"}"] }
```

**Frequency: once in four sittings today, once in two packaged sittings
yesterday.** Runs C and D are the non-reproduction control on the same rig and
the same leg family, minutes apart. What made the difference between "a bare
code" and "a named cause" is `switchRuntime` now capturing the wrapper message,
`data` and the `cause` chain beside the code, on the failure path only.
