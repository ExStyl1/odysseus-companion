### C5.13 / RS-17 — Pi's compaction floor is CROSSED for the first time, and the subject arm dies on its way there

**The floor, and why four previous attempts could not cross it.** R1 and R7 each drove RS-17's Pi arm and
each got `Nothing to compact (session too small)` — four readings across two lanes, the last of them with
eight fill turns. R7 identified the constant (`keepRecentTokens: 20000`) and the unit (message CHARACTERS)
but not the lever. Read the rest of the mechanism out of the shipped bundle:

- `prepareCompaction` returns `undefined` — and `compact()` then throws that string — when
  `messagesToSummarize` AND `turnPrefixMessages` are **both empty**
  (`node_modules/@earendil-works/pi-coding-agent/dist/core/compaction/compaction.js`, symbols
  `prepareCompaction` and `findCutPoint`);
- that happens when `findCutPoint`'s backward walk never accumulates `keepRecentTokens`, because `cutIndex`
  then stays at `cutPoints[0]` — the FIRST context message — leaving nothing in front of the cut;
- `estimateTokens` counts characters/4 over `user`, `assistant`, `toolResult`, `custom` and
  `bashExecution`. **A `toolResult` counts**, which makes a file read the cheapest lever available.

So the floor is ~**80 000 characters of transcript**, and the biggest unit one turn can add is a single Read
tool result, capped at 50 KB by `DEFAULT_MAX_BYTES` (`core/tools/truncate.js`). **Why the previous lever
failed**: re-reading a file already in context costs a sentence, not a tool result — a model answers such a
turn from context. A file the session has NEVER seen cannot be answered from context.

**The measurement.** Three unseen 62 811-byte filler files, one read per turn, each landing a **48 512-byte**
`toolResult` in Pi's own thread (the 50 KB cap, measured rather than assumed). The app's own notice then
reads:

> `Compacted context to fit within limits (from ~52,835 tokens)`

and Pi's thread carries a `compaction` entry of 4 507 bytes. **The floor is crossed, the mechanism is
recorded in the case, and the lever is a knob (`NESSY_CDP_COMPACT_FILL_TURNS`, default off) so the claude
and codex arms — which crossed their own floors on the six fixture files alone — are untouched.**

**And the same run reproduces PR-R7-3 on a wider subject.** The subject arm's six-file read turn — the FIRST
turn of an ordinary foreground session, no subagent anywhere — ended with a transcript `error` row reading
exactly:

> `set_auto_compaction timed out after 15s`

R7 met that string once, on a BACKGROUND subagent, and its proposed row is scoped to
`packages/pi-agent-server/src/orchestrator`. Here it killed the first turn of a plain session on the
packaged **1.37.0**, so the failure is not subagent-specific and the scope of that row is too narrow.

**What this costs the E7/E9 reading, stated plainly rather than banked.** Because that turn died, the six
fixture files were never read: the case's own detector check reported `0 of 6 paths appear in the session
file before compaction`, and the `returned: 0` beside it is *"nothing was read"*, not *"nothing came

### C3.344 — the producer of Pi's `.git` card under `bypassPermissions` is the GUARDIAN DENY-NET, not the protected-path table

The row was born from R1's PR-R1-2 with the fix already written into its title: *"correct the table (and its
test) to what the product does"*. F1 refused to take it and asked for the producer to be located first. It is
located, and F1 was right — **the table is innocent, and editing it would CREATE a floor rather than record
one.**

**The table really is skipped under `bypassPermissions`, re-verified at HEAD `bcc1e79c3`.**
`packages/shared/src/agent/core/pre-tool-use.ts` symbol `findNonNegotiableFloors` computes
`protectedPathWrite` only when `protectedPathOutcome(permissionMode) !== 'allow'`, and
`packages/shared/src/agent/pi-harness/protected-paths.ts` symbol `protectedPathOutcome` answers `'allow'` for
exactly that mode. So on the `.git` write R1 drove, the host floor produced nothing and the gate returned
`allow`. A card still appeared. Something else raised it.

**The chain that does raise it, every branch read at HEAD.** In
`packages/shared/src/agent/pi-agent.ts` the gate's verdict meets a second gate:

1. `denyNetEligible` is `(checkResult.type === 'allow' || checkResult.type === 'modify')` **and**
   `guardianMode.permissionMode === 'bypassPermissions'` — so the deny-net exists *because* the mode is bypass,
   and it reads exactly the verdict the table declined to touch;
2. the eligible verdict goes to `packages/shared/src/agent/pi-agent.ts` symbol `consultGuardianDenyNet`, which
   asks `shouldPromptInAutoMode` for the high-risk `band` and returns the verdict **unchanged** when there is
   none (`if (!band) return checkResult` — *"not high-risk in allow-all — runs as today"*);
3. a file write to a protected directory is in that band, because `shouldPromptInAutoMode`
   (`packages/shared/src/agent/core/pre-tool-use.ts`) delegates to `shouldPromptInAskMode`, for which a
   `FILE_WRITE_TOOLS` target prompts;
4. the Guardian is then consulted, and **two of its three outcomes produce something the user sees**: `deny`
   returns `{ type: 'block' }`, and `ask` — the judge declining, failing or its circuit opening — takes the
   branch whose own comment reads *"ask: DOWNGRADE the auto-allow to a human prompt"*, rebuilding the band as a
   `{ type: 'prompt' }` through `markJudgeFailure`. **That prompt is the card.**

So the shipped behaviour is not "the protected-path floor fires in a mode that documents it as bypassable". It
is "`bypassPermissions` skips the floor, and the deny-net that exists only in that mode re-raises the same
write as a judge question". The safety R1 observed is real and is the deny-net's, and it is
**load-bearing in the opposite direction**: a table edit would make the floor fire before the judge is ever
asked, which is a different product — stricter than the deny-net in the cases the judge would have allowed, and
silent about why.

**Status: the row is closed as a REFUTATION of its own title, with the producer named.** No table is corrected
and no test is changed. The one honest residue is a pointer: `protectedPathOutcome`'s docblock says of
`bypassPermissions` *"allowed, as documented … this floor is explicitly bypassable at the top of the ladder"*,
which is true of the floor and is the sentence that sent R1 to the wrong table. That file is W19-d's zone this
wave, so the sentence goes back as a hand-off patch rather than an edit.

**Instrument note.** This is a source trace, not a second drive: the live half is R1's own observation on the
packaged build (a card appeared on the `.git` write under a resolved `bypassPermissions`, control clean, card
baseline 0 immediately before it). What this pass adds is the producer, and no verdict of R1's is restated as
if it had been re-measured here.

### C3.173 (Pi arm) — the SDK emits `toolcall_delta` on the very adapter this fork runs, and our reader already consumes it

The claude arm was answered by R3 (frames ARRIVE and nothing reads them → K5/Claude `partial ᵏ`, the branch
handed to C3.348). The Pi arm was never driven. Its question, in the row's words, is *"whether the SDK emits
`toolcall_delta` for the providers this fork runs"* — so the two halves are **which adapter this fork runs** and
**whether that adapter emits**. Both are answered here, and neither is answered by a count.

**Which adapter this fork runs: `openai-completions`.** The Nessy gateway is OpenAI-shaped
(`…/api/v1/cli/openai-like/v1`), and the Pi connection carries `customEndpoint: { api: 'openai-completions' }`
— pinned by seven `pi-agent-server` real-server suites, and named outright by
`packages/pi-agent-server/src/__tests__/provider-refusal.test.ts` (*"(`dist/api/openai-completions.js`), which
is why this mapping can be read off"*).

**Whether that adapter emits: yes, and the site is verbatim rather than counted.** Pi **0.84.3**,
`node_modules/@earendil-works/pi-coding-agent/dist/bundle/chunks/openai-completions-JD4WAC3R.js`, the streaming
branch at byte offset 11216:

```js
block.partialArgs=(block.partialArgs??"")+toolCall.function.arguments,
block.arguments=parseStreamingJson(block.partialArgs);
…
stream2.push({type:"toolcall_delta",contentIndex:getContentIndex(block),delta,partial:output})
```

— i.e. a `toolcall_delta` per streamed tool-call chunk, on the ordinary `function.arguments` path and not only
on the `custom.input` one. The second site (offset 6682) is the flush at block close.

**And our reader already consumes exactly that shape.**
`packages/shared/src/agent/backend/pi/event-adapter.ts` handles `amEvent.type === 'toolcall_delta'`, keys its
accumulator on `amEvent.contentIndex`, appends `amEvent.delta`, and resolves the tool identity from
`amEvent.partial` — the same three fields the push above carries. So unlike codex (P6.159's open risk that
`acc.id` may not correlate with the later `item/started` tool id) there is **no correlation gap here**: the
`contentIndex` the SDK sends is the key the adapter uses.

| `toolcall_delta` | 14 | 14 |
| `toolcall_start` | 24 | 15 |
| `toolcall_end` | 14 | 14 |
| `text_delta` | 20 | 24 |
| `thinking_delta` | 21 | 25 |
| `ZZZ_FAKE_CONTROL` (negative) | **0** | **0** |

Instrument: `grep -ao <needle> <file> | wc -l` — **occurrences**, not lines, on a minified bundle.

**The verdict, and what it is NOT.** This is a bundle-and-source reading, and the row is explicit that *"a
hermetic test is not a live arrival"*. So **K5/Pi stays `partial`, with this measurement quoted** rather than
being promoted to `covered` off a source read. What is now settled is the part that used to be assumed: the
frames are produced by the adapter this fork actually runs, and the host reads them with a matching key. What a
live run would still add is one observation of a partial tool input crossing the
`PARTIAL_TOOL_INPUT_FLOOR_CHARS` (64) floor end to end — the arm this lane could not reach tonight (see the
scan-storm note above).

#### A methodological correction, recorded because it nearly became a product finding

The first pass at "which files carry it" ran `grep -rln toolcall_delta <dist> | head -10` in the background.
It returned **six** files, **and `openai-completions` was not among them** — a clean, plausible story
(*"the SDK emits tool-call deltas for Anthropic, Google, Bedrock and pi-messages, but not for the
OpenAI-compatible adapter this fork runs"*) that is **false**. The complete answer is **nine** files, the
OpenAI adapter among them with two occurrences.

What truncated it was the I/O storm: over the whole `dist` that grep takes longer than the 120 s background
ceiling, was killed part-way, **and the pipeline still reported exit 0 — because the exit status belongs to
`head`, which exits 0 when its input closes.** AGENTS.md §Traps already forbids the shape ("never `head -N` a
grep before knowing the hit count"); the specific form worth adding is that under a background-timeout kill the
truncation is invisible *from the exit code as well as from the output*. The absence was caught only because a
direct per-file probe with positive controls contradicted it — which is the rule that saved it: an absence
claim needs a positive control on the same rig.

#### A proposed row, stated with both of its readings rather than as a verdict

`sessions:get` and `sessions:getMessages` are answered over a **fixed 30 000 ms** ceiling with no backpressure
and no retry, and the caller receives the raw internal string `Request timeout: sessions:get (30000ms)`. On a
quiet box the same call is **297 ms**. This lane met the timeout under two independent load sources — the
post-reboot scanner, and a sibling lane's `node` at 128 % — so it is not a single confound, but it is still a
CONTENTION reading on a box running eight concurrent agent lanes, which is not a user's machine. Recorded as a
proposed row with both numbers and the conditions, deliberately **not** as a product defect this lane measured.

**Three detector faults were paid before the first arm measured anything, and all three are the same
mistake — trusting a name to identify a process.**

1. `pgrep -f "<token>"` matched **the CLI itself**, because the token travels in the PROMPT and the prompt is
   on the CLI's own argv. The rig read its own command line as the agent's child, declared the precondition
   met four seconds in, and signalled before the server had started — a green-looking arm measuring nothing.
2. Narrowing to "argv[1] is `/bin/sh`" then matched **nothing at all**: the host does not exec the command
   string literally, so no descendant carries the token either.
3. What survives every wrapper is the LEAF process's own argument. The marker is therefore a **unique sleep
   duration** — `sleep 9137` is the `sleep` binary's own argv and is visible however the shell around it is
   spelled. That is what finally found pids 87999 and 88016.
