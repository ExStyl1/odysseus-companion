# Runtime capability gaps — what is unavailable, per runtime, and why

Companion to `runtime-control-boundary.md`. That record draws the ownership
line; this one enumerates its consequences: for each runtime, what a user
cannot do there, **and which of four reasons it is** — because the reason
decides whether it can ever change.

| Reason | Meaning |
| --- | --- |
| **STRUCTURAL** | Follows from how the runtime or our integration is built. Cannot be flipped; changing it means changing the shape. |
| **DECISION** | An owner or engineering decision with a recorded reason. Reversible — it is a product call, not a defect. |
| **PLANNED** | A gap with a row in `docs/superpowers/plans/2026-08-16-clean-runtime-usage.md`. Closes when that row lands. |
| **UNVERIFIED** | Believed from reading code or docs, never measured live. Treat as a claim, not a fact. |

## Every row ends with a `[switch: …]` token, and it is not decoration

**P6.92 (2026-09-06).** `runtime-switch-costs.ts` tells a user what a switch
costs at the moment they take it, and a guard has always walked FROM that table
TO this document. Nothing walked the other way — so a gap could be written here,
reviewed and shipped while reaching no switch dialog, because nobody had decided
whether it should. Gaps are written far more often than cost rows are, which
makes that the direction a new gap actually travels.

So every per-runtime row now carries an explicit verdict at the row, in one of
exactly three shapes, and `runtime-switch-costs-gaps-parity.test.ts` fails until
a new row has one:

| Token | Means |
| --- | --- |
| `[switch: <id>]` | Surfaced at the switch, as that cost row. The id must exist in the live table AND must actually fire INTO this runtime — annotate a row in the wrong section and the suite goes red. |
| `[switch: none — <reason>]` | Ruled out, with the reason written **at the row**. Never inferred from the prose around it: P2.379 measured this guard family misfiring exactly that way. |
| `[switch: owner — <what a promotion would add>]` | It looks like a set difference, and adding a dialog line is a **product** call rather than a lane's. This shape exists so a pending decision is visible as a pending decision instead of being flattened into "no". |

No COUNT of rows is stated or pinned, deliberately. This guard's own row was
born saying "68 per-runtime rows"; the file held 61 when that was measured and 68
the day the guard landed, because four sibling lanes added rows in between.
Totality is the property; a number is a reading with a date.

**Measured 2026-08-16 against `feat/models-fetch`.** File coordinates drift; the
mechanism names and quoted sentences do not.

**Re-measured 2026-08-16 (later, at R11).** Seven PLANNED rows closed the same
day this file was written, so every row below was re-checked against the code
rather than carried forward. The closures are marked `CLOSED`, with what
actually landed rather than what the row predicted — three of them landed
differently from their own prose.

### The mechanism is NOT the one it looks like

The tempting one-line reading — *"`options.ts` spreads `process.env` for the
Claude subprocess and Pi does not, so spread it for Pi too"* — is **false, and
the fix it implies is a no-op.** `buildPiSubprocessEnv` (`pi-agent.ts`) spreads
`process.env` exactly as `buildClaudeSubprocessEnv` (`options.ts`) does.
Measured on one rig with both builders imported and the same host environment:

| | `BASH_MAX_TIMEOUT_MS` | `BASH_DEFAULT_TIMEOUT_MS` | an invented control | key count |
| --- | --- | --- | --- | --- |
| Pi subprocess env | `60000` | `30000` | carried | 69 |
| Claude subprocess env | `60000` | `30000` | carried | 70 |
| host `process.env` | `60000` | `30000` | set | 67 |

**The variables arrive at Pi and are never read.** The gap is a reader gap, in
the tool layer, not an environment gap in either spawn path.

**And the other place the one-liner could be aimed is worse than a no-op.** Pi's
Bash children do *not* get the host environment: they run under the supervisor's
`restricted` profile, a 29-name allowlist plus `LC_*`
(`RESTRICTED_HOST_ENVIRONMENT`, `process-supervisor.ts`), which on the measured
host admitted **5 of 64** host keys (`HOME`, `LOGNAME`, `PATH`, `SHELL`,
`USER`) and dropped 59. That is *stricter* than Claude's default, and it is
what `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` and `CLAUDE_CODE_MCP_ALLOWLIST_ENV` let
a Claude operator opt into. "Spread the host env for Pi" applied there would

## What this list is for

Two uses, and the second is why the reasons matter more than the gaps.

**Honesty at the seam.** Row R11 of the clean-runtime plan turned the STRUCTURAL
rows into something the user is told rather than something they discover — for
the mid-conversation switch, which is the one the plan's target is about. A
cross-runtime pick on a session with NO transcript stays silent by the same
deliberate rule that already governs the dialog, so a user choosing a runtime
for a fresh session is still told nothing.

**A queue for later.** DECISION rows can be reopened at any time — they are
product calls with recorded reasons, and the reason is what a future discussion
should argue with. PLANNED rows close on their own. STRUCTURAL rows change only
if the integration shape changes, which is a much larger conversation and should
be recognised as one before it starts.

## Refusals that are absent on ALL THREE, so they are not per-runtime rows

A capability nobody has is not a runtime capability gap: there is no runtime
where a user can do it, so there is no set difference and no switch loses it.
Recorded here rather than as three identical table rows, because a per-runtime
row would imply a per-runtime answer.
