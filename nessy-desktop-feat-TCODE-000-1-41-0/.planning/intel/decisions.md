## Codex-like Workspace Storage Architecture
- source: docs/architecture/codex-like-workspace-storage.md
- status: locked (Accepted 2026-07-13 for Nessy Desktop 1.0.12; "still in force at 1.15.0")
- decision: Nessy Desktop has one supported runtime layout: storage v2. Nessy-managed Workspaces, sessions, plugins, policies, trust records, and credentials live below `CONFIG_DIR`. External Projects and shared user-authored resources remain outside that tree. The default `CONFIG_DIR` is `~/.nessy-agent`; `NESSY_CONFIG_DIR` may relocate the whole managed tree and a blank value is treated as unset.
- scope: storage v2, CONFIG_DIR, workspaces, sessions, plugins, credentials, capability resolver
- supporting invariants (verbatim from the source's "Operational Invariants"): only storage layout v2 may start the runtime; `workspaceId` and composite `SessionKey` are identity, paths are I/O details; no renderer or remote caller chooses a managed path; plugin installation never implies activation, credential readiness, or trust; repository content never enters resolution before explicit project trust; all capability views come from one captured snapshot and release their leases; shared Gateway auth stays outside the storage cutover and is merge-preserved only by the dedicated DP auth module; "Claude, ChatGPT, and Codex runtime provider flags remain disabled by default."
- cutover rule: legacy conversations, settings, credentials, plugins, resources, and recents are NOT migrated. Unsafe, ambiguous, custom legacy, corrupt, symlinked, or colliding layouts fail closed before normal windows, RPC listeners, sessions, or services start.
- note: the last supporting invariant is contradicted by later-dated lower-precedence sources and by direct measurement on the working tree — see INFO-1, INFO-2 and WARNING-1 in `.planning/INGEST-CONFLICTS.md`. The invariant is LOCKED and is therefore carried unchanged; it is not silently amended here.

## Project-Local `.nessy-agent` And Session Filesystem Roots
- source: docs/architecture/project-local-nessy-agent-and-workspace-roots.md
- status: locked (self-declared "Final architecture for the project-namespace and filesystem-authority cutover (P1-P6, 2026-07)"; no Proposed/Draft marker)
- decision: A Nessy Workspace is the logical isolation boundary for projects, capabilities and sessions; the selected external project is the actual filesystem workspace of its session. `<project>/.nessy-agent` is the ONLY Nessy-native project namespace; `.nessy` has no legacy status (no reader, alias, fallback, migration or warning path). `SessionFilesystemScope` is the ONE captured filesystem authority per session, and every local tool, shell cwd and provider projection resolves through `resolveScopedPath`.
- scope: .nessy-agent project namespace, CONFIG_DIR / ~/.nessy-agent, Nessy Workspace, resolveProjectIdentity, ProjectHandleService, buildNativeCapabilityInventory, config.toml v1 allowlist, SessionFilesystemScope, resolveScopedPath, git metadata protection
- supporting rules: capability collisions resolve Nessy-native > portable > plugin after scope specificity; new-session defaults compose at explicit session > trusted project > Workspace > global > built-in; a project permission mode can only narrow the Workspace/global floor; git metadata stays read-only inside every allowed root and approval cannot broaden it; project agent configuration (`.nessy-agent`, `.agents`, Codex `.codex`/`.agents`) is read-only for file tools; managed Nessy storage is denied even under a broad approved parent; approve-always receipts are revoked on cwd/project switch, identity/trust loss, revocation RPC, session close and Workspace drain, and are never inherited by branches.

## Runtime Control Boundary — Pi, Claude, Codex
- source: docs/architecture/runtime-control-boundary.md
- status: proposed (no Status field; self-described as "a MEASURED SNAPSHOT, taken 2026-08-16 against `feat/models-fetch`")
- decision: The owner's rule for this fork, quoted from the code that implements it (`packages/shared/src/agent/claude-runtime-agents.ts:5-8`): "Pi is ours and is built to Claude Code's documentation; Claude runs 'as-is' so we do not diverge from its real behaviour." Per runtime — **Pi**: almost everything model-visible is ours (system prompt, entire tool list, every tool implementation, every permission decision, compaction instructions, subagents, skills, hooks), signed into a hashed manifest asserted identical on both sides of the subprocess boundary; the Pi SDK contributes **no tool** to a Nessy session. **Claude**: their agent, their tools, their loop, with our gate on every tool call and our tools added alongside theirs — an append block on the `claude_code` preset, per-turn user-message context, a `PreToolUse` hook that can block *and rewrite tool inputs*, an extra MCP server carrying our session tools, our subagent definitions through their own `agents` option, and a handful of env vars. **Codex**: the thinnest control of the three — a config file (14 of 93 schema keys), an approval answer, and text on the user message; no `PreToolUse` gate on this runtime at all.
- scope: Pi runtime, Claude runtime, Codex runtime, system prompt composition, tool surface, permission gate, compaction policy, session tools over MCP, subagent definitions, codex config.toml, network interceptor
- **the R3 change, dated 2026-08-16 and the newest state in this ingest set**: the pinned `permissionMode: 'bypassPermissions'` + `allowDangerouslySkipPermissions: true` — set for every session in every mode, which switched the SDK's permission system off entirely — **is gone**. The user's own mode is translated into the SDK's vocabulary (`claude-permission-mode.ts`; five names are identity, `explore` and `plan` map to `default`), so Claude's mechanism decides and our hook answers it. What makes that safe is R1: our allow now carries `permissionDecision: 'allow'`, which "skips the permission prompt". Consequence: the `permissions` allow/ask/deny blocks of `.claude/settings.json` now take effect on Claude, because the SDK reads those files itself under the `settingSources: ['user','project','local']` we pass. Rules written under `permissionDsl` in a Nessy `permissions.json` remain Pi/Codex-only.
- **corrections this record makes to its own earlier claims**: `canUseTool` is NOT dead code (R2 measured it — `permissions.md` puts three routes ahead of the permission-mode step, each "even in `bypassPermissions` mode"); `AskUserQuestion` is no longer banned (the "no UI" reason was stale); the inline comment at `claude-agent.ts:1911` saying "file tools are disabled (use MCP)" is **stale** and contradicts the code two lines below it.
- do our tools reach each runtime: **Pi** yes and more — all tools are ours, session tools travel a five-hop signed path and execute on the host. **Claude** yes, as an added MCP server next to Claude's own tools — but Claude's own Read/Edit/Write/Bash do the file and shell work, we gate and rewrite rather than substitute. **Codex** partly — a deliberately reduced standalone set; 25 names are excluded at `tool-defs.ts:1185-1216`. Orchestration tools (`subagent`, `review`, `workflow`, `ask_user`, `tool_search`/`tool_load`, `Task`, `Goal`) are **Pi-only on all counts**. Plugin LSP servers and plugin monitors do not reach Claude or Codex at all (`agent.redirect(text)` is a Pi-only steering primitive); plugin *command* hooks do run on every runtime.
- self-declared coordinate caveat: "Every `file:line` in it can drift and some already has… Re-verify a coordinate before relying on it. The durable parts are the quoted sentences, the mechanism names, and the shape of the boundary."
- seven items the record explicitly leaves open, stated as open rather than answered: Codex's `instructions`/`developer_instructions`/`hooks`/`skills`/`plugins` keys never exercised against our bundled binary; the Claude auto-compaction fix has one measurement in one direction and no live case showing a gateway session compacting after it; Codex compaction ordering marked unverified in the code; no end-to-end measurement of what the Codex session-tool reduction costs a user; the stale `:1911` comment's intent unrecorded; the whole record is a static read with no live per-runtime tool-roster capture; the unused Pi loop hooks are untested rather than unavailable.

## Runtime capability gaps — what is unavailable, per runtime, and why
- source: docs/architecture/runtime-capability-gaps.md
- status: proposed (no Status field; "Measured 2026-08-16 against `feat/models-fetch`")
- decision: Companion to `runtime-control-boundary.md`. For each runtime it enumerates what a user cannot do there **and which of four reasons it is**, because the reason decides whether it can ever change: **STRUCTURAL** (follows from how the runtime or our integration is built — changing it means changing the shape), **DECISION** (an owner or engineering decision with a recorded reason; reversible, a product call not a defect), **PLANNED** (has a row in `docs/superpowers/plans/2026-08-16-clean-runtime-usage.md`), **UNVERIFIED** (believed from reading code or docs, never measured live — treat as a claim, not a fact).
- scope: Pi runtime, Claude Agent SDK runtime, Codex app-server runtime, permissions, MCP, skills, plugins, compaction, network interceptor
- Pi gaps: only SDK 0.80.3 will start (DECISION, strict `!==`); session storage format is the SDK's (STRUCTURAL); *when* compaction fires is the SDK's call (STRUCTURAL); agent loop/streaming/tool-call parsing (STRUCTURAL); sandbox/isolation off by owner decision 2026-08-12/13 and not returning (DECISION).
- Claude gaps by DECISION: their native skills mechanism (our path is stronger — a skill's `allowed-tools`/`disallowed-tools` are enforced by us and, per Claude's own documentation, are **not** applied when running through the SDK); native plugin loading (`plugins: []`, but LSP servers and monitors bundled in plugins are genuinely lost); native plan mode (DECISION + STRUCTURAL, refuted rather than unplanned); the user-scope `~/.claude/settings.json`; the `auto` permission mode.
- Claude gaps that are STRUCTURAL: the network interceptor does not apply (Node `--preload` vs a native binary); per-MCP-server `timeout` cannot be expressed (shared connection pool — we hand the runtime a proxy, not its own transport; `alwaysLoad` was listed here until P2.446 and is NOT structural — it exists on the SDK options type and is simply not passed); MCP **resources** and **prompts** never reach the model; model aliases do not resolve on gateway/BYO connections; their auto-compaction is reachable only through an env var; cwd, system prompt, tool set, subagent set and hooks cannot change without a session restart; our `explore` mode has no SDK equivalent.
- Codex gaps: 26 session tools absent (STRUCTURAL — everything requiring a host callback); no per-tool permissions (`enabled_tools`/`disabled_tools` cover MCP **servers**, so a role that must be narrowed is denied wholesale); no native plan mode; a role cannot be stricter than the session by permission mode, nor have its own model; `web_search` disabled; permission rules not consulted at all (PLANNED R6); deferred tool loading (PLANNED C12); MCP tool names carry an extra namespace level; several Codex claims rest on code reading (UNVERIFIED).
- purpose stated by the source: honesty at the seam (a user moving Pi → Claude loses three capabilities today and is informed of none — row R11) and a queue for later, where DECISION rows can be reopened at any time, PLANNED rows close on their own, and STRUCTURAL rows change only if the integration shape changes.
- **STALE ROWS — superseded by measurement.** This record's section header "the SDK's own permission system is disabled, and several capabilities ride the callback that disabling it silences" and its PLANNED row *"Permission rules written in Claude's own `.claude/settings.json` do nothing — R3"* were **overtaken by R3 before this ingest**. Measured on the working tree: commit `3b78acb00` ("feat(claude): the runtime decides for itself — bypassPermissions is gone") updated `runtime-control-boundary.md` and did **not** touch this file; `claude-agent.ts:2397-2415` now carries the R3 comment in place of the pin, and `settingSources: ['user','project','local']` is passed at `:884`. Do not schedule R3 as open work. See INFO-8 in `.planning/INGEST-CONFLICTS.md`. The R2 row in this file *was* updated (marked CLOSED 2026-08-16) — so the file is partially, not wholly, current. The rows resting on the same bypass premise (`auto` mode as "a consequence of running our own gate", `PermissionRequest`/`PermissionDenied` automation events, approvals never persisting through the SDK's mechanism) were **not** re-measured here and are neither confirmed nor refuted.

## Extension-first Pi agent runtime
- source: docs/architecture/extension-first-pi-agent-runtime.md
- status: proposed (no status field in the document; classifier recorded locked=false)
- decision: Nessy Desktop ships the Pi-compatible runtime as a closed, host-composed subprocess pinned to Pi `0.80.3` (upstream tag `v0.80.3`, commit `a23abe4a695df8b69b613f73e9fdda2a8af894d4`, MIT, Node `>=22.19.0`). The runtime loads only source-controlled built-ins from the closed extension registry; it does not scan or install ambient extensions, skills, prompts, or `node_modules`.
- scope: Pi agent runtime, closed extension registry, authority map, ToolExecutor, PermissionService, MCP, LSP, checkpoint/rewind, child sessions
- authority rule: there is one owner for each durable or effectful responsibility (capability selection, tool identity, Pi session construction, tool execution, permission/approval, process/isolation, tasks, child orchestration, MCP/LSP, context, checkpoint/rewind, lifecycle hooks, persistence, desktop projection, provider dialects). "There is no standalone manifest ingress, fallback runtime, second resolver, second scheduler, or shadow permission path." The host fails before spawning Pi when the finalized capability runtime is absent.
- measured state: 48-case corpus, 46 implemented, 0 partial, 0 missing/blocked, 2 accepted provider differences; canonical weighted score 190/192 (98.96%) implemented, 192/192 (100%) accepted contract.

## Unified plugin adapter runtime
- source: docs/architecture/unified-plugin-adapter-runtime.md
- status: proposed (has a `## Decision` section; no status field, no "Accepted" marker)
- decision: Nessy Desktop has one installed/runtime plugin representation, `NessyPluginManifest`. Codex and Claude bundle layouts, marketplace catalogs and the internal marketplace are import/acquisition adapters only — never a second runtime mode. Runtime behavior depends only on normalized capabilities, selected scope, trust, credentials and immutable bundle identity; it never inspects `adapterId`, provider format or marketplace origin to choose behavior.
- scope: NessyPluginManifest, plugin adapters, Codex bundles, Claude bundles, hooks, MCP servers, LSP servers, marketplace
- supporting rules: every hook type executes through the same single hook executor and the existing trust, permission, isolation, supervision and receipt owners — never a second dispatcher; which events may return a blocking verdict is decided by `AGENT_EVENT_CONTRACTS_V1`, not by the hook's type; Themes and Channels are deferred (Themes with an author-facing diagnostic); Codex bundles do not yield prompt/slash commands or sub-agents by inference.

## Organization control over MCP servers
- source: docs/architecture/managed-mcp-access.md
- status: proposed (no status field; classifier recorded locked=false despite decision-record content)
- decision: Organization control over MCP servers is implemented as `allowedMcpServers`/`deniedMcpServers` on the managed Pi policy, gated by `isManagedMcpServerAllowed` in the capability-input filter before any denied server is materialized. Denylist is evaluated first and nothing overrides a denylist match.
- scope: managed Pi policy, allowedMcpServers, deniedMcpServers, MCP servers, plugin marketplace, strictPluginOnlyCustomization, capability-input filter, workspace MCP browse pool
- deliberate deviations recorded by the source: the `serverName` allowlist charset is WIDER than the upstream page (adds `.`), because narrowing a grant would strip an existing deployed entry fleet-wide; an invalid whole `allowedMcpServers` value is enforced as `[]` while an invalid whole `deniedMcpServers` field is dropped; a deny entry carrying two recognised keys has EVERY valid key enforced as its own deny (recorded `tightened`) rather than being stripped; the `${VAR}` expansion bypass is inherited deliberately.
- declined: `managed-mcp.json` fixed deployment, disable-MCP-entirely, claude.ai connectors / `allowAllClaudeAiMcps` / `disableClaudeAiConnectors`, `allowManagedMcpServersOnly`, `--mcp-config`/`--strict-mcp-config`, the `claude mcp add` refusals, `OTEL_LOG_TOOL_DETAILS` MCP usage monitoring.
- known open (1): the managed lists and the origin lock do not cover the workspace BROWSE pool, so a denied server is still contacted when the Sources UI warms the pool ("Recorded here rather than changed").
- known open (2), and the premise it rests on is now contested: this record states "Pi is the shipped default runtime — the Claude and Codex providers are off unless a build enables them", and uses that to justify the managed-MCP gate running only when `context.provider === 'pi'`. Two withheld-then-released SPECs record the same gate as a live unenforced admin control, and the flag premise no longer holds on the working tree — see WARNING-1 in `.planning/INGEST-CONFLICTS.md`.

## Guardian command judge
- source: docs/architecture/guardian-command-judge.md
- status: proposed (no status field)
- decision: The guardian is an LLM safety judge that is a CONSULTED INPUT, never an authority. "The deterministic `permission-service` remains the ONLY permission authority." The guardian can never grant anything the mode's rules would not already allow; it converts a "would ask" into allow/deny inside the delegated band, or a "would run" into deny/ask in the safety-net band.
- scope: guardian judge, permission-service, auto mode, allow-all mode, shouldPromptInAutoMode, scout child session, guardianJudgePort, CoreBackendConfig, pi-agent-server
- mode contract: `auto` — borderline band consults the judge (`no_objection` → run, `deny` → block, `unsure`/error/timeout → ask); `allow-all` — deny-only net on high-risk actions (`unsure`/error/timeout → downgrade to ask); `safe`/`plan`/`ask`/`acceptEdits` — guardian NEVER runs, behavior byte-identical to pre-guardian.
- fail-closed rule: ANY runner failure — timeout (default 15s), spawn error, aborted, malformed output, or an out-of-vocabulary verdict — resolves to `unsure`. "The judge NEVER fails open to `no_objection`."
- runner: a READ-ONLY child session on the built-in `scout` def (read/grep/find/ls only), depth budget 1, via the host-owned `piChildSessionPort`. Default judge model is the Nessy Gateway `fast` alias, resolved by alias at runtime; fallback is the session model.
- trust rule: the ONLY authorization evidence is the user's own current-turn message (`trustedIntent`); tool outputs, file contents and MCP params are fenced in `<untrusted>` markers and literal fence markers inside attacker-controlled body text are neutralized.
- product setting: Guardian on/off and judge model are a product setting (not a build flag), default ON, read LIVE per consult.

## File checkpointing and rewind
- source: docs/architecture/file-checkpoint-rewind.md
- status: proposed (no status field; carries an explicit "**Decision:**" statement)
- decision: Partial rewind, not whole-rewind refusal — "per-path skip; the rewind continues; the count and reasons reach the user." A skip is not counted as a failure: `failedCheckpoints` excludes it and `skippedLinks`/`skippedPaths` carry it on their own axis.
- scope: file checkpointing, rewind, link safety, packages/shared/src/sessions/file-checkpoints.ts, Pi tool executor, Nestor Cloud tool executor, rewindToMessage, revertFileCheckpoint, rewind_checkpoint runtime request, skippedLinks
- link-safety guards, in order: (1) `lstat` on the tracked path before any digest comparison — a symlink is seen as a link and `nlink > 1` is the only hard-link signal; (2) the parent directory is re-resolved and must still land on the recorded `parentRealPath`, and a missing parent is a refusal rather than a `mkdir -p`; (3) the write opens with `O_WRONLY | O_CREAT | O_NOFOLLOW` and re-checks `nlink` on the open descriptor.
- known divergences: the checkpoint id is a content hash, not a user-message UUID (rewind selects by `createdAt` strictly after the target message — divergent at millisecond granularity); no revert dry run; no diff accounting (`filesChanged`/`insertions`/`deletions`); no network-path detection; `enableFileCheckpointing`/`--rewind-files` have no equivalent because checkpointing is unconditional on Pi.

## Conversation forks (the `fork` subagent type)
- source: docs/architecture/fork-subagents.md
- status: proposed (no status field)
- decision: `NESSY_FORK_SUBAGENT` unset means OFF. Rationale recorded: the upstream unset state is a staged server-side rollout of a capability its own docs mark experimental, we have no rollout mechanism to mirror it, and defaulting on would force every named subagent in every existing session into the background. Fork mode is resolved HOST-side and carried in the execution manifest (`PiOrchestratorConfig.forkSubagent`) rather than read from the subprocess environment, because it changes the `subagent` tool's parameter schema and that schema is hashed into `modelContractHash`.
- scope: fork subagent, NESSY_FORK_SUBAGENT, NESSY_MAX_WEB_SEARCHES_PER_SESSION, web_search budget, background tasks, modelContractHash, /subtask
- must-not-regress rule: "A fork that cannot inherit **fails**; it never runs as a summarised or seeded child." Three enforcement paths: `resolveForkBranchOptions`, `createSession` + `startPiChildRuntime` lineage re-check, and `createManagedSession` pinning a restored fork child to `sdk-fork`.
- verification caveat carried by the source: "Code-complete is not live-verified here." AGT-1…AGT-5 in `docs/testing/cdp-live-checklist.md` were still open, and AGT-1 was once filed as PASS and had to be retracted.

## Transport locality: which clients may do what
- source: docs/architecture/transport-locality.md
- status: proposed (Decision + Consequences sections present; no status field)
- decision: "Locality is read from the capability set the client advertises at handshake, not from a flag it sets." `isLocalClient(server, clientId)` tests for `client:showItemInFolder`. An unknown or empty capability set reads as REMOTE (fail closed).
- scope: transport locality, LOCAL_CLIENT_CAPABILITIES, isLocalClient, RemoteBrowserPaneManager, REMOTE_CLIENT_PERMISSION_MODE_CEILING, permission mode, mobile client, packages/server-core/src/transport/capabilities.ts
- what it gates: browser tools (`client:browser:invoke`; a phone-only session is refused with `BROWSER_NO_CAPABLE_CLIENT`) and `REMOTE_CLIENT_PERMISSION_MODE_CEILING = 'auto'` (a remote caller asking for anything above it, in practice `bypassPermissions`, is refused with `CAPABILITY_UNAVAILABLE`).
- what it deliberately does not gate: reading and steering a session — messages, approvals, stop, model and permission mode below the ceiling — for any authenticated client.
- recorded consequence: `apps/cli` classifies as REMOTE today because only the Electron preload handles `client:showItemInFolder`; verified 2026-08-09 that this gates nothing it currently does, and the stated fix for the future is for the CLI to advertise the capability, not to loosen `isLocalClient`.
