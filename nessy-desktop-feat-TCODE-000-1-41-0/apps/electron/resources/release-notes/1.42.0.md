# Nessy Desktop 1.42.0

October 14, 2026

The task-board release. Sessions can live on a Kanban board: drag them between columns,
watch a "needs input" badge when one is waiting for you, and give every column its own
colour and drop status. A task on the board is a graph of subtasks that the Conductor runs
across Pi, Claude Code and Codex — each subtask an ordinary chat in the task's folder,
outputs feeding the next, a failed grade sending the named subtasks back for repair, and a
run confirmation that shows every subtask's runtime, connection, model and mode before an
agent-written plan runs. Generate drafts a plan from your goal without writing anything
until you save it. Projects give those chats a home: a folder bound through the trust
picker, a description the agent sees on every runtime, assets, per-project board columns,
and grouping, filtering and colour in the session list. Pages let agents build small HTML
apps and reports in the workspace — sandboxed, with posters, scheduled refresh and
click-gated source actions recorded in a signed approvals ledger — and any page, file or
chat can be published to the company's t-artifacts service through one review card that
shows the exact bytes first. Sharing a chat now sends a masked snapshot instead of the raw
conversation, agents no longer close sessions on their own, "Always Allow" remembers
exactly what you approved, and a long close-out pass tightened what runs without asking on
every runtime. The bundled agent runtimes ship current: Claude Code 2.1.280, Pi 0.87.1 and
Codex 0.162.0.

## NEW
- Codex sessions can set their own status and labels, like Pi and Claude Code; on every runtime the tool now refuses a session outside its own workspace instead of reporting a change it never made.
- Host approvals (page grants, script and refresh approvals, confirmed task specs, project context) are kept in a signed per-workspace ledger, and agents can no longer write task specs, page and project configuration, project context or the ledger directly.
- Press Up in an empty composer while a turn is running to stop it and get your prompt back (a draft you cleared with Esc Esc is restored first).
- Background session alerts — an optional chip above the composer when a session in the background finishes; turn it on in Settings → Appearance (off by default).
- Settings → Appearance gains a Kanban board section (a colour per column and the live-pulse toggle) and a Status on move section (the status a session takes when dropped into a column).
- Agents can publish a page they wrote — an HTML or Markdown file in the session's folder — to the company's t-artifacts service with `publish_artifact`, on Pi, Claude and Codex. Every publish and every update shows a confirmation card first, in every permission mode: the page preview with scripts disabled, its size, scripts and external hosts, who can open it and when the link expires (1–30 days, default 7). Automations, scheduled runs, subagents and Don't ask mode cannot publish. `list_artifacts` lists the pages the session published.
- `nessy://pages` and `nessy://pages/page/<slug>` deep links open the Pages library and a page.
- On Pi, an agent that starts a new session with `spawn_session` can place it in a project.
- A shared chat becomes a readable snapshot of the conversation — messages, tool calls with their input and output, thinking collapsed — with file paths made relative to the project and tokens, keys and card numbers masked; the home folder and account name never leave the machine.
- Task board — switch the session list to a Kanban board with the List / Board toggle; drag cards between To Do, In Progress and Done.
- Task board cards show which runtime runs the session (Pi, Claude, Codex) and a "Needs input" badge when the session is waiting for your answer.
- Board cards move with the keyboard: Space picks a card up, Left/Right choose the column, and Space drops it there, applying the column's drop status. Escape cancels. Screen readers announce each step, and board cards open with Enter.
- Agents on Pi, Claude Code and Codex can put a task on the task board with create_board_task: it lands in To do and never runs on its own, and it stays in the agent's own folder, project, connection and enabled sources.
- A task on the board can run as a graph of subtasks across Pi, Claude Code and Codex. Each subtask is an ordinary session in the task's folder and project. Each one's answer feeds the next, and the task's own session checks the result at the end.
- Published pages — Settings → Workspace lists the pages you published to t-artifacts (from Nessy or elsewhere) with open, copy, extend (up to no expiry) and delete, each confirmed; a delete that cannot reach the service is kept and retried after you sign in again. A published page's tool row shows a chip with the link and its expiry date.
- inline HTML and Markdown previews of a file gain a Publish button that goes through the same confirmation card (with a preview of exactly what is sent) as the agent's publish_artifact, in every permission mode.
- Task editor: New Task on the board creates a task with subtasks (goal, acceptance criteria, models grouped by connection with their runtime, permission mode, sources, skills, folder); edit it from the tile's pencil or the chat header's Edit task.
- Pages: agents can list, create, update and delete workspace pages; deleting a page always asks you first, in every permission mode, and is refused when nobody is there to answer.
- Share a chat again — from the session menu or the chat header. Nessy shows a confirmation card first (what is sent, how many secrets were masked and paths shortened, the 7-day expiry, a preview of the exact page) and then publishes a masked snapshot to t-artifacts with your dp account; Update share re-sends it to the same link, Stop sharing deletes it, shared chats carry a Chat badge in Published pages, and deleting a shared chat asks whether to stop sharing too.
- Agents can build and keep Pages: six page tools let Pi, Claude and Codex (Codex over its per-session link) list, read, create, update, feed data to and delete the workspace's Pages; deleting a page always asks you first, in every permission mode.
- A Pages authoring guide ships with the app (~/.nessy-agent/docs/pages.md), and every runtime is told how to build Pages: self-contained HTML, data through the page's own store, no network from the page.
- Pages: the sidebar has a Pages entry. It opens a library of the pages your agents build; you can open a page in a sandboxed view, rename it or delete it. When a page asks to open a link, Nessy shows you the full address and opens it only after you confirm.
- The Pages library shows a preview poster for each page, rendered offscreen in a window with no network access, no pop-ups and no navigation, and refreshed when the page's content changes; "Refresh preview" on a tile or in the page menu re-captures it.
- Run a task from its card or from the editor (Create & Run / Save & Run). If you did not save the plan yourself (an agent wrote it, Generate drafted it, or it changed on disk), the run asks for confirmation first, and the app refuses the run without it. The confirmation lists every subtask's runtime, connection, model and permission mode, the sources and the plugins it will see. The editor's Results tab shows the grade, each subtask's answer and Pause / Resume / Stop, and you can resume a run that an app restart interrupted.
- Generate: the task editor drafts a plan from your goal for you to review and edit. The draft writes nothing and is deleted unless you save it.
- Pages can refresh their data on a schedule, and automations can run a workspace script. In both cases nothing runs until you approve the exact script in the app. Any change to the script asks again, a refused run says why in the history, and scripts get no app secrets in their environment.
- Pages can ask to use your sources and scripts. A request appears only after you click inside the page, and the dialog shows exactly which source, tool, endpoint or script (with its fingerprint) the approval allows. Approvals are kept in the app's protected approvals store, expire after 30 days or when the page changes, and are listed and removable under the page's "Approved actions". A granted source that needs reconnecting shows a Reconnect row that opens it in Sources.
- A session bound to a project now gives the agent the project's description and details on every runtime (Pi, Claude, Codex), and a project without a folder also carries its own MEMORY.md as project memory; an edit reaches the next message. The text the agent sees is written by the app and checked against its approvals ledger, so a file rewritten behind the app's back is never used as is.
- Projects can hold reference files (assets). You can upload, list and delete them per project. Every session bound to the project, on every runtime, sees the list of files with their types and sizes and can open any of them when it is relevant.
- Publish a page: the Share button on a page publishes a view-only copy to the company's t-artifacts service (7 days; extend it in Published pages). Before anything is sent you see exactly what will be published, and you choose whether to include the page's current data. A page that may run a script on your computer is never published; a page with approved actions is published only after you confirm the copy is view-only; pages carrying token-shaped values are refused. Unpublish closes the link, and deleting a published page takes its copy down first.
- Projects. A Projects section in the sidebar holds a page per project (sessions, assets, settings, folder). Sessions can be grouped, filtered and colour-marked by project from the session list, and pages can be filtered by project and moved between projects.

## KNOWN

- **A task's orchestrator chat is marked done when its run completes** — including a run
  you started yourself from the card or the editor. The grade and every subtask's answer
  stay on the Results tab; this close-out is the documented behaviour, not a defect.
- **A subtask runs under the mode its task's run was started with.** A subtask starts in
  its own mode capped at the orchestrator's, and every later change is capped again. While
  a run is live, the cap is the broader of the orchestrator's current mode and the mode the
  run last dispatched under. So lowering the orchestrator mid-run applies to the subtasks
  dispatched after the change, and a run resumed after a restart keeps the mode it was
  started with. Stop the run to lower it at once.
- **Once every subtask of a task has run, the card's Play is disabled** until you add a
  node; this matches the upstream task board.
