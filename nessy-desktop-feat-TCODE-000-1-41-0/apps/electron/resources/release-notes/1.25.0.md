# Nessy Desktop 1.25.0

August 11, 2026

## IMPROVED

- A plugin's MCP server that stands down as a duplicate now says which parts of that plugin went quiet with it. Previously the reason explained that the server was a duplicate and stopped there, while the plugin's own hooks and skills kept pointing at a server that would never start — with nothing on screen to say so. The reason — shown on the server's detail page in Sources, the page its row in the MCP servers panel opens — now reads "Parts of this plugin that used this server are inactive:" followed by the hooks and skills that referenced it, so it covers the whole effect and not just the server. (A plugin's agents are not listed yet.)
- In the rare case a server's name still can't be used in tool names, it now says so instead of quietly having no tools. Such a server would otherwise look normal while every one of its tools was silently dropped; it is now marked "This server's name can't be used in tool names; its tools are unavailable", so an empty tool list has a visible reason.
- **If you have a permission rule naming an MCP server whose name contains a space, a dot, or any other character outside letters, digits, `-` and `_`, rewrite it — check your deny rules first.** Those names are now converted (see below), and a rule — allow, ask, or deny — written against the old raw name (`my server.v2`) no longer matches. A deny rule still naming the old spelling stops blocking anything, so the tool it used to block now runs unchallenged; an allow or ask rule still naming it simply stops granting anything. Look in Settings -> Permissions, in any subagent file with `disallowedTools`, and in any skill file with `allowed-tools` or `disallowed-tools`. For an ordinary name you can work out the new spelling from the conversion rule itself — each run of characters outside letters, digits, `-` and `_` becomes a single `_`, so `my server.v2` is `my_server_v2`. For a name with no usable character at all, the generated `server-…` name is not shown in the **MCP servers** panel — that panel keeps showing the name as you wrote it — but it appears in the server's own tool names, `mcp__server-…__<tool>`, the first time one of its tools asks for permission. Built-in servers and plugin-provided servers are unaffected — their names were already in the accepted form.

## FIXED

- Codex runtime sessions now receive the same context every other runtime gets — including the list of available skills. Previously a Codex conversation never saw the skills you or your plugins installed, so the model could not use or even mention them; now they are listed and invocable, the same as on Pi. Session commands such as `/compact` are unaffected — they reach the runtime as commands, not as text buried in context.
- MCP tool calls on Codex runtime sessions now appear in the transcript, like every other tool. The call itself already worked, but nothing showed in the conversation — you could not see what ran, with which arguments, or what came back. The row also names the tool's real server rather than the internal bridge it travels through.
- A Codex runtime request to widen its sandbox (extra file or network access) now shows a permission card naming exactly what is being granted — previously the card mislabeled the request as a shell command, and whichever button you pressed, the answer was lost in transit and the request failed. Grants are per-turn only and never widen beyond what was asked.
- An MCP server's sign-in link (an OAuth or consent URL) now opens for you on Codex runtime sessions: a permission card shows the exact link, and approving it opens your browser. Unsafe links (anything that is not plain http/https) are refused outright. Previously every such link was silently declined, so servers requiring a browser sign-in could not be connected from that runtime.
- MCP tool labels in the chat now split the server and tool halves correctly for every name shape — a server whose converted name contains `_` (such as `my_server_v2`) previously showed its raw internal name instead of a clean "server: tool" label, and Codex rows leaked the internal name into the tool half.
- MCP tools now work on Codex runtime sessions. Every MCP tool call on that runtime was silently rejected: the runtime's approval question was answered in a shape it could not read, so it treated the answer as "no" — the transcript showed the tool failing with "user rejected MCP tool call" while no question had ever been shown to you. The approval now surfaces as a normal permission card (naming the tool and its arguments) and your answer reaches the runtime intact. Note that on the Codex runtime a permission card appears for these calls in every mode except Don't Ask — that runtime asks per call by design.
- An installed plugin's skill metadata — its `allowed-tools` list and its `paths` activation patterns — now survives installation. Previously both fields were dropped while the plugin was being installed, with two visible consequences: the "parts of this plugin that used this server are inactive" list above could never name a skill for an installed plugin, and a skill that declared `paths` was invocable at any time instead of only when a matching file is in play. Both now behave as the skill's author wrote them. Note for skill authors: a plugin skill declaring `paths` now activates only for matching files — if your skill stopped appearing, that is the declared gate working, not a loss. Plugins installed before this version keep their old metadata until they are updated or repaired (Plugins → the plugin's menu → Repair); the skill's tool ceiling at invocation time was never affected — it is read from the skill file itself.
- An MCP server declared in a project's `.mcp.json` — or by another native declaration — whose name contains a space, a dot, or any other character outside letters, digits, `-` and `_` now works. Those characters made every one of the server's tools unusable — the name could not be turned into a valid tool name, so nothing the server published ever reached the agent. Such names are now converted automatically: `my server.v2` becomes `my_server_v2`. A server whose name has no usable characters at all — an entirely Cyrillic or Japanese name, for example — is given a stable generated name of the form `server-<short code>` instead of the empty name it used to get.
