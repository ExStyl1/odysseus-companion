# Nessy Desktop 1.28.1

August 16, 2026

## NEW

- **The app's own built-in tools are now fetched on demand as well.** In 1.28.0 this applied only to tools from your connected sources; the groundwork noted there is now the feature. Nine built-ins — notebook editing, web search and fetch, review, the subagent controls, background shell and workflows — are described to the agent only once it decides to use one. The tools that a turn always needs, like reading files and running commands, are still there from the first word.

- **Most of the app's session tools follow the same rule.** Things you reach for by name — managing sources, plugins, automations, scheduled work, the browser, worktrees — are now pulled in when they are called for rather than described in every message. Ten stay present at all times because a turn's own flow depends on them: submitting a plan, todos, tasks, goals and memory.

- **Nothing becomes unavailable, and that is a property of the design rather than a hope.** A tool fetched on demand is still listed in the session, still findable, and still arrives before it runs. The cost of the app guessing wrong about which tools you need is one extra lookup, never a missing capability.

## IMPROVED

- **Pinning a source is now covered by a test that fails if it ever stops working.** 1.28.0 explained that pinning still means "always present" after the on-demand change; that promise is now checked automatically in both directions, along with the separate setting that turns the mechanism off entirely.

## FIXED

- **An internal check that could pass for the wrong reason.** A test verifying the app reads a setting correctly also pinned the exact list of tools that setting affects. Every time the list legitimately grew, the check broke — twice in two days — while never testing the thing it was written for. It now verifies the setting and ignores the list.

## KNOWN OPEN

- **Codex support for on-demand tools: investigated, and the answer is that it cannot be settled the cheap way.** 1.28.0 said we could write the setting but had not tested whether Codex acts on it. We have now tested it, and the result is that writing it proves nothing: the Codex version we ship accepts an invented setting name exactly as readily as a real one, with no error either way. Confirming this properly needs a full conversation run against a live model rather than a configuration check, and that is scheduled separately. Nothing is claimed in either direction until then.
