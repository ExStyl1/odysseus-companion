# Nessy Desktop 1.25.1

August 12, 2026

## NEW

- **Command isolation is now off by default, and there is a setting to turn it back on.** Until now the commands an agent ran on your machine were wrapped in the operating system's sandbox, which confined what they could read, write and reach on the network. That wrapping is now disabled unless you ask for it. The reason is that the sandbox was breaking real work: a browser started by a test tool crashed the moment it launched inside it, which read as "the agent is broken" rather than "the sandbox refused something", and there is no way to tell the two apart from where you sit. Turning it off until agent workflows settle is a deliberate trade: **agents now run with the same access to your machine that you have, and nothing at the operating-system level stands between a command and your files.** The permission rules are unchanged and still ask before risky actions — but they are now the only layer, so a mode that skips prompts skips everything. One nuance worth knowing if you use Auto mode: its judgement of what counts as risky was calibrated when commands were sandboxed, and it has not been re-calibrated for running without that, so treat it as somewhat more permissive than before rather than less. To turn isolation back on for every project, add `"sandbox": { "enabled": true }` to `~/.nessy-agent/config.json`; an organization policy can also require it, and a policy's answer wins over a personal setting in both directions. Note that with it on you may hit the browser crash described above until a later release fixes the profile. One thing does not change: the diagnostic script tool stays sandboxed in every mode, because it is meant to run untrusted snippets and needs network isolation to be worth anything.

- **Your agents now work on Codex sessions.** An agent you created yourself — or one an installed plugin provides — used to exist on Pi and Claude runtime sessions and be silently absent on Codex: the catalog called it active, but nothing on a Codex session could actually start it. Every agent Codex can express is now registered with the session as a Codex "agent role", so the model can start it by name and it runs with exactly the instructions you wrote. Codex has no per-agent tool policy, so an agent that declares its own tool list or permission mode cannot be expressed faithfully there — such an agent is deliberately left out rather than allowed to run wider than you wrote it, and the session log says which agent was left out and why. This was verified by driving the running app: a spawned agent answered with a value that exists only in its own definition, an undeclared name was refused, and an agent with a tool list was refused with the reason logged.
- **You can watch a Codex session's subagents work.** When the model on a Codex session starts one of your agents, sends it input, or waits for its answer, those steps now appear in the chat as tool rows — the same way MCP tool calls already do — instead of the whole exchange happening invisibly. A start that the runtime refuses no longer leaves a row spinning forever either: it closes with the refusal.

## IMPROVED

- **A skill's `allowed-tools` now pre-approves tools instead of restricting them — and in the modes that skip prompts, that means an unlisted tool now runs.** The field was built as a hard ceiling: a tool a skill did not list was refused outright, in every mode, even one where you have turned confirmations off. That was never what the field means — it names the tools the assistant may use *without asking you* while the skill runs, and everything else stays available through the normal permission flow. Two consequences, and the second is the one to read carefully. Skills written for the wider ecosystem now work as their authors intended: a skill listing `Read Grep` no longer breaks the moment its own instructions need anything else, and a skill whose list came out empty is no longer impossible to invoke at all. But **in Auto and Bypass Permissions, a tool the skill never listed is no longer stopped by that ceiling — it simply runs**, where before the ceiling refused it even in those modes. Combined with command isolation now being off by default (above), a skill in Bypass Permissions runs with nothing between it and your machine. If you want a skill to be unable to reach a tool, name that tool in `disallowed-tools`, which removes it from the pool outright — that is the field that restricts, and it is unchanged.
- **Command-line runs no longer skip every permission check by default.** `nessy-general-agent run` used to create its session in the mode that approves everything without asking, so a scripted run had the widest possible permissions unless you narrowed them yourself — the opposite of what you would expect from a default. Runs now start in the normal mode that asks. Because a scripted run has nobody to ask, a request for approval is refused, the run stops with a line explaining what was refused, and the exit code is non-zero, rather than the command hanging or silently proceeding. **If you have scripts relying on the old behaviour they will now stop at their first privileged action** — pass `--dangerously-skip-permissions` (or `--permission-mode bypassPermissions`) to restore it, or pre-approve just what the script needs with allow rules.
- The mode that skips all permission checks now refuses to start as `root` or under `sudo`, unless you are inside a container. Running an agent with no approval prompts and full administrator rights on your own machine is the one combination with no safe outcome, so it is declined with an explanation instead. Containers are exempt, since isolating the whole machine is exactly what they are for. More generally, now that command isolation is off by default, that mode is the one place the two changes meet: with no prompts to catch a mistake and no sandbox to contain one, nothing is left between the agent and your files — so run it inside a container or a VM, and keep to the modes that ask on a machine you care about.
- Your acceptance of the responsibility warning for that mode is now remembered properly. It used to live in the window's local storage, so clearing site data or moving between builds could ask you again; it is now stored with your other settings.
- A plugin's MCP server that was refused now says so on the plugin's own page. Previously such a plugin read "Active" with no issues detected while nothing it shipped was actually running — the refusal was recorded, but only somewhere you never saw. The plugin page's **Diagnostics** section now lists every refused server together with the reason it was refused, and a plugin whose components all ended up unusable no longer presents as healthy: its state reads "no usable components (see Diagnostics)" instead. Plugins installed before this version keep their old records until they are updated or repaired (Plugins → the plugin's menu → Repair).
- The Marketplace's "Showing N of M" counts the rows you can actually see. With a filter applied, the number after "of" used to count every plugin in every marketplace, so a filtered list of two could claim to be showing two of four with no way to reach the other two. The total now matches the filter, and when your search does have matches in marketplaces the current filter hides, the line says so — "· 2 more in other marketplaces" — instead of leaving the difference unexplained.

## FIXED

- Codex runtime sessions start again in the installed app. This is the important one: in 1.25.0 the Codex runtime could not start at all in the released build. The app checks that the bundled Codex program is byte-for-byte the one we shipped, and the signing step that prepares the app for distribution rewrote that program, so the check refused to start it — a check meant to protect you was stopping the runtime instead. Signing now leaves that program untouched, and the build itself refuses to produce a release whose check would fail, so this cannot reach you again. Everything 1.25.0 fixed for Codex — skills in the session's context, MCP tool rows in the transcript, the sandbox permission card, and MCP tool calls working at all — was unreachable in that build and is now genuinely available, verified by driving the installed app. One item from that list was **not** true when 1.25.0 implied it was — an MCP server that needs you to sign in through a browser link could not ask you to, on Codex sessions — and that is fixed in this release too; it has its own entry below.
- **A correction to the 1.25.0 release notes.** That release said a plugin skill's tool list "at invocation time was never affected" by the metadata that got dropped during installation. That was wrong, and the effect was worse than described. A skill whose `allowed-tools` contained an entry with a comma inside its parentheses — `Agent(reviewer, planner)` — lost the entire list, and that same list is what the app reads when you invoke the skill, so the skill was not merely displayed incorrectly: it could not be invoked at all. If one of your skills stopped running for no visible reason, this was very likely why. Such lists now survive intact, along with a `paths: [a, b]` pattern list written on one line. As above, a plugin installed before this version keeps its old records until it is updated or repaired (Plugins → the plugin's menu → Repair).
- An installed plugin whose agents grant tools in the parenthesised form no longer breaks every message. If a plugin shipped an agent declaring `Agent(security-reviewer)` or `Workflow(scan)` in its tool list, every single turn on Pi ended with an internal error from the moment that plugin was installed — the conversation was unusable while it stayed installed. A grant that can be resolved is now kept and applied as its author meant it; one that cannot be resolved is simply left out of the agent's tools and reported in the session log, rather than ending the turn.
- A rule you wrote to block a tool now blocks it. A tool entry carrying more than one argument — `Agent(reviewer, planner)` — was being split on the comma into two fragments, neither of which matches any tool. In an agent's `tools` list that quietly cost you the grant; in a `disallowedTools` list it was a security problem: the denial silently stopped denying, and the tool it named ran unchallenged. This affected agents you wrote yourself exactly as much as ones a plugin provided, and on every format we import. Multi-argument entries now survive everywhere, and an entry that is not text at all is still refused by name rather than passed over in silence. **If you added a `disallowedTools` rule with multiple arguments and never saw it take effect, it is in force now — check that it blocks what you meant it to block, and nothing you rely on.**
- A denial naming a whole MCP server now denies that server. Writing `mcp__github` in `disallowedTools` — without a trailing `__*` — matched nothing at all, so every one of that server's tools stayed available to the agent while the rule looked like it was doing its job. The bare server name is now honoured, and it is honoured in both places that check it, so the rule holds however the agent was started.
- A grant naming a whole MCP server now gives the agent that server's tools. The reverse of the rule above: `mcp__playwright__*` in an agent's `tools` list expanded to nothing, so an agent written around a server's tools started without a single one of them and no explanation. It now receives exactly that server's tools, and only that server's.
- **A workspace whose project folder went missing can start chats again.** If you had set a default folder for a workspace and that folder was later renamed, moved, deleted, or simply lived on a drive you had not plugged in, the workspace stopped being able to open a new chat **at all** — the New Session button and the panel's "New session" both did nothing, with no message explaining why, and the only way out was editing a settings file by hand. A folder the app cannot reach is now treated as an absence: the chat opens with no default folder instead of refusing to open. Your setting is deliberately **left in place** rather than cleared, so an external drive you reconnect later simply starts working again. The one case that still refuses is the one that should: if the path is reachable but now holds a *different* folder than the one you pinned, that is a change of identity and the app says so rather than quietly using it.
- **An MCP server can now ask you to sign in, whichever runtime you are on.** Some MCP servers need you to open a link in your browser and log in before they will do anything, and the way they ask is a question sent back to the app. Only Pi ever answered it. On Claude and Codex sessions the question was refused as an unknown request, so the server waited on an answer that was never coming and the connection quietly never came up — no card, no error, nothing you could act on. The cause was ordering rather than the runtimes themselves: the app states what it is willing to be asked at the moment it connects to a server, and on a shared workspace that connection is made before the part of the session that shows you dialogs exists — so it stated "I cannot be asked", and nothing set up later could change that answer. The app now always states that it can be asked, and works out *who* to ask when a question actually arrives, matching it to the session whose tool call the server is answering. When it cannot tell which session a question belongs to — two sessions using one server at once, with no call of yours in flight — the question is declined and the reason recorded, rather than being put to the wrong person or left hanging. **On Pi there was a second half to this.** When a request had to be refused, the explanation was itself shown as a dialog with a single **OK**, and that dialog was rejected for having only one button — so on the one runtime where this worked, the refusal you were meant to read was the one thing that never appeared. Refusals are now shown.
- A WebSocket MCP server is visible everywhere it should be. Such a server connected and its tools worked, but internally the app filed the connection and its settings under two different identities, so anything that looked the server up by its configuration missed it — the per-session list of servers, its tool timeout, and the option that pins its tools into context.
- A subagent that declares a tool the app cannot resolve now starts. The app and the runtime each worked out the agent's isolation setting from a different tool list — the one the agent declared versus the one that could actually be resolved — so a single unresolvable entry made the two disagree and the agent failed to start with an internal mismatch. Both now read the same rule.
- **An agent that asks for a model your connection cannot serve now runs anyway.** Plugin agents often pin a model by name — `claude-security` asks for "opus" — and on a Nessy Gateway or custom-endpoint Claude session no such model exists, so starting that agent failed with "model not available". The agent now runs on the session's own model instead, and the session log notes the substitution naming both models. The same situation was already handled this way on Pi and on Codex; the Claude runtime was the one place it still failed. Sessions connected directly to Anthropic are unchanged — there the model names an agent asks for genuinely exist.
- **A Codex session that used subagents could lose the assistant's final answer.** Everything a Codex subagent did was reported over the same channel as the main conversation, without saying whose it was. The moment a subagent finished, the app took *its* completion as the end of *your* turn — so the assistant's actual final message, composed after collecting the subagent's answer, never reached the chat, and what you saw as the reply was the subagent's own last line. Every report is now attributed to the conversation it belongs to.
- **On the Claude runtime, four things now work that quietly did not.** A trusted project's own instructions and output styles now actually reach the model — previously they were read but never delivered, so a Claude session behaved as if your project files were empty. Turning the 1M-token context window *off* is now honoured; before, the app kept requesting the large window even after you disabled it to conserve your usage limits. An image too large for the model is now scaled down and retried instead of refused with "Image too large". And closing a Claude session no longer disconnects MCP servers that your other sessions were still using — teardown was treating the shared workspace pool as its own.
