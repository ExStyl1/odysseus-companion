# Разрешения

Ваш агент может делать значимые вещи — читать files, запускать shell commands, редактировать documents, вызывать external tools. Чтобы вы контролировали, насколько далеко он действует самостоятельно, Nessy Desktop запускает каждую session в одном из шести permission modes Claude Code, задающих уровень autonomy.

::: tip
**Просто попросите.** Агент может настроить permissions за вас. Попробуйте "Allow `npm run build` in Plan mode" или "Let me run pytest without a prompt", и он сам изменит configuration files.
:::

## Permission Modes

Есть шесть режимов, здесь они перечислены от самого строгого к самому свободному. Меню режимов предлагает пять из них, и **SHIFT+TAB** в chat input переключает между теми же пятью (см. [Переключение режимов](#переключение-режимов)).

| Mode | Config value | Behaviour | Лучше всего для |
| ---- | ------------ | --------- | --------------- |
| **Не спрашивать** (Don't ask) | `dontAsk` | Никогда не спрашивает; выполняет только заранее разрешённое, остальное запрещает | Запуски, где некому ответить |
| **План** (Plan) | `plan` | Read-only; готовит план, пишет только файл плана и папку data самой session | Исследование и проработка задачи до начала |
| **Ручной** (Manual) | `default` | Всегда спрашивает перед изменениями | Пошаговая работа под контролем |
| **Принять правки** (Accept edits) | `acceptEdits` | Авто-принятие правок files в session roots; остальное спрашивает | Быстрая работа с доверенными files |
| **Авто** (Auto) | `auto` | Сам решает, что разрешать: low-risk actions проходят, borderline actions проверяет судья безопасности | Режим по умолчанию — длинные tasks с safety checks |
| **Обход разрешений** (Bypass permissions) | `bypassPermissions` | Разрешает всё заранее, без prompts; некоторые вызовы всё равно отклоняются | Trusted repeatable automation |

Это собственные permission modes Claude Code с его config values, поэтому знакомое оттуда имя режима означает здесь то же самое, а названия и описания — те, что показывает меню режимов Claude Desktop. Собственный режим Nessy Desktop **Explore** («Обзор») с версии 1.41.0 упразднён, его место занял Plan — см. [Режим Explore упразднён](#режим-explore-упразднен) ниже.

### Режим — это ваше намерение; сколько его удержать, решает рантайм

Таблица выше — это то, о чём вы просите, и читается она одинаково, на каком бы
рантайме ни шла сессия: так сделано намеренно, потому что ваше намерение не
меняется, когда вы переключаете рантайм посреди разговора.

Меняется принуждение. На **Pi** и **Claude** Nessy проверяет каждое действие до
того, как оно выполнится, — режим обеспечиваем мы. На **Codex** это не так: тот
рантайм сам решает, о чём вас спрашивать, а Nessy отвечает, а не преграждает.
Отсюда два следствия, и теперь приложение называет оба рядом с режимом, который
вы выбираете, а не оставляет вас узнавать о них потом:

- В Plan на Codex изменение файла удерживает собственная read-only
  песочница Codex, а не Nessy: команда, которая пишет файл, отклоняется, а
  правка файла сначала спрашивает вас. Дополнительные каталоги, подключённые к
  session, и папки plans и data самой session остаются доступными для записи.
- Plan на Codex не даёт плана, который можно утвердить, — у этого рантайма нет
  такого понятия.

Единственное исключение — Don't ask: в этом режиме Nessy отвечает на запросы
Codex, поэтому всё, что не разрешено заранее каким-нибудь правилом, отклоняется
без prompt. Codex всё равно выполняет команды, которые сам считает безопасным
чтением файлов, вообще не спрашивая нас, и — при включённом и при выключенном OS
sandbox — точно так же выполняет всё, что позволяет его read-only sandbox, в том
числе запись в каталог, добавленный к сессии: для неё не нужно правило и не
появляется карточка.

Там, где Codex всё-таки спрашивает Nessy — вызов MCP-инструмента или инструмент
сессии, — Nessy отвечает по вашему режиму и вашим правилам, как на Pi и Claude
Code:

- В Plan инструмент записи источника и инструмент настройки сессии
  (например, правка автоматизации) отклоняются, а не показываются вам карточкой.
- Правило allow или deny для `mcp__<source>__<tool>` или для инструмента сессии
  одобряет или отклоняет вызов без карточки.
- Правило deny для MCP-инструментов — одного инструмента, целого сервера или
  шаблона — убирает названные им инструменты из Codex совсем, а правило ask
  заставляет Codex спрашивать даже про инструмент, который его сервер помечает
  как read-only. Единственный пробел: источник, который ещё подключался, когда
  запускался рантайм Codex, может добавить read-only инструмент, и Codex выполнит
  его без вопроса — до перезапуска рантайма; сессия записывает об этом заметку.
- **Always Allow** на MCP-карточке Codex действует до конца сессии.
- **Always Allow** на карточке shell-команды Codex сохраняет правило для этой
  команды в разрешениях рабочего пространства, и следующие сессии в нём
  выполняют её без вопроса; карточка говорит об этом под кнопками. Карточка,
  разрешение которой сохранить нельзя, говорит, что оно действует до конца сессии.
- С версии 1.41.0 shell-команда, о которой Codex вас спрашивает, после
  одобрения выполняется **вне** sandbox Codex, как это делает сам Codex: Nessy
  больше не добавляет в этот sandbox свой список запретов на учётные данные (см.
  `deniedPaths` ниже). Только пока до Codex доходит одна из ваших собственных
  записей `deniedPaths`, одобренная команда остаётся внутри sandbox; тогда всё,
  что он блокирует, например запись вне рабочей папки, по-прежнему не
  срабатывает, карточка об этом говорит, а **Always Allow** на такой карточке
  действует до конца сессии и не сохраняет постоянного правила.
- Правило ask для shell-команды или MCP-инструмента ждёт ответа на карточке,
  которая называет правило, включая Bypass permissions, и у этой карточки нет
  **Always allow**; когда ответить некому, вызов отклоняется с названием правила.
- Правило deny или ask, добавленное, пока сессия Codex работает, действует со
  следующего хода этой сессии — в том числе для команд, которые Codex выполняет
  без вопроса.
- При включённом [авто-ревью Codex](/ru/reference/config/config-file) проверяющий
  отвечает только в Auto и Bypass permissions: в Manual, Accept edits и Plan
  вопрос Codex приходит вам, а Don't ask его отклоняет. Если политика Codex
  вашей организации разрешает только проверяющего, решает она — при включённом
  и при выключенном авто-ревью: проверяющий отвечает и в Manual, Accept edits и
  Don't ask (так что в Don't ask он может одобрить то, что не разрешено заранее
  правилом), Codex отклоняет ходы Plan, и сессия сообщает об этом.

Старые конфигурации продолжают работать: упразднённый `explore`, домиграционные написания `safe`, `ask` и `allow-all`, ещё более старые `execute` и `ask-to-edit`, `automatic`, а также синоним Claude `manual` — постоянные aliases на каждом пути чтения. Session files, workspace config, определения агентов, automations и deep links принимают их (без учёта регистра и разделителей) и разрешают в режимы из таблицы выше; `explore` и `safe` разрешаются в `plan`. Новые записи всегда используют текущие написания.

### Каждый режим на каждом рантайме

Шесть режимов означают одно и то же на каждом рантайме; различается то, как рантайм их удерживает:

- **Claude Code** запускает каждую session в собственном режиме Claude Agent SDK с тем же именем, а проверка Nessy выполняется перед каждым вызовом инструмента, как описано в разделах ниже.
- **Pi** следует страницам Claude Code: собственная проверка Nessy читает режим напрямую и решает каждый вызов до его выполнения.
- У **Codex** таких режимов нет, поэтому каждый режим отображается на собственные настройки Codex — его песочницу, его вопросы о согласовании и его проверяющего auto-review, — а Nessy отвечает на вопросы Codex по вашему режиму и правилам. Где у Codex нет подходящей настройки, таблица говорит, что отличается:

| Режим | На что настроен Codex | Что отличается на Codex |
| --- | --- | --- |
| **Авто** (Auto) | Собственная настройка Codex *Default*: он читает, правит и выполняет команды внутри workspace и спрашивает, прежде чем выйти за его пределы. При включённом [авто-ревью Codex](/ru/reference/config/config-file) на эти вопросы раньше вас отвечает проверяющий Codex. | Авто-ревью по умолчанию выключено, и без него Auto на Codex работает как Accept edits: вопросы Codex приходят вам. Проверяющий оценивает только то, о чём спрашивает Codex. |
| **Ручной** (Manual) | Та же настройка *Default*. Вопросы Codex приходят вам. | Codex не умеет спрашивать перед правкой или командой внутри workspace, поэтому на Codex режим Manual правит файлы и выполняет команды там без карточки; спрашивает он о том, что выходит за пределы workspace. |
| **Принять правки** (Accept edits) | Та же настройка *Default*. Вопросы Codex приходят вам. | У Codex нет настройки «только правки»: внутри workspace он выполняет и любую команду, которую позволяет его песочница, а не только `mkdir`, `touch`, `mv` и `cp`. |
| **План** (Plan) | Собственная настройка Codex *Read Only*; папки plans и data этой session и добавленные каталоги остаются доступными для записи. Вопросы Codex всегда приходят вам, а не проверяющему. | Собственный режим плана Codex не используется, поэтому плана, который можно утвердить, нет, а команды во время планирования не проверяет судья, как на Pi. |
| **Обход разрешений** (Bypass permissions) | Настройка *Default*, и Nessy отвечает «да» на всё, о чём спрашивает Codex, если не срабатывает защитный порог или ваше правило ask. При включённом авто-ревью первым отвечает проверяющий Codex. | Собственный *Full Access* Codex никогда не используется: защищённые папки остаются только для чтения, а shell-команду, которая пишет вне workspace, отклоняет операционная система, — это уже, чем Bypass в Claude Code. |
| **Не спрашивать** (Don't ask) | *Read Only*. То, что не разрешено заранее правилом, отклоняется без prompt, и проверяющий никогда не отвечает — если только политика Codex вашей организации не разрешает только проверяющего (см. выше). | Каталог, добавленный к сессии, остаётся доступным для записи, поэтому команда или изменение файла в нём выполняются без правила и без карточки, тогда как Don't ask в Claude Code отклоняет их, если их не разрешает правило. |

Сессии **Nestor Cloud** вместо этого используют собственные режимы облачного агента — см. [Переключение режимов](#переключение-режимов).

### Don't Ask Mode (`dontAsk`)

Don't ask (в интерфейсе — «Не спрашивать») никогда не спрашивает: он существует для запусков, где некому ответить. Выполняется только заранее разрешённое: то, что явно допускают ваши permission rules, встроенный read-only набор команд и вызовы, одобренные hook-ом. Всё остальное запрещается сразу — с причиной, которую агент может отразить в отчёте, вместо prompt, который повис бы навсегда.

Поскольку спросить некого:

- `WebFetch` и browser tool запрещены, если их заранее не разрешает allow rule.
- Web search разрешён заранее: он выполняется здесь, как и в любом другом
  режиме, без карточки, если deny rule не называет search tool. Deny rule
  `WebSearch` покрывает собственный поиск Claude Code, `web_search` у Pi,
  собственный search tool приложения (`mcp__session__web_search`) везде, где
  он предлагается, и собственный поиск Codex на карточке ChatGPT (Codex): он
  выключается при старте сессии, а для rule, добавленного посреди сессии, — со
  следующего хода. Allow или ask rule для `WebSearch` не переносится на search
  tool приложения и не доходит до собственного поиска Codex: у него нет шага
  подтверждения. Домены поиска не ограничены, если оператор не задал
  [`NESSY_WEB_SEARCH_ALLOWED_DOMAINS`](/ru/reference/config/environment-variables#nessy-web-search-allowed-domains).
- Запись в [защищённые пути](#защищенные-пути) запрещается, а не запрашивается.
- Любой tool, требующий участия человека, запрещён.

Don't ask никогда не попадает в ротацию **SHIFT+TAB** и не предлагается в меню режимов — случайно провернуться в режим, который молча всё запрещает, было бы сюрпризом. Выбирайте его осознанно: как workspace default, из automation или через deep link. Session или automation, которая в нём работает, по-прежнему показывает режим по имени — «Не спрашивать».

### Plan Mode (`plan`)

Plan (в интерфейсе — «План») — read-only режим для исследования и планирования: агент может собирать информацию, но не может менять ваши файлы. Он может закончить работу планом, который вы одобряете до любого выполнения, или просто ответить вам — как и в plan mode Claude Code, план не обязателен.

**Allowed:**

- `Read`, `Glob`, `Grep` — reading and searching files
- `WebSearch`, `WebFetch` — web search and page fetching
- `Task`, `TaskOutput` — sub-agent orchestration
- `TodoWrite`, `SubmitPlan` — planning
- `LSP` — read-only language-server queries (hover, definitions, and so on)
- `browser_tool` — команды браузера, которые только читают страницу или состояние браузера
- Read-only bash commands (см. [Safe Commands](#safe-commands) ниже)

**Blocked или спрашивается:**

- `Write`, `Edit`, `MultiEdit`, `NotebookEdit` — кроме двух папок ниже
- MCP tool mutations (create, update, delete)
- Write-style API requests (POST, PUT, DELETE)
- Bash mutations (`rm`, `mv`, `mkdir`, and the like) и команды браузера, меняющие страницу или состояние браузера, — они не отклоняются сразу, см. правило для shell ниже

Четыре core write tools жёстко заблокированы и не включаются через configuration, с двумя исключениями в Pi и Claude Code. Первое — сам план: агент записывает его как Markdown-файл (`.md`) в собственную папку plans этой session через `Write`, `Edit` или `MultiEdit`, а `SubmitPlan` затем открывает вам карточку плана. Второе — собственная папка data этой session: любой из четырёх инструментов может записать туда любой файл, и карточки [защищённого пути](#защищенные-пути) это не вызывает — файл записывают и Claude Code, и Pi. File tools Pi открыта вся собственная папка session, кроме её записей (`session.jsonl`, `attachments`, `long_responses` и файлы, которые там хранят Nessy и Pi: `.pi-carry`, `.pi-sessions`, `.pi-agent`, `.orchestrator`, `meta`, `hook-env`, `file_checkpoints`, `checkout-move.patch`, `tool-metadata.json` и `api-error.json`): в них они никогда не пишут, а читают из них только `attachments` и `long_responses` — там агент находит приложенные вами файлы и полный вывод большого результата инструмента. Больше Plan ничего не пишет: ни другой файл в папке plans, ни что-либо в каталоге, добавленном к session, ни через shell. На Codex папки plans и data и добавленные каталоги остаются доступными для записи, как описано выше.

Если инструмент отклонён, агент получает причину и отвечает вам — ход не обрывается. Отказ относится к одному вызову инструмента, а не ко всему ответу, поэтому вы видите объяснение и можете решить, что делать дальше.

Shell commands во время планирования подчиняются своему правилу: read-only команды выполняются свободно, а в Pi sessions команду вне read-only набора проверяет [судья безопасности Guardian](#судья-безопасности-guardian), когда он доступен (это поведение по умолчанию) — одобренные команды выполняются, отклонённые блокируются. Без судьи, а также в Claude Code, такие команды запрашивают подтверждение у вас; Codex сам решает, о чём вас спрашивать, как описано выше. Команда браузера, меняющая страницу или состояние браузера, обрабатывается так же.

Plan mode никогда не заканчивается сам. Отправка плана агентом оставляет session в Plan; следующее сообщение уточняет план, а не выходит из режима. Принятие плана — единственный явный шаг, который меняет режим session. Одобрение из Plan переключает её в **Manual**: план может выполняться, а каждое изменение по-прежнему спрашивает вас. Одобрение из Manual, Accept edits, Auto или Bypass permissions оставляет режим прежним. Одобрение никогда не переключает session в Bypass permissions — в Bypass можно попасть только через его собственное подтверждение. Повторный вход в Plan столь же явный. Используйте Plan, когда хотите, чтобы агент осмотрелся и порассуждал без риска случайного изменения, или когда хотите сначала получить предлагаемый подход, а затем выполнить его на подходящем уровне autonomy.

### Режим Explore упразднён

До версии 1.41.0 у Nessy Desktop был седьмой собственный режим, Explore (`explore`, в интерфейсе — «Обзор»), которого нет в Claude Code. Его больше нет, его место занял Plan:

- Session, automation, workspace default, определение агента, deep link или флаг CLI, где указан Explore — или его старое написание `safe`, — открывается в Plan и записывается обратно как `plan`. Automation, сохранённая в Explore, показывается и выполняется как Plan, а при следующем сохранении любой automation в файле будет `plan`.
- Plan теперь тоже пишет в папку data этой session, как это делал Explore. Остальные записи Explore убраны: всё в папке plans, кроме `.md`-плана, каталоги, добавленные к session, пути из `allowedWritePaths` и shell-перенаправления в эти папки. Settings → Permissions больше не предлагает `allowedWritePaths`; `permissions.json`, где он ещё указан, загружается как прежде, но ни один режим его не читает.
- Бывшая session в Explore и в остальном ведёт себя как Plan: в Pi shell-команда вне read-only набора или команда браузера, меняющая страницу, уходит к Guardian или спрашивает вас, а не отклоняется.
- Для сообщений из ваших других sessions она тоже считается Plan. Там, где Bypass permissions доступен, Plan считается режимом, обходящим permission prompts, поэтому такая session теперь придерживает до вашего решения сообщение из session, которая спрашивает разрешения, и принимает без вопроса сообщение из обходящей session ([`crossSessionInbound`](/ru/reference/config/config-file) меняет это умолчание).
- Собственные инструменты агента, которые запускают session или создают и правят automation, предлагают шесть режимов; агент, который просит там `explore`, получает ошибку с их перечнем.

### Manual Mode (`default`)

Manual (в интерфейсе — «Ручной») применяет three-tier policy к bash commands:

| Command type | Behaviour |
| ------------ | --------- |
| **Safe commands** | Auto-allowed, как в Plan mode |
| **Regular commands** | Prompt for approval; доступно "always allow" |
| **Dangerous commands** | Prompt every time; "always allow" недоступно |

**«Safe commands» — это read-only allowlist, и он выполняется без запроса.** Это
тот же набор, который Plan mode выполняет свободно — см.
[Safe Commands](#safe-commands), он читается из `default.json`, так что его можно
расширить, — и команда из него выполняется вообще без карточки, хотя вы её
никогда не разрешали и хотя Manual — это режим, который вы выбрали именно чтобы
вас спрашивали. Поэтому `echo`, `uname` и им подобные здесь не запрашиваются
никогда, ни на одном рантайме, а правка файла в той же сессии — запрашивается.
Это posture, а не недосмотр: Manual спрашивает про команду, которая может что-то
изменить. Ни один режим не спрашивает перед read-only командой — Plan выполняет тот же
набор свободно, — поэтому, чтобы вас спрашивали и о ней, добавьте для неё правило ask.

Когда агент хочет запустить что-то, что не является safe command, вы получаете prompt:

```
The agent wants to run: npm install lodash

Allow?  [y]es  /  [n]o  /  [a]lways allow
```

- **yes** — разрешить эту одну operation
- **no** — отклонить её
- **always** — запомнить одобрение, чтобы та же команда в следующий раз выполнилась без карточки. Что именно запоминается и на какой срок, зависит от рантайма: см. [Что запоминает Always Allow](#что-запоминает-always-allow). Кнопка не предлагается, когда точно запомнить нечего (в том числе для dangerous commands).

**К любому из ответов можно приложить заметку.** На карточке есть поле для
комментария, и написанное доходит до модели: как причина, если вы отказываете, и
после результата, если разрешаете. Работает одинаково на Pi, Claude Code и
Codex — на Claude Code причина отказа едет на собственном поле рантайма, а не
через наше. «Always allow» намеренно заметку не принимает: заметка объясняет
один ответ, а правило переживает ответ, которым оно было создано.

### Accept Edits Mode (`acceptEdits`)

Accept edits (в интерфейсе — «Принять правки») авто-подтверждает запись files (`Write`, `Edit`, `MultiEdit`, `NotebookEdit`), чтобы агент мог итеративно править files без prompt на каждое изменение, но по-прежнему спрашивает про shell commands, network calls и MCP tool actions.

Авто-подтверждение ограничено, а не глобально. Запись принимается автоматически, только когда её цель лежит внутри write roots этой session — working directory, корень workspace, папки plans и data самой session и дополнительные каталоги, подключённые к session. Запись куда-либо ещё запрашивается как обычно.

Одно действие приложения считается записью файла: сохранение заметки памяти в файл памяти session или проекта — оно принимается как запись внутри этих roots. Заметка в вашу общую пользовательскую память и любое другое действие приложения — установка plugin, управление sources, automations или расписаниями — по-прежнему запрашиваются.

Четыре простые filesystem commands — `mkdir`, `touch`, `mv`, `cp` — тоже авто-подтверждаются, и только когда каждая цель находится внутри тех же roots, а команда состоит ровно из одной этой команды: любой pipe, цепочка, redirect или substitution возвращает её к обычному prompt. Этот набор сознательно уже, чем эквивалент в Claude Code: `rm`, `rmdir` и `sed` здесь никогда не авто-подтверждаются, а написания с env-префиксом или обёрткой (`env mkdir …`) не проходят по этому исключению — удаление или обёрнутая команда всегда запрашиваются.

### Auto Mode (`auto`)

Auto (в интерфейсе — «Авто») — режим управляемой autonomy и режим, в котором стартует новая session. Действия с низким риском, которые приложение может уверенно классифицировать, выполняются без prompt; пограничные действия в Pi sessions проверяет [судья безопасности Guardian](#судья-безопасности-guardian), прежде чем вернуться к prompt, а в Claude Code и Codex они сразу запрашиваются у вас; явно рискованные действия запрашиваются как обычно. Используйте его для длинных coding tasks, когда хочется меньше прерываний, но без полной свободы без prompt.

Другой стартовый режим задаётся для каждого workspace в **Workspace Settings** или на уровне приложения через workspace default `permissionMode`.

Auto держат в рамках три ограничения:

- **Запись ограничена теми же session roots, что и в Accept edits.** Auto никогда не авто-подтверждает запись файла вне working directory, корня workspace, папок plans/data и дополнительных каталогов session — такая запись идёт через обычный prompt.
- **В Pi sessions Auto сам ставит себя на паузу, когда судья продолжает возражать.** Если судья безопасности блокирует 3 действия подряд или 20 всего за session, Auto mode останавливается: session переходит в Manual, сообщает вам (и агенту) причину, и запросы подтверждения возобновляются. Вернитесь в Auto явно, если он снова нужен. В Claude Code и Codex режим сам по себе никогда не меняется.
- **Первое чтение за пределами рабочих каталогов спрашивает.** Раньше у чтения не было границы вообще: у записи были roots, у чтения — ничего. Теперь Auto поднимает одну карточку при первом чтении сессии за пределами её рабочих каталогов, с тремя ответами: *Разрешить один раз*, *Продолжать разрешать* (гасит запрос на эту сессию) и *Блокировать впредь*, который отказывает в таких чтениях и во всех последующих сессиях. Последний ответ записывает `blockReadsOutsideWorkingDirectories: true` в `config.json`, и оператор может выставить этот ключ напрямую: это жёсткий забор, действующий во **всех** режимах, включая Bypass, а не просто запрос.

Отказы самого судьи теперь можно прочитать. **Settings → Разрешения**
показывает, что судья безопасности Auto запретил, и показывает правила, которые
выданы самому судье, — так что развёртывание больше не инструктирует вторую
модель втайне. Та же страница объясняет, как складываются области workspace и
приложения, и помечает правило workspace, которое умолчания и так дают, как
недействующее.

### Bypass Permissions Mode (`bypassPermissions`)

Bypass permissions (в интерфейсе — «Обход разрешений») даёт полную autonomy. Operations выполняются без prompts — именно это делает возможными hands-off workflows.

Он сознательно закрыт дополнительными барьерами:

- Он **предлагается по умолчанию** — и в ротации SHIFT+TAB, и в меню режимов. Чтобы убрать его для workspace, исключите его из cyclable modes в **Workspace Settings**.
- **Первая активация** на установке показывает подтверждение ответственности; отказ оставляет session в текущем режиме.
- **Managed policy**, установленная администратором, может полностью отключить режим; session, запросившая его, попадает в самый строгий доступный вариант.
- Он **не восстанавливается, когда session открывается заново** с диска, например после перезапуска приложения: session, сохранённая в Bypass permissions, открывается в режиме, в котором стартовала бы новая session в её workspace (Auto, если вы не меняли режим по умолчанию), — так же поступает Claude Code при возобновлении session. Чтобы продолжить без подтверждений, снова переключитесь в Bypass permissions.

Даже в Bypass permissions остаются три предохранителя: удаления, нацеленные на корень файловой системы или домашний каталог (`rm -rf /`, `rm -rf ~`), запрашиваются в любом режиме как circuit breaker, собственные управляющие записи Nessy (файлы, которые решают, что можно будущим sessions, — см. [Защищённые пути](#защищенные-пути)) отклоняются, а в Pi sessions [Guardian](#судья-безопасности-guardian) может заблокировать действия с высоким риском.

Проверка внутри одного tool в Bypass permissions не является границей, потому что собственные shell-команды агента вокруг неё выполняются без карточки. Например, `plugin_plan_install` отклоняет repository URL, для которого у него нет маршрута (скажем, адрес `file://` или `git://` — см. [Плагины](/ru/plugins/overview)), а session в Bypass может ответить на это, раздав plugin source сама: в одной измеренной session модель Pi запустила собственный локальный `git daemon` ровно для этого.

::: warning
Bypass permissions полностью пропускает permission prompts. Используйте его только когда доверяете каждому действию, которое агент может выполнить — например, в хорошо понятной automation, которую вы уже запускали.
:::

## Судья безопасности Guardian

Guardian — это опциональный LLM-судья безопасности, который проверяет
рискованные действия в автономных режимах в **Pi** sessions. Он является consulted input для
системы разрешений — может заблокировать или запросить подтверждение, но никогда
не разрешает то, что режим и так запретил бы.

- **В режиме Auto** Guardian проверяет пограничные действия до того, как Nessy
  спросит вас. `No objection` позволяет действию выполниться; `deny` блокирует
  его с короткой причиной; всё неопределённое, как обычно, запрашивается у вас.
  Это уменьшает число prompts для действий, в которых судья уверен.
- **В режиме Plan** Guardian проверяет shell commands вне read-only набора во
  время планирования (включено по умолчанию через настройку auto-during-plan).
  Одобренные команды выполняются, отклонённые блокируются; когда судья
  недоступен, такие команды запрашивают подтверждение у вас.
- **В режиме Bypass permissions** Guardian работает как сеть безопасности только
  на запрет для действий с высоким риском — утечка секретов, сбор учётных
  данных, деструктивные операции и git-действия в защищённых ветках. Он может
  заблокировать опасное действие или понизить его до запроса, но всё остальное
  выполняется как обычно, без дополнительной задержки. Правки файлов внутри
  папок session (рабочая папка, workspace, папки plans и data этой session и
  дополнительные каталоги) выполняются без него, как в Auto; правка вне их или
  в [защищённый путь](#защищенные-пути) по-прежнему проверяется. При включённом Guardian
  режим Bypass также спрашивает его перед действием приложения, например
  установкой plugin или управлением sources, как и перед другими MCP-действиями.
- **В режимах Don't ask, Manual и Accept edits** Guardian не работает.

**Sessions Claude Code и Codex не спрашивают Guardian о своих действиях.** То,
что он проверил бы в Auto или Plan, запрашивается у вас, а у Bypass на этих
runtimes нет сети безопасности только на запрет. У Codex есть собственный
проверяющий: при включённом [Codex auto-review](../reference/config/config-file)
Codex спрашивает его прежде, чем спросить вас, в Auto и Bypass permissions.

Судья никогда не отвечает на вопрос, зарезервированный за вами: запись в
[защищённый путь](#защищенные-пути), удаление, пойманное circuit breaker-ом, или
явное правило `ask` всегда доходят до человека, а не до модели.

Судья запускается как read-only помощник (может читать файлы и проверять
состояние git, но не может редактировать, выполнять команды или обращаться в
сеть) и имеет жёсткий лимит времени — 90 секунд на одну проверку. В его
пределах судья может сначала посмотреть, а потом ответить: до восьми обращений
к модели, так что он успевает прочитать цель действия и вынести вердикт. Если он
превысит время ожидания, выдаст ошибку или не сможет принять решение, Nessy
всегда возвращается к запросу у вас — и никогда к выполнению действия.

Судья решает по планируемому действию вместе с его входными данными — команде,
аргументам MCP-инструмента или инструмента сессии, пути и содержимому записи или
правки файла — и по вашим собственным словам. Ничто другое не считается вашими
словами: skill, который вы запускаете, доходит до него только по имени, и сам он
не загружает ни одного skill, а начинает без MCP-серверов сессии, так что ни
инструкции skill, ни описание сервера самим сервером не могут повлиять на
вердикт. Судья никогда не показывает вам собственную карточку: чтение вне
проекта, вызов, подпадающий под правило `ask`, или hook, которые подняли бы её,
пока он судит, вместо этого сразу отклоняются. Отклонённое чтение помечено как не давшее содержимого файла, и его
инструкции отправляют вам действие, риск которого зависит от содержимого, которое
он не смог прочитать.

Включить или выключить Guardian и выбрать модель, на которой он работает, можно
в **Settings → AI → Guardian**. По умолчанию он включён. Модель по умолчанию —
быстрая модель Nessy Gateway; рекомендуется дешёвая и быстрая модель.

Тот же переключатель управляет одной проверкой, которая работает на всех
runtimes и во всех режимах: сообщение, которое агент одной session отправляет в
другую session, перед доставкой проверяет судья вообще без tools. Сообщение,
которое он отклонил, не доставляется, а агент-отправитель узнаёт причину. Если
этот судья не может ответить, сообщение доставляется, потому что спросить
некого.

## Переключение режимов

Меню режимов в composer — как в Claude Desktop: **Авто** (с пометкой *Рекомендуется*), **Ручной**, **Принять правки**, **План** и **Обход разрешений**, в этом порядке и с номерами 1–5 — пока меню открыто, цифра выбирает режим. Галочка отмечает текущий режим, а пометка *По умолчанию* — режим, в котором начинается новая session в этом workspace (пометка переезжает сразу после сохранения нового умолчания в Workspace Settings).

**SHIFT+TAB** в chat input проходит тот же список по кругу:

```
Auto → Manual → Accept edits → Plan → Bypass permissions → Auto → …
```

**Не спрашивать** (Don't ask) — единственный режим, которого нет ни в меню, ни в ротации: он молча запрещает и никогда не спрашивает, поэтому выбирается только через конфигурацию, флаг CLI или automation. Из Don't ask, а также из режима, который workspace исключил из ротации, первое нажатие **SHIFT+TAB** ведёт в Manual. **Bypass permissions** предлагается по умолчанию — и в ротации, и в меню режимов. При первом входе в него на данной установке появляется диалог подтверждения ответственности; каждое следующее переключение происходит сразу. Чтобы убрать его для workspace, исключите его из настройки cyclable modes этого workspace.

Текущий режим всегда показан в interface, чтобы было видно, сколько свободы есть у агента. Cycle можно сузить в **Workspace Settings** до режимов, которыми вы пользуетесь (минимум два). Каждый режим также доступен как slash command в composer.

Для sub-agents и для подзадач, которые запускает задача, действует ещё одно правило: режим дочерней session ограничивается так, чтобы никогда не быть шире родительского — для подзадачи это session самой задачи, — дочерняя session может сузить свои permissions, но не расширить, и это ограничение применяется заново при каждой последующей смене режима. Для задачи понижение режима оркестратора во время прогона ограничивает следующую смену режима каждой идущей подзадачи и каждую подзадачу, которая стартует после этого, а прогон, возобновлённый после перезапуска, сохраняет режим, в котором он шёл, пока вы не измените режим оркестратора. Подзадача, которую вы сами добавили с плитки на доске, — ваша собственная session и не ограничивается.

**Сессии Nestor Cloud предлагают собственные режимы Nestor Cloud.** Когда такая session запускается, Nessy Desktop читает режимы, которые объявляет облачный агент, — сейчас это **Plan** и **Act**, — и меню режимов, slash menu и SHIFT+TAB предлагают только их, под собственными названиями и описаниями Nestor (без перевода). Каждый ход отправляет выбранный режим в Nestor Cloud по его собственному id, `plan` или `act`. Этот список приходит от Nestor Cloud, а не из таблицы выше, поэтому изменение собственных режимов Nessy Desktop его не меняет; если карточку агента прочитать не удалось, session предлагает ту же встроенную пару ([Nestor Cloud composer modes](/ru/reference/config/llm-connections#nestor-cloud-composer-modes)). Действия с файлами и shell, которые запрашивает облачный агент, по-прежнему выполняются на вашем компьютере под собственными проверками Nessy Desktop: в Plan — только чтение, в Act — проверки Manual, которые спрашивают перед рискованными действиями. Меню режимов приложения для iPhone в session Nestor Cloud предлагает те же два режима, а в любой другой session — Auto, Manual, Accept edits и Plan; Bypass permissions показан в списке неактивным, потому что server не принимает его с телефона.

## Защищённые пути

Небольшой набор путей никогда не авто-подтверждается для записи, что бы ни говорили allow rules — эта проверка выполняется до чтения allow rules, поэтому широкий allow pattern не может её открыть:

- Состояние репозитория и tooling: каталоги `.git`, `.husky`, `.vscode`, `.idea`, `.cargo`, `.devcontainer` и подобные
- Конфигурация агента: каталоги `.nessy-agent`, `.agents` и `.claude`, а также папка данных Nessy, где бы она ни находилась, — если `NESSY_CONFIG_DIR` указывает в другое место, эта папка защищена так же, как `~/.nessy-agent`
- Файлы запуска shell: `.zshrc`, `.bashrc`, `.profile` и остальное семейство rc
- Конфигурация package managers и сборки: `.npmrc`, `.yarnrc`, `bunfig.toml`, lockfile hooks, wrapper properties и тому подобное

В каждом режиме, который умеет спрашивать, запись в защищённый путь запрашивается лично у вас — она никогда не делегируется Guardian-у, — и у карточки нет Always Allow: сохранённый ответ эту проверку не пропускает, и следующая запись спросит снова. В Don't ask она запрещается. Bypass permissions — единственный режим, который её пропускает, за исключением собственных управляющих записей Nessy (см. ниже). Собственная папка этой session — исключение, где бы ни лежала папка данных: её папки plans, data, черновик `job/tmp` и downloads, а также файлы, которые создаёт там session без проекта. Исключение действует для file tools и для команды shell, все пути которой лежат там (`echo x > job/tmp/a`, `mkdir data/out`). Относительный путь отсчитывается от папки, в которой выполняются команды агента. В Claude Code session без проекта выполняет их в собственной папке session, поэтому примеры выше работают как написано, а слово, которое выходит из неё через `..`, оставляет карточку. В Pi такая session выполняет команды в папке workspace, поэтому там папку session называйте полным путём и в команде, которая только перенаправляет вывод в неё (`echo x > <полный путь>/job/tmp/a`): команда, которая сама меняет файлы, например `mkdir` или `cp`, оставляет карточку, потому что Nessy не может отличить её остальные слова от имён файлов в папке workspace. Её собственные записи остаются защищёнными (`session.jsonl`, `attachments`, `long_responses`, `.pi-carry`, `.pi-sessions`, `.pi-agent`, `.orchestrator`, `meta`, `hook-env`, `file_checkpoints`, `checkout-move.patch`, `tool-metadata.json` и `api-error.json`), как и папка другой session, команда shell, которая называет ещё и путь вне этих папок или путь, который Nessy не может разрешить (переменную, шаблон), и остальная папка данных, включая папку workspace.

Этот предохранитель касается записи file tools, а с 1.38.0 — и shell-пути: команда оболочки, пишущая в каталог конфигурации агента или в один из защищённых файлов (например `>> ~/.zshrc`), поднимает ту же карточку, что и файловый инструмент. `.git` намеренно не входит в shell-предохранитель, чтобы `git commit` работал без запроса; на рантайме Codex защищённые каталоги отказываются его собственной таблицей разрешений, а защищённые файлы туда не проецируются — переключение рантайма раскрывает оба различия. Независимо от него patterns `deniedPaths` (секреты вроде `.env`, `~/.ssh`, key files) блокируют и чтение, и запись в любом режиме — см. [configuration schema](#configuration-schema).

**Собственные управляющие записи Nessy отклоняются в любом режиме, включая Bypass permissions.** Они решают, что можно будущим sessions, поэтому session, способная их переписать, могла бы выдать себе больше прав. В папке данных это глобальный `hooks.json` (его command hooks выполняются без карточки), `mcp.json`, `config.json` и всё в `permissions/`. В папке workspace это `permissions.json`, `automations.json` и `automations-history.jsonl`, а для любого workspace, кроме собственного workspace этой session, ещё и его `hooks.json`. Запись в любой из них — file tool или командой shell — отклоняется с причиной и указанием, где вносить изменение: в Settings Nessy, в самом том workspace или через automation tools. Это касается и копирования или перемещения файла в их папку (`cp x/hooks.json ~/.nessy-agent/`, в том числе с другой машины через `scp`), создания в ней ссылки на файл, `dd of=`, распаковки архива туда (`tar -x -C`, `unzip -d`, `7z x`) и скачивания файла туда (`wget -P`, `curl -O`, `aria2c -d`); а если команда пишет в папку данных, её папку `workspaces` или папку другого workspace под именами, которых в ней не видно (папка, wildcard, переменная), отклоняется вся команда. Это касается и папки, скопированной в папку выше папки данных, если в её дереве есть путь самой папки данных (`cp -R x/me /Users/`, когда внутри `x/me` есть папка `.nessy-agent`); дерево без этого пути копируется. В папку собственного workspace этой session копия под именами, которых в команде не видно (содержимое папки, как в `cp -R x/ .`, или wildcard, как в `cp x/* .`), отклоняется, только если Nessy, просматривая источник при проверке команды, находит в нём `permissions.json`, `automations.json` или `automations-history.jsonl`; любая другая такая копия выполняется. Команда shell, которая называет такой файл, отклоняется, даже если только читает его; инструмент `Read` читает их по-прежнему. `hooks.json` собственного workspace этой session вместо этого сохраняет карточку защищённого пути, так что агента по-прежнему можно попросить добавить hook в workspace, в котором вы работаете. На Codex Nessy тоже в любом режиме отклоняет изменение файла, write grant или команду оболочки, на которую Codex запрашивает разрешение, если они нацелены на эти записи, на домашние папки Codex или на `credentials.enc` (команда, которая только читает такую запись, тоже отклоняется, когда Codex о ней спрашивает; обычное чтение вроде `cat` обычно выполняется без вопроса), и никогда не отдаёт Codex папку внутри папки данных как дополнительный каталог. Skills в папке данных — не управляющие записи, и это правило их не отклоняет. На Codex, если папка данных лежит внутри папки, в которую Codex может писать, кроме рабочей папки session (ваша домашняя папка, добавленная как каталог, или папка данных в `/tmp`), sandbox Codex закрывает для команд агента всю папку данных, вместе со skills и plugins: в такой раскладке команда не может прочитать или запустить собственные файлы skill. Инструкции skill при этом всё равно доходят до агента, потому что читаются вне sandbox: Nessy читает их сам, когда агент вызывает skill как `[skill:name]`, а Codex делает то же для упоминания `$name` skill из своего собственного списка. Не работает любой шаг, который открывает файл в папке skill командой: скрипт, который skill просит агента запустить, справочный файл, который он просит прочитать, или skill, который агент сам выбрал из списка Codex без упоминания по имени, — его Codex открывает командой.

## Основная подключённая папка

На странице Permissions есть один контрол, который не меняет никаких
разрешений, — и он описан здесь, чтобы это различие было видно. **Primary
folder** выбирает, какая из уже подключённых к session папок показывается и
сортируется первой; значение хранится как `primaryDirectory` в `config.json`, а
select не предлагает ничего, что не подключено. Discovery по-прежнему идёт от
project root, и resolver может ответить лишь папкой из подключённого набора —
поэтому никакое его значение не расширяет то, что агент может читать и писать.
Контрол скрыт, когда выбирать не из чего.

Добавление root остаётся permission decision и делается двумя документированными
способами: `additionalDirectories` или approval на выход за root, чей ответ
*Allow for this session* добавляет отзываемый session root.

## Dangerous Commands

Внутри non-safe категории есть меньшая группа, требующая дополнительной осторожности. Отличия от regular commands:

- **Regular commands** можно запомнить через "always allow" — см. [Что запоминает Always Allow](#что-запоминает-always-allow).
- **Dangerous commands** требуют подтверждения при каждом invocation: на их карточке нет "always allow", а строка под кнопками говорит, что ничего не запоминается.
- **`curl` / `wget`** — особый случай в Claude Code: "always allow" разрешает целевые **хосты** до конца сессии, а не саму команду. Разрешение покрывает следующий вызов, только если это одна простая команда и каждый хост, к которому она обращается, разрешён: передача скачанного в shell, второй хост, чтение параметров из файла конфигурации (`-K`), перенаправление вывода в файл или ещё одна команда в цепочке снова вызывают запрос. Строка `curl`, за которую приложение так поручиться не может, вообще не получает "always allow". В Pi у такой карточки его тоже нет; в Codex доступ к сети решает собственная песочница Codex.

В Bypass permissions mode каждая command выполняется автоматически, включая dangerous — кроме удалений, нацеленных на корень файловой системы или домашний каталог: они запрашиваются в любом режиме как circuit breaker. Команда, затрагивающая собственные управляющие записи Nessy, отклоняется (см. [Защищённые пути](#защищенные-пути)).

В Pi и Claude Code у карточки circuit breaker нет Always Allow, как и у карточки команды, которая выполняет `eval`, и инструмента, который его MCP-сервер помечает как требующий вашего участия: сохранённый ответ эти проверки не пропускает, и следующий вызов спросит снова.

```
rm, rmdir                          # Delete files and directories
mv, cp                             # Move/copy (can overwrite)
sudo, su                           # Privilege escalation
chmod, chown, chgrp                # Permission changes
dd, mkfs, fdisk, parted            # Disk operations
kill, killall, pkill               # Process termination
reboot, shutdown, halt, poweroff   # System control
curl, wget                         # Network downloads
ssh, scp, rsync                    # Remote access and transfer
git push                           # Push to a remote
git reset                          # Reset git state
git rebase                         # Rewrite history
git checkout                       # Can discard changes
```

## Что запоминает Always Allow

**Always Allow** на карточке shell-команды запоминает ровно то, что вы одобрили, и никогда не более широкую команду. Строка под кнопками карточки говорит, что сохранит нажатие, и происходит именно это:

- Утилита командной строки с подкомандами (`git`, `npm`, `docker`, `kubectl` и подобные) запоминается по первым словам — не больше трёх и до первого флага: одобрение `git status` покрывает `git status -s` позже в этой сессии, но не `git push`.
- Несколько однозначных команд (`mkdir`, `touch`, `sleep` и подобные) запоминаются по имени.
- Всё остальное — включая интерпретаторы и запускалки вроде `node`, `python3`, `npx` или `npm run` — запоминается как **точная** команда, которую вы видели. Одобрение `node -e "console.log(1)"` не покрывает `node evil.js`, а одобрение `npx prettier --check .` не покрывает `npx prettier --write .`.
- Ничего не запоминается и кнопка не предлагается для цепочки команд, передачи вывода в другую программу, перенаправления в файл, присваивания или подстановки переменной, dangerous command, `gh api`, флага перед подкомандой, разрушительного слова среди первых слов (`aws s3 rm`, `docker system prune`, `npm uninstall`) и команды, которая выполняет собственный аргумент (`bash -c …`). Допустимы два безобидных окончания: `2>&1` в конце и последний `| tail`, `| head`, `| wc` или `| grep`, который только фильтрует вывод.

Сколько это действует, зависит от рантайма, и карточка говорит, как именно:

| Рантайм | Что сохраняет одно Always Allow |
| --- | --- |
| Pi | Сессия запоминает одобрение, а правило сохраняется в `.claude/settings.local.json` в корне репозитория, так что последующие сессии Pi в этом репозитории выполняют команду без запроса. Сохранённое правило — точная одобренная строка (для однозначной команды — её имя с любыми аргументами), поэтому следующая сессия снова спросит про другое написание флагов, которое разрешение этой сессии покрывает. Строка, в которой есть `*`, и сессия без папки сохраняют разрешение только на сессию: сохранённое правило прочитало бы `*` как шаблон, а у сессии без папки нет репозитория, куда сохранять. |
| Claude Code | Только сессия. Ничего не сохраняется: сохранённое правило не избавило бы следующую сессию Claude Code от карточки, а то, что разрешено сессиям Pi и Codex в репозитории, расширило бы. |
| Codex | Правило для этой команды в разрешениях рабочего пространства, как описано в разделе [Permission Modes](#permission-modes). |

Одобрения другого рода — MCP-инструмента, инструмента сессии — действуют до конца сессии. Карточка действия, которое запомнить нельзя никогда (защищённый путь, circuit breaker, команда с `eval`, правило ask), так и говорит, и Always Allow на ней нет.

## Метки риска

Когда в [модели решений](./decision-model) включены **Метки риска**, карточка разрешения может нести небольшие метки о том, что делает действие: удаляет данные, отправляет данные наружу, публикует, затрагивает секреты, меняет систему или тратит деньги. Карточка с известным риском рисуется в тоне опасности. Метки только информируют: кнопки, фокус по умолчанию и то, что делает ваш ответ, не меняются. Карточка недолго ждёт свои метки; если модель решений не ответила вовремя, карточка появляется без них.

В Codex, когда действие оценивал собственный auto-review Codex, сообщённый им уровень риска показывается в строке проверки с пометкой, что это оценка Codex.

## Настройка read-only набора

::: info
**Попросите агента.** Самый простой способ расширить то, что Plan mode выполняет без вопроса, — сказать агенту, что нужно:

- "Allow `npm run build` in Plan mode"
- "Let Linear comments work in Plan mode"
- "Add `bun run test` to the allowed commands"

Агент обновит configuration files за вас.
:::

Если хотите править вручную, read-only набор гибко настраивается: можно добавить bash commands, MCP tool patterns и API endpoints. File write paths из `allowedWritePaths` ушли вместе с Explore mode: ни один режим их не читает.

### Configuration Files

Permissions читаются из `permissions.json` files на нескольких уровнях:

```
~/.nessy-agent/permissions/default.json                             # App-wide defaults
~/.nessy-agent/workspaces/{id}/permissions.json                     # Per workspace
~/.nessy-agent/workspaces/{id}/sources/{slug}/permissions.json      # Per source
```

Более специфичные files **extend** более широкие, а не заменяют их. Patterns в source file автоматически scoped к tools этого source. File источника может разрешать только собственные tools этого источника: его `allowedBashPatterns`, `allowedWritePaths` и allow rule для любого другого tool игнорируются, потому что агент может править этот file, когда настраивает источник. Разрешение на всю session задавайте в file workspace (**Settings → Permissions**). Запреты из file источника по-прежнему действуют.

**Когда правка вступает в силу.** Правило deny или ask, которое вы добавили в `permissions.json` workspace или источника, пока работает session Claude Code или Pi, действует со следующего вызова инструмента этой session, в том же ходе, как в Claude Code. В `toolRules`, который читается по первому совпадению, это верно для нового правила deny или ask, стоящего выше всех правил allow в файле; если ход начался с правилом deny в `toolRules` любого файла разрешений этой session (`default.json`, файла workspace, файла источника или `.nessy-agent/permissions.json` проекта), даже для других инструментов, новое правило ask, как и любое правило ниже правила ask, тоже ждёт. Правило, которое ждёт, в том же ходе действует только для инструментов, которым не соответствует ни одно прежнее правило, а полностью — со следующего хода. Удаление правила или новое allow rule ждёт следующего хода session, как и правка `default.json`. На Codex новое правило deny или ask действует со следующего хода session.

### Configuration Schema

```json
{
  "allowedBashPatterns": [
    { "pattern": "^npm run build\\b", "comment": "Allow npm build" },
    { "pattern": "^make\\s+test\\b", "comment": "Allow make test" }
  ],
  "allowedMcpPatterns": [
    { "pattern": "create_draft", "comment": "Allow creating drafts" }
  ],
  "allowedApiEndpoints": [
    { "method": "POST", "path": "/api/drafts", "comment": "Create drafts" }
  ],
  "deniedPaths": [
    "~/.ssh/**",
    "**/.env"
  ],
  "deniedToolPatterns": [
    "Web*",
    "mcp__linear__*"
  ],
  "disallowedTools": [
    { "pattern": "mcp__jira__*", "comment": "No Jira writes from this workspace" }
  ],
  "allowedTools": [
    "Read",
    "Glob",
    { "pattern": "mcp__linear__*", "comment": "Linear only, nothing else" }
  ],
  "toolRules": [
    { "pattern": "mcp__jira__create*", "action": "ask", "comment": "Confirm each Jira write" },
    { "pattern": "mcp__jira__*", "action": "deny" }
  ]
}
```

### Pattern Types

**`allowedBashPatterns`** — regex patterns, matched against bash commands:

```json
{ "pattern": "^npm run (build|test|lint)\\b", "comment": "npm scripts" }
```

**`allowedMcpPatterns`** — patterns, matched against MCP tool names:

```json
{ "pattern": "^mcp__linear__create_comment$", "comment": "Allow Linear comments" }
```

На уровне workspace pattern сравнивается с полным именем tool, `mcp__<source>__<tool>`, поэтому двойные подчёркивания пишите явно, как выше.

В `permissions.json` конкретного source они auto-scoped и привязаны к началу имени: запись `list` становится внутренним match для tools этого source, чьё имя **начинается** с неё как с целого слова (`mcp__linear__list`, `mcp__linear__list_issues`), — но никогда для tool, который её просто содержит (`mcp__linear__delete_playlist`), и никогда для tools другого source.

Ещё одно правило действует для любого read-only MCP-паттерна — встроенного, source-level или вашего: tool, в имени которого после первого слова стоит слово записи (`get_or_create_user`, `find_and_replace`, `status_update`), никогда не считается read-only, какой бы паттерн ему ни соответствовал. Встроенный read-only список следует тому же правилу ведущего глагола и называет read-инструменты встроенных dp-серверов точно по имени (например, `dp_jira_jql_search`), потому что глагол у них стоит не первым словом. Существующие установки обновлены автоматически: старые встроенные записи заменены, ваши записи сохранены — кроме записи, написанной в точности как одна из старых встроенных: она уходит вместе с ней.

**`allowedApiEndpoints`** — HTTP method плюс path pattern:

```json
{ "method": "POST", "path": "/api/comments", "comment": "Create comments" }
```

`method` должен быть одним из `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD` или `OPTIONS`. `path` — regex.

**`allowedWritePaths`** — упразднён вместе с Explore mode в 1.41.0. В нём были glob patterns для paths, куда агент мог писать в Explore; теперь его не читает ни один режим, и Settings → Permissions его больше не предлагает. Файл, где он ещё указан, загружается как прежде, а записи просто не используются.

**`deniedPaths`** — glob patterns для файлов, которые агент **никогда не может ни
прочитать, ни записать**, ни в одном режиме:

```json
["~/.ssh/**", "**/.env", "**/*.pem", "/srv/deploy/secrets/**"]
```

Это ответ на вопрос «как запретить агенту читать мои credentials?». Совпадение
блокирует `Read`, `Write`, `Edit`, `MultiEdit`, `NotebookEdit`, `Glob`, `Grep`,
`Find`, `Ls` и любой путь, названный внутри команды `Bash` — `Glob`/`Grep` — это
имена file discovery и search в Claude runtime, `Find`/`Ls` — в Pi, и один deny
покрывает оба словаря. Проверка выполняется **до** любого
решения режима, поэтому Bypass permissions её не открывает, а отказ называет
запись, которая его вызвала.

Задать список можно в любом из файлов выше, а администратор может доставить его в
managed policy. Список additive только в одну сторону: слой может добавить
записи и не может убрать запись, добавленную другим слоем, — поэтому managed
запись перекрывает всё. Когда администратор включает managed-only lock, этот lock
отбрасывает вклад в сторону *allow* от остальных слоёв, а `deniedPaths` каждого
слоя продолжает мержиться.

Patterns сравниваются с **абсолютными** путями, поэтому запись должна быть
заякорена: начинайте её с `/`, `~/` или `**/`. Голое `secrets/**` или `.env` не
совпадёт ни с чем. `**` матчит любую глубину, `*` — один сегмент пути, `?` — один
символ.

Запись вида `<dir>/**` **покрывает и сам каталог**: `~/.ssh/**` запрещает файлы
внутри `~/.ssh` *и* сам путь `~/.ssh`, поэтому `Grep` и `Glob` тоже нельзя
запустить с корнем там.

Некорректная запись **отбрасывается с предупреждением, которое её называет**, а
остальной файл продолжает действовать. Три формы не могут совпасть ни с чем и
сообщаются: пустая запись, путь в Windows-стиле вроде `C:\secrets\**` (пишите
разделители как `/`) и незаякоренная вроде `secrets/**`.

Одно ограничение, о котором стоит знать: проверка применяется к *запросу*
инструмента, а не к его *результатам*. Поиск с корнем **выше** запрещённого
каталога всё ещё может вернуть совпадения изнутри него — запрет `~/.ssh/**`
останавливает `Grep` по `~/.ssh`, но пока не фильтрует `Grep` по `~`.

Nessy поставляет credential floor в `default.json` — файлы `.env`, `~/.ssh`,
`~/.gnupg`, `~/.aws`, `~/.config/gcloud`, `~/.azure`, `~/.kube`,
`~/.docker/config.json`, git credential stores, `.npmrc`, `.pypirc`, `~/.netrc`,
`*-service-account.json`, `*.pem`, `*.key`, `id_rsa`, `id_ed25519` — и ваши
записи добавляются к нему.

**В Codex поставляемый floor не доходит до sandbox Codex (с версии 1.41.0).**
Codex работает со своими собственными настройками sandbox по умолчанию, поэтому
команда, которую выполняет Codex, может прочитать собственные файлы учётных
данных Nessy (`credentials.enc` в папке данных, `~/.nessy`), `~/.ssh`, `~/.aws`
и остальной список выше, как любой другой файл, который разрешает sandbox
Codex. Записи, которые вы или администратор добавляете в `deniedPaths`,
по-прежнему доходят до sandbox Codex, и он отклоняет чтение — в том числе
запись, написанная в файле рабочего пространства или источника точно так же,
как поставляемая. Каждая такая запись замедляет открытие треда Codex, потому
что Codex тогда проверяет свои файлы инструкций через sandbox; строка
`codex-deny-read-slows-thread-open` в журнале сессии называет их число. В Pi и
Claude Code ничего не изменилось: там действует весь floor.

**`blockedTools`** — дополнительные имена инструментов, заблокированных в
read-only режимах (Plan и Don't ask):

```json
["BashOutput", "mcp__linear__create_issue"]
```

Точные имена инструментов, не glob-шаблоны. Четыре инструмента, которые runtime
блокирует сам (`Write`, `Edit`, `MultiEdit`, `NotebookEdit`), — это нижняя
граница: список здесь добавляется к ним и не может убрать ни один. Для
glob-совпадений или для блокировки, действующей и в режимах записи, используйте
`deniedToolPatterns` или `disallowedTools`. Некоторые имена он заблокировать не
может, и **начиная с 1.34.0 страница «Разрешения» об этом сообщает**: запись,
которую рантайм не читает, остаётся там, где вы её написали, сохраняет свой
бейдж и получает строку с ветвью, которая решает вместо неё (*«blockedTools
"Bash" НЕ применяется: вызовы shell решает классификатор read-only команд,
который отрабатывает раньше этого списка»*). Заблокировать нельзя всегда
разрешённые read-only инструменты
(`Read`, `Glob`, `Grep`, `Task`, `TaskOutput`, `WebFetch`, `WebSearch`,
`TodoWrite`, `SubmitPlan`, `LSP`, `read_mcp_resource`, `list_mcp_resources`,
`read_skill_resource` и их написания вида `mcp__…__<имя>`), `Bash` и
`browser_tool` решаются до того, как этот список вообще читается, поэтому имя
такого инструмента здесь ничего не даёт — берите вместо этого
`deniedToolPatterns`, где `["Web*"]` действительно блокирует `WebFetch` и в
Plan, и в Manual. Для явных решений `allow`, `ask` и
`deny` используйте `permissionDsl`. `blockedCommandHints` меняет только подсказку
для отклонённой команды.

**`deniedToolPatterns`** и **`disallowedTools`** — glob-шаблоны, сопоставляемые с
**именем инструмента** и блокирующие его во **всех** режимах доступа:

```json
{
  "deniedToolPatterns": ["Web*", "mcp__linear__*"],
  "disallowedTools": [
    { "pattern": "mcp__jira__*", "comment": "No Jira writes from this workspace" }
  ]
}
```

Это те самые два glob-рычага, к которым отсылает `blockedTools`, и единственные
средства по имени инструмента, действующие в режимах записи. Элемент списка —
строка либо объект с полем `pattern` и необязательным `comment`. `**` совпадает с
любой глубиной, `*` — с одним сегментом пути, `?` — с одним символом; в имени
инструмента нет `/`, поэтому `Web*` покрывает `WebFetch`, а `mcp__linear__*` —
все инструменты этого сервера.

Оба списка проверяются **до** решения о режиме — сначала `deniedToolPatterns`,
затем `disallowedTools`, — поэтому Bypass permissions их не открывает, и на них
не действует список всегда разрешённых read-only инструментов, из-за которого
запись в `blockedTools` может оказаться молча бесполезной. В отказе называется
сработавший шаблон (`Tool blocked: WebFetch matched deniedToolPatterns pattern
Web*`).

Их можно задать в любом из перечисленных выше файлов, а администратор — доставить
в managed policy. Как и `deniedPaths`, списки складываются только в одну сторону:
слой может добавить записи и не может убрать чужие, поэтому managed-запись
перекрывает всё и переживает managed-only lock.

Здесь оба ключа делают одно и то же, так что берите любой: `disallowedTools` —
это ещё и имя, которым denylist инструментов называется в Claude Agent SDK и во
frontmatter скиллов, поэтому принимаются оба написания.

**`allowedTools`** — парный **allowlist**, и единственный ключ здесь, чьё имя
означает противоположное тому, чего ждёт пользователь Claude. `--allowedTools` в
Claude *добавляет* разрешающие правила на одну сессию; этот ключ *сужает*. Он
ничего не разрешает — он запрещает всё, что не перечислено:

```json
{
  "allowedTools": [
    "Read",
    "Glob",
    { "pattern": "mcp__linear__*", "comment": "Linear only, nothing else" }
  ]
}
```

Записи имеют те же две формы, что и denylist выше — строка либо объект с
`pattern` и необязательным `comment`, — и сопоставляются с именем инструмента как
glob.

**Пустой список означает «нет ограничения», а не «запретить всё».** Проверка
выполняется, только пока объединённый список непуст, поэтому отсутствующий ключ и
`[]` ведут себя одинаково. Это главное, что нужно понять до развёртывания:
`"allowedTools": []` ничего не закрывает, и политика, написанная в расчёте на
обратное, остаётся молча открытой.

Как только список непуст, инструмент, не совпавший ни с одним шаблоном,
отклоняется: `Tool blocked: <name> is not included in allowedTools`. Как и оба
denylist, он проверяется **до** решения режима, поэтому Bypass permissions его не
открывает. И он **проигрывает любому запрету**: `deniedPaths`,
`deniedToolPatterns` и `disallowedTools` вычисляются раньше, так что упоминание
инструмента здесь не вернёт тот, который уже заблокирован запретом.

Между слоями списки объединяются, поэтому записи следующего слоя только
расширяют допустимое. Под managed-only lock `allowedTools` каждого
не-managed-слоя отбрасывается, и решает только managed.

**`toolRules`** — решения `allow` / `deny` / `ask` для отдельных инструментов, на
случай когда простого allowlist или denylist недостаточно:

```json
{
  "toolRules": [
    { "pattern": "mcp__jira__create*", "action": "ask", "comment": "Confirm each Jira write" },
    { "pattern": "mcp__jira__*", "action": "deny" }
  ]
}
```

Каждой записи нужны `pattern` и `action`; `comment` необязателен. Шаблон — glob
по имени инструмента, как и везде на этой странице.

**Порядок важен здесь и только здесь.** `toolRules` читается по первому
совпадению, поэтому пример выше спрашивает про вызовы `create` и запрещает
остальные; если поменять записи местами, запрещено будет всё, а до правила `ask`
дело не дойдёт. Остальные списки инструментов — проверки на вхождение, где
порядок влияет только на то, какой шаблон будет назван в отказе.

`deny` отклоняет. `allow` разрешает инструмент и полностью пропускает решение
режима. `ask` спрашивает — кроме режима Don't ask, который не спрашивает
никогда: там правило `ask` вместо этого запрещает, и такой отказ не подлежит
обсуждению, поэтому хук не может его одобрить. Как и списки выше, `toolRules`
вычисляется до решения режима и действует во всех режимах. В Pi и Claude Code у
карточки правила `ask` нет Always Allow: одобрение разрешает только этот вызов, и
правило спросит снова в следующий раз.

Под managed-only lock записи `allow` из не-managed-слоёв отбрасываются поштучно,
а их записи `deny` и `ask` сохраняются: lock убирает разрешения, но никогда —
защиты.

### Permission DSL v1

`permissionDsl` — читаемый версионированный формат policy для Pi runtime. Его
правила `deny` действуют и в sessions Claude Code: до запуска tool Nessy
отклоняет то, что запрещает объединённая policy, в любом режиме, включая Bypass
permissions, и называет правило. Правила `ask` там тоже действуют: вызов ждёт
одобрения на карточке, которая называет правило, в любом режиме, включая Bypass
permissions, а Don't ask вместо этого его отклоняет, потому что никогда не
спрашивает. У такой карточки нет Always Allow (в Claude Code — нет «Allow for this
session»): одобрение разрешает только этот вызов, и правило спросит снова в
следующий раз. То же действует на Pi — в Manual, как и в любом другом режиме, — и
на Codex, как описано выше. На Pi карточка показывает рядом с правилом команду
или путь, о которых спрашивает, а на Claude Code — команду, файл, URL или
аргументы вызова. В Claude Code не учитывается только правило `allow` — решает
режим.
Он размещается внутри любого поддерживаемого `permissions.json`:

```json
{
  "permissionDsl": {
    "version": 1,
    "rules": [
      {
        "id": "ask-git-push-origin",
        "action": "ask",
        "match": { "kind": "bash", "executable": "git", "args": ["push", "origin"] }
      },
      {
        "id": "deny-production-host",
        "action": "deny",
        "match": { "kind": "host", "host": "production.example.com" }
      }
    ]
  }
}
```

У каждого правила есть стабильный `id`, действие (`allow`, `ask` или `deny`) и
один matcher:

| Matcher | Поля | Что сопоставляется |
| --- | --- | --- |
| `tool` | `semanticId` | Семантический ID или имя tool |
| `bash` | `executable`, опциональные `args`, `cwdRoot` | Разобранная shell command; `cwdRoot` должен быть абсолютным и канонизируется приложением |
| `path` | `root`, опциональный `parameter` | Канонизированные приложением paths внутри абсолютного root |
| `host` | `host` | Hostname назначения |
| `mcp` | `server`, опциональный `tool` | MCP server и tool |
| `agent` | `agent` | Допуск именованного custom agent |
| `parameter` | `name` и `equals` или `oneOf` | Ограниченное безопасное input field |

Для `path.parameter` допустимы `file_path`, `notebook_path`, `path`, `cwd` и
`workingDirectory`. Для `parameter.name` допустимы `method`, `mode`, `action`,
`access`, `operation` и `transport`.

Правило `bash` сопоставляется с одной разобранной командой. Команду, которую
parser не может разложить на одну, — цепочку с `;` или `&&`, redirect вроде
`>>`, подстановку `$(…)`, glob — правило `allow` для bash никогда не одобряет:
проверка переходит к следующему правилу, а затем к режиму, ровно как если бы
этого правила не было. Правило `ask` или `deny` для bash читает такую команду
по частям, как собственные правила Claude Code: оно срабатывает, когда любая
часть — в том числе внутри подстановки `$(…)`, subshell или тела `if` — запускает
программу правила (с аргументами правила, если они указаны), а команда, ни одна
часть которой этого не делает, решается так, будто правила нет. Поэтому правило
`ask` для `touch notes.txt` спрашивает о `cd docs && touch notes.txt`, но не о
`echo 1 >> log && wc -l log`. О команде, слишком сложной для разбора по частям,
правило спрашивает, называя себя, а правило `deny` для любой программы
(`"executable": "*"`) по-прежнему отклоняет каждую такую команду. Правила, которые **Always allow** в Codex
сохранял в прежних версиях, имеют именно такую форму, поэтому одно такое разрешение для `git`
не превращает посторонние составные команды в отказы.

Если совпало несколько правил, побеждает более безопасное действие:
`deny` → `ask` → `allow`. При одинаковом действии приоритет scopes:
`managed` → `global` → `workspace` → `project` → `plugin`.

Для каждого совпавшего решения сохраняются `id` правила, scope policy и digest
источника, поэтому app может объяснить, какое правило сработало. Правило, чей
matcher не компилируется, пропускается с предупреждением, которое его называет,
а остальной документ продолжает действовать. Документ, который не удаётся
прочитать, — невалидный JSONC, неверная форма, неизвестный вид matcher или
поле, несовпадающий опциональный `generation` — игнорируется целиком:
предупреждение сессии называет его уровень настроек, его собственные правила,
включая `deny`, перестают действовать, пока файл не исправлен, а все остальные
документы продолжают действовать (нечитаемый документ недоверенного проекта
пропускается так же, но без предупреждения). Безопасно закрываются, отказывая в каждом
вызове с указанием причины, только два случая: нечитаемый managed-документ и
один источник настроек, в котором правил `deny` и `ask` больше лимита
компиляции в 512 правил, потому что отбросить любое из них значило бы
расширить policy. Request из другой generation тоже получает `deny`; policy
никогда не используется молча.

### Managed Pi policy

Администратор может установить одну host-owned, non-overridable Pi policy:

| Платформа | Path |
| --- | --- |
| macOS | `/Library/Application Support/Nessy/managed-policy.json` |
| Linux | `/etc/nessy/managed-policy.json` |
| Windows | `%ProgramFiles%\Nessy\managed-policy.json` |

На Windows прежнее место, `%ProgramData%\Nessy\managed-policy.json`, не
читается: в этот каталог могут писать обычные учётные записи. Policy, оставленная
там, игнорируется, и diagnostic называет путь, куда её перенести. Если
`%ProgramFiles%` не задана или не является абсолютным путём, либо путь policy
разрешается за пределы `%ProgramFiles%\Nessy` (например, через directory
junction), file policy не применяется, и причина попадает в diagnostic. Проверки
владельца на Windows нет: защита в том, что по умолчанию писать в
`%ProgramFiles%` могут только администраторы.

Server читает file при startup вместе со всеми `*.json` в каталоге
`managed-policy.d/` рядом с ним; они сливаются после file в порядке имён
(скрытые files пропускаются), так что несколько команд могут поставлять каждая
свою часть. Project, workspace, user, plugin и repository config не могут
выбрать другой path или расширить загруженную policy. Отсутствующий file
оставляет built-in managed layer.

Когда Nessy Gateway доставляет managed policy, в которой есть хоть одна
настройка, применяется доставленная policy вместо file и его частей из
`managed-policy.d/`: они не сливаются. Переменная за переменной объединяется
только `env`, и несколько lock-ключей действуют, из какого бы источника они ни
пришли (`forceRemoteSettingsRefresh` и network- и filesystem-locks в `sandbox`).

**Когда начинает действовать изменённая policy.** Работающее приложение
перечитывает policy (file, его части из `managed-policy.d/` и доставленную
policy) в начале каждого хода, а доставленную policy, которая только ужесточает,
принимает сразу. Уже одобренный вызов инструмента не перерешается. Со следующего
решения новая policy действует для permission modes (`disabledPermissionModes`,
`defaultMode` для новых sessions), `permissionDsl`,
`allowManagedPermissionRulesOnly`, `autoMode`, allowlists HTTP hooks
(`allowedHttpHookUrls`, `httpHookAllowedEnvVars`), channel pushes
(`channelsEnabled`, `allowedChannelServers`, `deniedMcpServers`),
`connectSourcesOnStartup` и `companyAnnouncements`. Hook-locks
(`allowPluginHooks`, `allowManagedHooksOnly`, `disableAllHooks`) действуют сразу
только в одну сторону: ужесточение применяется со следующего решения, а
ослабление возвращает hooks пользователя и проекта на следующем ходе, но hooks
из plugins только после перезапуска, потому что набор plugins, который
предлагается session, строится из policy, с которой приложение стартовало.
Одно ужесточение тоже ждёт перезапуска: `allowManagedHooksOnly`, включённый,
пока managed `enabledPlugins` принудительно включает plugins, останавливает
hooks пользователя и проекта на следующем ходе, но hooks всех plugins, с
которыми приложение стартовало, продолжают работать, а не только hooks
принудительно включённых, потому что то, чьи hooks сохраняет этот lock,
решается при startup. По той же причине изменение того, какие plugins
принудительно включает `enabledPlugins`, доходит до их hooks только после
перезапуска. Опустевший набор — единственное изменение, которое не ждёт: пока ни
один plugin не принудительно включён, hooks из plugins останавливаются на
следующем ходе. Allow- и deny-списки MCP servers (`allowedMcpServers`, `deniedMcpServers`)
проверяются заново при каждом запуске встроенного dp server или локального
(stdio) server из plugin, так что ужесточение доходит до этих servers при их
следующем запуске, а собственные servers организации (`managedMcpServers`)
следуют текущей policy при каждом запуске. Всё остальное решается по policy, с
которой приложение стартовало: server из plugin, запрещённый при startup,
вернётся только после перезапуска, а вне session Claude Code изменение списков,
которое касается любого другого MCP server, например из file `.mcp.json`, из
source workspace или удалённого server из plugin, действует в обе стороны
только после перезапуска. Session Claude Code получает текущую policy как свои
managed settings на следующем ходе. То, что приложение строит один раз при
startup, держит policy, с которой оно стартовало, до перезапуска Nessy Desktop:
какие plugins предлагаются session (`allowedPluginKeys`, `deniedPluginKeys`,
`strictPluginOnlyCustomization`), ключи marketplaces, список и цены models,
network-правила sandbox, `env`, `claudeMdExcludes` на Pi и Codex и границы
версий. После изменения ключа, не названного в этом абзаце, перезапустите
приложение.

File policy, которому нельзя доверять или который нельзя прочитать, закрывается
безопасно: если file или его каталог — symlink, не принадлежит root или доступен
на запись group или others (macOS и Linux), либо file больше 256 KiB, не
является валидным JSON или не является JSON-объектом, server не стартует, а
Nessy Desktop показывает ошибку с именем file. File в `managed-policy.d/`,
который не проходит те же проверки, вместо этого пропускается с diagnostic, а
остальная policy продолжает действовать.

Внутри читаемой policy entry, которую schema не принимает, — неизвестное или
опечатанное поле, неверное значение, невалидное правило — отбрасывается
отдельно и попадает в diagnostic, а все остальные entries по-прежнему
применяются. Плохой элемент списка отбрасывает только этот элемент; allowlist,
значение которого не список, применяется как пустой и ничего не допускает, пока
его не исправят; on/off-lock со значением не `true` и не `false` читается в
запирающем положении. Поэтому ключ с опечаткой не применяет ничего. Отброшенные
entries пишутся в log при startup под `[managed-settings]`, а
[`doctor`](/ru/reference/cli#doctor-проверка-конфигурации) перечисляет каждую с
file и полем и завершается с кодом 1 — запускайте его перед раскаткой на парк.

Schema version 1 принимает, кроме `schemaVersion`, такие ключи:

- **Разрешения:** `disabledPermissionModes`, `defaultMode`, `permissionDsl`,
  `allowManagedPermissionRulesOnly`, `claudeRules`, `autoMode`,
  `unattendedApprovalFallback`.
- **Plugins и marketplaces:** `allowedPluginKeys`, `deniedPluginKeys`,
  `enabledPlugins`, `strictPluginOnlyCustomization`,
  `disableCommandPluginSources`, `disableSideloadFlags`, `pluginTrustMessage`,
  `strictKnownMarketplaces`, `blockedMarketplaces`, `extraKnownMarketplaces`,
  `pluginSuggestionMarketplaces`.
- **MCP servers и channels:** `allowedMcpServers`, `deniedMcpServers`,
  `allowManagedMcpServersOnly`, `managedMcpServers`, `channelsEnabled`,
  `allowedChannelServers`, `connectSourcesOnStartup`.
- **Hooks:** `allowPluginHooks`, `allowManagedHooksOnly`, `disableAllHooks`,
  `allowedHttpHookUrls`, `httpHookAllowedEnvVars`.
- **Models:** `model`, `availableModels`, `enforceAvailableModels`,
  `modelPricing`, `disableNonGatewayConnections`.
- **Sandbox и окружение:** `sandbox`, `env`.
- **Workflows, agents и память:** `workflow`, `disableAgentView`,
  `claudeMdExcludes`, `autoCompactEnabled`, `cleanupPeriodDays`.
- **Приложение и его browser:** `companyAnnouncements`, `disableInAppUpdates`,
  `requiredMinimumVersion`, `requiredMaximumVersion`,
  `forceRemoteSettingsRefresh`, `disableInAppBrowser`,
  `disableBrowserExternalNavigation`, `disableBrowserCdp`,
  `browserHostAllowlist`, `browserExternalPageTools`.

Deny имеет приоритет над allowlist. Policy
применяется до mode clamping, capability resolution и process creation, поэтому
managed denial не зависит от cleanup после side effect.

### Example: allow npm scripts in Plan mode

Create `~/.nessy-agent/permissions/default.json`:

```json
{
  "allowedBashPatterns": [
    { "pattern": "^npm run\\b", "comment": "All npm scripts" },
    { "pattern": "^yarn\\b", "comment": "All yarn commands" },
    { "pattern": "^bun run\\b", "comment": "All bun scripts" }
  ]
}
```

### Example: allow Linear comments in Plan mode

Create `~/.nessy-agent/workspaces/{id}/sources/linear/permissions.json`:

```json
{
  "allowedMcpPatterns": [
    { "pattern": "create_comment", "comment": "Allow posting comments" }
  ]
}
```

## Заблокированные shell constructs

Otherwise-safe command перестаёт считаться read-only, если содержит shell constructs, которыми можно злоупотребить, и больше не выполняется без вопроса: в Plan она уходит к Guardian или спрашивает вас (см. [Plan Mode](#plan-mode-plan)), а Don't ask её отклоняет:

**Command chaining** — может перейти к dangerous command:

```
&&   ||   ;   |   &   |&
```

**Redirects** — могут перезаписать files:

```
>   >>   >&
```

**Substitution** — может выполнить embedded commands:

```
$(…)   `backticks`   <(…)   >(…)
```

**Control characters** — newlines и carriage returns работают как separators.

Commands разбираются в syntax tree, поэтому compound вроде `git status && git log` валидируется по частям — каждая simple command должна быть safe сама по себе. Safe input redirects (`<`) и output to `/dev/null` разрешены.

::: note
Safe command перестаёт выполняться без вопроса, как только вы соединяете её с shell construct. Например, `ls | grep foo` больше не выполняется без вопроса в Plan mode, потому что pipe может перейти к небезопасному действию. Запускайте части отдельными commands.
:::

## Credentials

Карточки Nessy Gateway аутентифицируются токеном шлюза, который хранит приложение; сессия командной строки Developer Platform (`dp`) нужна только для выпуска этого токена и для самих инструментов Developer Platform. С 1.38.0 чат никогда не ждёт эту сессию: если она закончилась, чат продолжает отвечать, в сессии появляется одно уведомление с командой `dp auth login`, и отказывают только инструменты Developer Platform — по имени, с указанием, что делать. Уведомление различает закончившуюся сессию и `dp`, до которого приложение не смогло достучаться.

Secrets для external services обрабатываются аккуратно:

- Хранятся в encrypted file внутри config directory
- Не показываются plain text после ввода
- Scoped к workspaces и sources, которым нужны

Когда агенту впервые нужны credentials сервиса, вы получаете prompt, вводите их, и они безопасно сохраняются для следующих запусков. См. [Credentials](../reference/config/credentials) для полной storage model.

## Best Practices

- **Начинайте в Plan.** Когда смотрите незнакомый code или systems, сначала исследуйте безопасно.
- **Используйте Manual для ежедневной работы.** Default даёт хороший balance между speed и control.
- **Оставляйте Bypass permissions для trusted flows.** Используйте его для понятных repeatable tasks, где доверяете каждому действию.
- **Настройте read-only набор под свой workflow.** Добавьте обычные build commands, test runners и safe MCP operations, чтобы они работали в Plan без prompts.
- **Читайте перед approval.** В Manual mode просматривайте, что сделает command, прежде чем разрешить — особенно если она незнакома.
