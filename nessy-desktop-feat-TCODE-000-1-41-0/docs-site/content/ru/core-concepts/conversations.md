# Диалоги

Nessy Desktop хранит работу так же упорядоченно, как почтовый клиент хранит inbox. Каждая задача живёт в отдельном conversation thread, поэтому можно вести несколько задач одновременно, отойти и позже вернуться к любой из них без потери контекста.

## Inbox для нескольких диалогов

Каждый диалог — независимый thread. Из inbox можно:

- Начать новый thread, поставить его на паузу и вернуться к нему когда удобно
- Группировать threads по status (Backlog, Todo, Needs Review, Done и любые custom states, которые вы добавите)
- Искать и фильтровать, чтобы находить прежнюю работу
- Архивировать или удалять threads, когда они больше не нужны

Поскольку threads изолированы, долгий refactor не смешивается с быстрым разовым вопросом.

## Формат Session ID

Каждому диалогу назначается читаемый identifier такого вида:

```
YYMMDD-adjective-noun
```

Сегмент `YY` — двухзначный год (`26` для 2026, `25` для 2025). Несколько примеров:

- `260111-swift-river` — создан 11 January 2026
- `260108-bright-mountain` — создан 8 January 2026
- `251230-calm-harbor` — создан 30 December 2025

Дата в начале упрощает сортировку и просмотр threads, а пара adjective-noun делает каждый identifier узнаваемым.

## Хранение диалогов

Диалоги записываются на диск как JSON Lines (JSONL) в глобальном разделе
сессий. `CONFIG_DIR` равен `NESSY_CONFIG_DIR`, если переменная задана, иначе —
`~/.nessy-agent`:

```
CONFIG_DIR/sessions/{workspace-id}/{session-id}/session.jsonl
```

Ресурсы Workspace находятся в `CONFIG_DIR/workspaces/{workspace-id}`. Сессии
не вложены в этот каталог: связь с Workspace задают раздел пути и поле
`workspaceId` в заголовке.

Структура файла:

- **Line 1** — session header со всеми metadata для list view
- **Lines 2 and beyond** — по одному message на строку

```jsonl
{"id":"260111-swift-river","workspaceId":"ws-abc123","createdAt":1737451800000,"lastUsedAt":1737451900000,"sessionStatus":"todo","permissionMode":"default","workingDirectory":"/Users/you/projects/nessy"}
{"id":"msg_1","type":"human","content":"Summarise the auth module","timestamp":1737451800000}
{"id":"msg_2","type":"assistant","content":"The auth module has three entry points...","timestamp":1737451802000}
```

Частые поля header:

| Field | Описание |
| ----- | -------- |
| `id` | Session ID (`YYMMDD-adjective-noun`) |
| `workspaceId` | Неизменяемый идентификатор Workspace, которому принадлежит диалог |
| `createdAt` | Время создания в milliseconds |
| `lastUsedAt` | Время последней активности в milliseconds |
| `sessionStatus` | Status ID, например `todo` или `done` |
| `permissionMode` | Stored mode: `dontAsk`, `plan`, `default`, `acceptEdits`, `auto` или `bypassPermissions`; упразднённый `explore` (читается как `plan`) и прежние написания (`safe`, `ask`, `allow-all`, …) в старых файлах остаются читаемыми |
| `name` | Optional name, заданное для thread |
| `isFlagged` | Отмечен ли thread флагом |
| `labels` | Applied labels (bare IDs или entries `id::value`) |
| `model` | Per-session model override, если задан |
| `llmConnection` | Connection slug; можно менять в любой момент, когда сессия не занята (см. *Смена интеграции*) |
| `connectionLocked` | Привязана ли к сессии собственная connection вместо workspace default |
| `thinkingLevel` | Reasoning level: `off`, `low`, `medium`, `high`, `xhigh` или `max` |
| `workingDirectory` | Directory, из которой запускаются bash commands и file tools |
| `enabledSourceSlugs` | Slugs источников, active для этого thread |

`workingDirectory` — необязательный указатель на внешний Project, а не путь к
хранилищу Workspace. UI передаёт выбранный Project через непрозрачный handle,
а backend заново проверяет его каноническую идентичность. Ни путь, ни запись в
истории недавних Project не являются основанием для авторизации. Инструкции,
skills, MCP, hooks, agents, memory и policy из `.nessy-agent` загружаются только после
доверия Project.

Ветка сессии ссылается на родителя парой `{ workspaceId, sessionId }` и не
хранит путь к управляемой родительской сессии.

Вынос header в отдельную строку полезен по трём причинам:

- **Быстрый рендер списка** — inbox читает только первую строку каждого файла
- **Дешёвые appends** — новые messages добавляются без переписывания всего файла
- **Простой parsing** — каждая строка самостоятельна и обрабатывается отдельно

## Организация по статусам

Statuses помогают отслеживать, где thread находится в workflow:

| Status | Category | Meaning |
| ------ | -------- | ------- |
| **Todo** | Open | В очереди, ещё не начат |
| **Backlog** | Open | Записано, но ещё не запланировано |
| **Needs Review** | Open | Ждёт проверки результата |
| **Done** | Closed | Завершён |
| **Cancelled** | Closed | Брошен или больше не актуален |

**Open** statuses остаются в inbox; **closed** statuses выводят thread из active queue. Набор полностью редактируется — см. [настройку статусов](../statuses/customizing), чтобы добавить состояния вроде Blocked или Waiting.

## Batch Operations

Выберите несколько threads, чтобы действовать с ними вместе. Удерживайте **⌘ Click** (macOS) или **Ctrl+Click** (Windows/Linux), чтобы переключать отдельные threads, или **⇧ Click**, чтобы выбрать диапазон. Если выбрано больше одного thread, batch panel предлагает:

| Action | Effect |
| ------ | ------ |
| **Change Status** | Применить один status ко всем выбранным threads |
| **Set Labels** | Переключить labels по всему selection |
| **Flag / Unflag** | Поставить или снять flag у всех выбранных |
| **Archive** | Архивировать весь selection |
| **Delete** | Навсегда удалить выбранные threads |

Нажмите **Esc**, чтобы сбросить selection.

::: tip
Right-click по multi-selection открывает context menu с теми же actions.
:::

## Непрерывность диалога

Повторное открытие thread восстанавливает всё его состояние, поэтому можно продолжить так, будто вы не уходили:

- Все прежние messages на месте
- Агент помнит, что уже обсуждалось
- References к files и documents из прошлых turns остаются валидными

### Повторное открытие длинного, давно неактивного диалога

Большой диалог, который долго лежал без движения, стоит вам денег на **каждом**
последующем запросе, потому что вся история пересылается заново. Поэтому при
повторном открытии такого диалога — неактивного и размером примерно от 100 000
токенов — Nessy один раз спрашивает, до вашего первого сообщения:

- **Возобновить по сводке** — диалог сначала сжимается, и последующие запросы
  несут сводку вместо полной расшифровки.
- **Возобновить целиком** — сохраняется каждая деталь, ценой запроса, растущей
  вместе с размером диалога.

Спрашивается один раз на открытие, а не на каждое сообщение. Порог меняется
ключом `reopenCompactPromptTokens` в `config.json`; **ноль или отрицательное
число выключает диалог**.

### Ветвление диалога

`/branch` форкает диалог на месте и переключает вас в ветку, так что можно
попробовать другое направление, не теряя нить, из которой вы пришли. Кнопка на
ходе делала это и раньше; команда нужна, чтобы ветвление было доступно и там,
где нечего нажать в расшифровке. Работает на всех трёх рантаймах, включая ещё не
запущенную сессию Codex.

### Диалог, работающий агентом

Диалог можно закрепить за одним из ваших агентов. Тогда его system prompt и его
ограничения инструментов действуют на каждый ход — а не только на порождённых им
детей, — и в композере рядом с режимом разрешений появляется `@<имя>`, чтобы
было видно, кто отвечает. Задаётся ключом `sessionAgent` в `config.json`.
Переключение на рантайм без агента основного потока сообщает, что закрепление
снимается, а не игнорирует его молча.

```
> Resuming 260111-swift-river…

Last message: "Mapped out the auth module dependencies."

> Good — let's start the refactor.
Picking up where we stopped. I'll begin with the token exchange path…
```

## Сколько живёт агент диалога

Открытый диалог держит запущенного агента, и этот агент переживает отдельные
сообщения. На Claude это новое: раньше приложение поднимало процесс на каждое
сообщение и завершало его вместе с ответом — поэтому на этом runtime ничто не
могло продолжаться между ходами.

**Освобождается он только когда простаивает.** Через тридцать минут без начатых
и завершённых ходов агент выключается, а следующее сообщение поднимает его
заново — диалог, файлы и история не меняются, и цена освобождения — секунды на
старт, а не тред. Окно меняет
[`NESSY_IDLE_AGENT_TTL_MS`](/ru/reference/config/environment-variables), им же
освобождение выключается совсем. Чат Codex хранит свои файлы переписки (собственный
транскрипт треда Codex, вместе с выводом инструментов) в закрытой папке, пока вы не
удалите чат, поэтому после освобождения или перезапуска приложения модель продолжает
тот же тред.

**Пока агент что-то держит, освобождение откладывается.** Идущий ход, фоновая
задача, фоновая команда, дочерний агент, неотвеченная карточка разрешения и
ожидающий вас вопрос — всё это его удерживает. Как и диалог, который слушает:
monitor плагина, канал подключённого инструмента. Освободить такой — не поставить
на паузу, а оглушить до вашего следующего сообщения.

**Когда открыто слишком много диалогов сразу**, приложение отказывается поднимать
нового агента, а не отбирает работу у занятого, и называет, сколько диалогов ещё
что-то держат. Дождитесь завершения или остановите один и отправьте снова.

**Stop отменяет ход, а не диалог.** Агент остаётся и отвечает на следующее
сообщение. Если он перестал реагировать на отмену, приложение завершает его через
пять секунд — чтобы не оставить тред, который никогда не ответит.

## Смена интеграции

Диалог не привязан к той интеграции, на которой начался. Picker предлагает все
интеграции в любой момент, когда сессия не занята, и смена происходит на месте —
тред сохраняет имя, проект, файлы и историю.

Есть три уровня, и они отличаются по последствиям:

| Что меняется | Что происходит |
| --- | --- |
| Модель внутри одной интеграции | Больше ничего не меняется. Подтверждения нет. На Claude запущенный агент перенастраивается на месте, так что нет даже перезапуска — если только у новой модели не другая форма thinking или она вне семейства Claude. |
| Интеграция, тот же агент под ней | Агент перезапускается и продолжает свою запись диалога. |
| Интеграция, другой агент | Диалог передаётся, часть вещей останавливается. Спрашивает заранее. |

**Спрашивает только третий уровень.** В подтверждении перечислено именно то, что
остановится: фоновые агенты, always-on monitor плагина, language server от
плагина и уже приложенные изображения, которые новый агент прочитать не сможет.
Именно перечислено, а не посчитано: число не с чем сверить.

### Что переходит, а что нет

Агент, которого в этом диалоге ещё не было, получает сам диалог, а не его
пересказ: когда история помещается в контекстное окно новой модели, переносится
вся переписка целиком — включая вызовы инструментов и их результаты, так что
агент может ответить про файл, который читали, или команду, которую запускали
до переключения, — и она становится его собственной нативной историей. Когда не
помещается или окно неизвестно, переносится текстовая сводка последних
сообщений — и окно подтверждения заранее говорит, какой из двух вариантов вас
ждёт. Агент, на котором вы **уже были**, помнит диалог сам — он возобновляет
свою запись и получает только то, что пропустил, а не всю переписку второй раз.

Выбранная модель тоже переживает переезд, если новая интеграция её предлагает;
если нет — сессия окажется на модели по умолчанию этой интеграции, и
уведомление назовёт обе стороны замены.

Не переходит:

- **Незавершённый ответ.** Пока пишется ответ, смена отклоняется.
- **Всё, что запланировал прежний агент** — `/loop`, фоновые агенты, мониторы.
  Они останавливаются вместе со сменой; те, что могут запуститься снова,
  запускаются при возврате.
- **Выданные разрешения.** «Always allow» — это ответ про одного агента; другой
  спросит заново.
- **История счётчика контекста.** У каждого агента своя ёмкость, поэтому счётчик
  сбрасывается и наполняется заново от текущего агента.

Смена также отклоняется, если уход оставит незакоммиченную работу в worktree, —
и отклоняется заранее, до того как что-либо демонтировано, когда цель попросту
не сможет запуститься здесь: её рантайма нет в этой сборке, отсутствует бинарь
или у подключения нет рабочих учётных данных. Сначала войдите, затем
переключайтесь.

## Как строится контекст

Диалог привязан к одной workspace, а context накапливается естественно по ходу работы:

```
> Find the release checklist
Found "Release Checklist v3" — here's the outline…

> Add a section called "Rollback"
Added a "Rollback" section.

> Now add three steps under it
Added three steps:
1. Snapshot the database
2. Revert the deployment
3. Notify the on-call channel
```

Можно опираться на прошлые turns фразами вроде "that document" или "the step we just added" — агент отслеживает, на что вы ссылаетесь.

## Новый диалог

Используйте **New Chat** в sidebar (или keyboard shortcut), чтобы открыть свежий thread. Создаётся новый session ID, а все существующие threads остаются на месте в inbox.

## Skills в диалогах

Skills — named capabilities, которые вызываются inline через bracket syntax. Вызванный skill работает с доступом ко всему разговору на текущий момент:

```
> Find the release checklist
Found "Release Checklist v3"…

> [skill:research] Gather background on the rollback strategy
Running the research skill…
(the skill can read the checklist from the previous turn)
```

Это значит, что skills могут строиться на прежнем контексте, ссылаться на documents, уже появившиеся в thread, и вызываться цепочкой. См. [документацию Skills](../skills/overview), чтобы добавить и вызвать их.

## Длинные диалоги

Для extended sessions context управляется автоматически, поэтому его не нужно
pruning вручную. Большие tool results обрезаются, а active agent backend
управляет context window.

Local Pi sessions умеют показывать live context usage: команды `/usage` и
`/context` отображают model window, current context, remaining tokens и source
числа. После `/compact` session обновляет meter сразу после завершения
compaction.

Когда вы сами запускаете `/compact` в Pi session, модель формирует
структурированную контрольную точку контекста — текущий прогресс и ключевые
решения, действующие ограничения и ваши предпочтения, что ещё осталось сделать
и любые критичные данные или ссылки — так что заменяющее transcript summary
читается как handoff для модели, которая продолжит работу. Автоматическая
compaction (когда context window заполняется) использует встроенное summary
самого backend.

Автоматическая compaction проверяется после ответа модели, поэтому оставленный
запас должен покрыть весь следующий ход — ваше сообщение и каждый tool result,
который оно вызовет. Nessy Desktop подбирает этот запас так, чтобы в него
помещался хотя бы один tool result максимально разрешённого размера, и
увеличивает его вместе с `NESSY_MCP_OUTPUT_TOKENS`. На модели с небольшим context
window запас ограничен третью окна, чтобы в узком окне оставалась пригодная
история.

Nestor Cloud sessions показывают только то, что сообщает remote agent. Если
cloud agent присылает structured usage или compaction state, Nessy Desktop
отображает их; если нет, context meter остаётся unavailable и не угадывает
remaining window локальными heuristics.

## Отдельная история на workspace

У каждой Workspace отдельная история диалогов, хотя все разделы сессий находятся
в `CONFIG_DIR/sessions`:

| Workspace | History |
| --------- | ------- |
| Personal Notes | Separate |
| Work Projects | Separate |
| Client Engagement | Separate |

Переключение workspace переключает вас на threads этой workspace.

## Sharing

Поделиться чатом можно из его меню или заголовка: после карточки подтверждения снимок со скрытыми секретами публикуется в t-artifacts. См. [Общий доступ](/ru/go-further/sharing).

## Советы для эффективных диалогов

- **Ссылайтесь коротко.** Вместо повторения полных названий достаточно фразы вроде "that doc" или "the task from a moment ago" — агент удерживает, что вы имеете в виду.
- **Итерируйте сразу.** Сразу после создания чего-то уточняйте на месте: "give it a due date" или "rename that".
- **Исправляйте быстро.** Если агент понял запрос не так, скажите прямо — "no, I meant the other repo" или "the older one".
- **Опирайтесь на статусы.** Пометки Todo, Needs Review или Done делают параллельную работу читаемой.
