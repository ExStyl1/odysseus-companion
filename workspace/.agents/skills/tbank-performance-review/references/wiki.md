# Wiki

Используй authenticated read-only Wiki/Wixie MCP tools Nessy. Выбранные Wiki instances исследуй отдельно.

## Identity-first запрос

Перед первым вызовом сверь runtime schema Wiki/Wixie search tool. Корпоративный login из входа — первый и основной seed. Не начинай Wiki-ветку с названий целей, сервисов или task IDs.

Составляй первый запрос по следующему приоритету:

```text
1. Если schema имеет author_login, author, creator или user filter:
   author=<точный employee login>
   query=<пусто>
   date range=<search_window>, если поддерживается

2. Если отдельного identity filter нет:
   query="<точный employee login>"
   date range=<search_window>, если поддерживается
```

В первом запросе login должен быть единственным поисковым значением. Не соединяй его с ФИО, целью или ключевыми словами через `AND/OR`. Если tool сначала требует разрешить пользователя, получи внутренний user ID по exact login и используй его в author filter.

Начинай с компактной страницы. Листай до reported total, пустой страницы или platform cap. Если API не поддерживает даты, собери bounded identity-выдачу и классифицируй `created/updated` относительно `search_window` после получения результатов; отсутствие server-side date filter явно зафиксируй как ограничение.

## Проверка identity

Для каждого результата сравни `author`, `creator`, `owner`, `contributors`, `created_by` и `updated_by` — только те поля, которые реально вернула schema. Разделяй роли:

- сотрудник создал документ;
- сотрудник содержательно обновлял документ;
- login только упомянут в тексте или метаданных;
- связь с сотрудником не установлена.

Exact query по login может находить простое упоминание. Оно помогает discovery, но не подтверждает авторство. ФИО или альтернативное имя используй только после подтверждённого mapping с исходным login; не расширяй identity по догадке.

## Уточнение по целям

После identity inventory:

1. Сопоставь найденные страницы с исходными целями по title, space, task IDs, repository/service names и содержанию.
2. Прочитай только релевантный shortlist.
3. Извлеки решения, рассмотренные альтернативы, критерии принятия, метрики и связанные task/repository IDs.
4. Только для пробелов выполни дополнительные exact-поиски по task ID или устойчивому термину цели. Такие страницы могут подтверждать контекст или командный outcome, но личный вклад — только при наблюдаемой identity-связи.

Не выполняй широкий goal search, если identity inventory уже дал достаточное подтверждение цели. Нулевая выдача по login не завершает Wiki-ветку: проверь корректность instance, identity field и exact syntax, затем используй exact task IDs целей как fallback для контекста.

Документ без подтверждённого авторства или содержательного обновления сотрудником доказывает контекст или решение, но не личный вклад. Страница вне `review_period` требует связанного события или изменения внутри него, иначе остаётся context-only.

`complete` требует по каждому выбранному Wiki instance: identity-first запрос по exact login/user ID, проверенную пагинацию, классификацию ролей и сопоставление identity shortlist со всеми целями. Непроверенный instance, truncation или только тематический поиск без login означает `partial`.
