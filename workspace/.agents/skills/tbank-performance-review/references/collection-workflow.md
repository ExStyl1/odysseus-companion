# Workflow сбора

Этот файл читается только после получения login, периода, выбранных систем, целей и allowlist каналов Time, если Time выбран.

## Подготовка

Если output path не указан, создай без перезаписи `performance-review/<employee-slug>-<start>-<end>/` относительно рабочей директории. Не проси пользователя выбирать технический путь. Создай только `raw/<selected-system>/`.

Зафиксируй два разных интервала:

- `review_period = [start, end)` — указанный пользователем период оценки;
- `search_window = [start - 14 дней, end + 14 дней)` — техническое окно сбора во всех выбранных системах.

Пользователя отдельно о буфере не спрашивай. Во всех поисковых запросах используй `search_window`, но для каждого существенного события сохраняй фактическую дату и `period_relation`: `before-period-buffer`, `in-period` или `after-period-buffer`. Пограничные события включай только когда они связаны с работой периода: например, задача заведена незадолго до начала, закрыта вскоре после конца или содержит доказательство работы внутри периода.

Исходный корпоративный login — главный identity seed во всех выбранных системах. В каждой ветке сначала выполни bounded identity inventory по exact login или разрешённому из него внутреннему user ID, затем уточняй найденное через цели, task IDs и названия сервисов. Широкий поиск только по теме не заменяет identity inventory.

Не добавляй к login ФИО, goal terms или большой `OR` в первый запрос: это снижает точность и усложняет проверку покрытия. Не приписывай находку сотруднику, пока источник не показывает наблюдаемую связь: author, assignee, committer, reviewer, coordinator или другую точную роль.

## Параллельный сбор

Назначь независимого subagent каждой выбранной системе. Используй максимум доступных слотов, остальные системы запускай по мере освобождения. Каждый subagent:

1. читает только reference своей системы;
2. работает прямыми authenticated read-only Nessy MCP tools и сверяет runtime schema;
3. сохраняет ответы только в своём `raw/<system>/`;
4. пишет свою сводку и ответ координатору на русском;
5. возвращает компактные факты и новые cross-system seeds.

Для Time координатор принимает сводку только при пройденном `Inventory gate` из [Time reference](time.md): отдельный paginated `search_posts` без query для каждого разрешённого канала, exact channel ID, employee ID и полное `search_window`, затем goal searches и thread expansion. Если trace показывает `read_channel` вместо author inventory, response содержит posts другого канала либо даты выходят за окно, верни ветку на досбор и не используй её счётчики в `RESULTS.md`.

Первичная сводка GitLab не финальна. Координатор собирает из Jira, Tracker, Wiki и Time все GitLab URLs, repository paths, task IDs, branch names и commit clues, передаёт их GitLab-ветке и принимает её результат только после второго прохода и `GitLab completion gate` из [GitLab reference](gitlab.md). Непроверенные MR URLs или вывод `0 direct MR` после одного author-search требуют досбора.

References: [Jira](jira.md), [Tracker](tracker.md), [GitLab](gitlab.md), [Wiki](wiki.md), [Time](time.md).

Если subagents недоступны, выполни те же независимые ветки сам. Недоступность одной системы не блокирует остальные.

## Поисковая воронка

Для каждой исходной цели в каждой выбранной системе двигайся адаптивно:

```text
exact employee login/user ID + search_window
→ identity inventory
→ exact IDs и устойчивые термины цели внутри найденного scope
→ semantic shortlist
→ детали релевантных сущностей
→ перенос новых IDs, repos и документов в другие системы
→ проверка пробелов относительно ожидаемого результата
```

Конкретные запросы и их количество определяет subagent. Для каждой цели получи хотя бы один прямой результат либо зафиксируй, какие независимые стратегии ничего не нашли. Расширяй ветку, пока следующая bounded-итерация добавляет факты или связи. Остановись при исчерпании seeds, двух последовательных нерелевантных итерациях, platform limit либо достаточном подтверждении результата. Не делай массовую выгрузку.

После первичного сбора выполни одну correlation wave: например, task ID из Jira ищи в GitLab, название решения из Wiki — в Tracker, MR — в документации. Time остаётся внутри исходного allowlist. Дождись результатов повторных веток: correlation wave считается завершённой после проверки переданных seeds, а не после их перечисления в разделе «нужно уточнить».

## Coverage-checkpoint

Для каждой выбранной системы проверь: identity, полное `search_window`, классификацию относительно `review_period`, цели, pagination/truncation, выполненные стратегии, cross-system seeds и сохранённые raw-ответы. `complete` допустим только при выполнении критериев platform reference. Усечённая выдача, непроверенная большая выборка, непроверенные прямые ссылки или единственная неудачная попытка означают `partial`, а не `complete`/`failed`.

## Результат

Создай один пользовательский `RESULTS.md` по [формату результата](results-format.md). Правила силы источников возьми из [качества доказательств](evidence-quality.md).

Перед синтезом нормализуй находки в claim ledger из `evidence-quality.md`, объедини дубли одного события и проведи contradiction audit. Ценность формулируй только после установления фактического изменения и его получателя. Наблюдаемое поведение сохраняй как конкретный эпизод; повторяющееся качество отмечай только при двух независимых эпизодах.

Все значимые задачи, документы, MR и другие артефакты с известным URL оформляй кликабельными Markdown-ссылками. Сохрани полный безопасный ответ каждого bounded read в `raw/<system>/`; рядом зафиксируй tool, arguments без секретов, время, scope, pagination и truncation.

Отделяй личное действие, deliverable, командный outcome и ценность. Неизвестное оставляй неизвестным, inference помечай. Все существенные утверждения должны иметь прямой источник или явную пометку о слабом подтверждении.

Не смешивай основной период с буфером. Событие из `before-period-buffer` или `after-period-buffer` используй как пограничный контекст и явно подписывай. Закрытие задачи после `end` не является завершением в периоде; при наличии доказательств можно отдельно описать работу, выполненную в периоде, и более поздний outcome.

После записи перечитай `RESULTS.md` по точному пути. Только успешный read-back позволяет утверждать, что файл сохранён; при ошибке записи честно верни материал в ответе и назови blocker. В финальном ответе на русском покажи статусы выбранных систем и ссылку на подтверждённый `RESULTS.md`. `raw/` упомяни только как технический след. Для подготовки текста предложи `tbank-performance-writer`.

Read-back включает смысловую проверку: статусы целей не смешаны со статусами систем; суммы и списки согласованы; утверждения `все`, `полностью`, `production`, `без downtime`, `закрыта уязвимость` имеют прямое подтверждение; каждая сильная сторона опирается минимум на два эпизода. При ошибке исправь `RESULTS.md` и перечитай снова.

## Границы

- Все внешние операции read-only: не создавай и не изменяй задачи, комментарии, сообщения, MR или статусы.
- Не сохраняй tokens, cookies и authorization headers.
- Личные email, телефоны, screenshots и другие персональные данные, не нужные для рабочего результата, замени на `<REDACTED>` уже в raw и не переноси в `RESULTS.md`.
- Не выставляй оценку сотруднику и не превращай ожидаемый результат в достигнутый без evidence.
