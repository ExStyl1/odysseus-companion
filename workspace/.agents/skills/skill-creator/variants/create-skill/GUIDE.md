# Create Skill

Skill для создания новых skills, соответствующих контракту и принципам репозитория.

## Когда использовать

- Создать новый skill с нуля;
- проверить существующий skill на соответствие контракту;
- переработать или улучшить структуру skill'а.

## Инструкции

### 1. Выясни задачу

Спроси у пользователя (если не указано явно):

- **Что должен делать skill?** — одна конкретная задача, не набор слабосвязанных действий.
- **Какой триггер?** — когда skill должен запускаться (ключевые слова, контекст, тип задачи).
- **Какой ожидаемый результат?** — что агент выдаёт на выходе (отчёт, код, чеклист, diff и т.д.).
- **Глобальный или доменный?** — применим для всех команд shopping или специфичен для одной (Hotels, Avia, ЖД и т.д.).

Потребитель skill'а — AI-агент, но создаёт его разработчик через агента. Пиши инструкции так, чтобы разработчик понимал назначение, а агент мог точно исполнить.

### 2. Выбери имя

- kebab-case, 2–3 слова: `code-review`, `bug-investigation`, `release-checklist`.
- `name` во frontmatter совпадает с именем папки.
- Имя самодокументирующееся — понятно без пояснений.
- **Доменный скилл**: `name` = `<domain>-<skill>`, например `hotels-acceptance-criteria`. Папка: `skills/hotels-acceptance-criteria/`.

### 3. Создай структуру

```text
skills/<skill-name>/
  SKILL.md                      ← обязательный, < 2500 токенов
  references/                   ← опционально, детали по запросу
    examples.md
  assets/                       ← опционально, не-markdown файлы
    config.json
```

Единственный обязательный файл — `SKILL.md`. Подробные примеры → `references/`, конфиги → `assets/`.

### 4. Напиши SKILL.md

#### Description — самая важная часть

Формула: `что делает` + `когда применять`. Description определяет, когда skill активируется.

```yaml
# Плохо — размытый, агент не поймёт когда активировать
description: Помогает с код-ревью

# Хорошо — конкретные триггеры
description: >
  Структурированное код-ревью с фокусом на безопасность и читаемость.
  Применяй при ревью PR, проверке чужого кода или запросе review.
```

Если skill пересекается с другим: `"...Не для поиска багов (→ см. bug-investigation)."`

#### Шаблон

```markdown
---
name: <skill-name>
description: >
  <Что делает.> <Когда применять — конкретные триггеры.>
---

# <Название>

<1–2 предложения: что это и зачем.>

## Когда использовать

Используй этот skill, когда нужно:

- <сценарий 1>;
- <сценарий 2>;
- <сценарий 3>.

## Инструкции

<Пошаговые действия. Нумерованный список для последовательных шагов.>

## Формат ответа

<Опционально. Структура результата.>

## Ограничения

<Опционально. Чего skill НЕ делает.>
```

#### Persona (опционально)

Одна строка в начале body (до первого заголовка) для скиллов с чёткой доменной ролью. Пропусти для процедурных или коротких скиллов.

```markdown
**Persona:** Ты — старший инженер по безопасности. Думаешь в терминах моделей угроз, а не фич.
```

#### Reasoning в инструкциях

Каждое правило должно объяснять **почему** — без обоснования агент не адаптирует правило к граничному случаю:

```markdown
# Плохо — голое правило

3. Не используй `any` в типах.

# Хорошо — с обоснованием

3. Не используй `any` — это отключает проверку компилятора,
   и баг проявится только в рантайме.
```

#### Токен-бюджет

| Компонент            | Лимит                            |
| -------------------- | -------------------------------- |
| `description`        | ~100 токенов                     |
| `SKILL.md` body      | < 2 500 токенов (~100–150 строк) |
| body + `references/` | < 10 000 токенов суммарно        |

Не влезаешь → выноси в `references/`: `[Подробнее](references/details.md)`

### 5. Проверь по чеклисту

- [ ] **Одна задача** — не пытается быть универсальным.
- [ ] **Frontmatter** — `name` и `description` есть, name = имя папки.
- [ ] **Description с триггерами** — `что делает` + `когда применять`; нет пересечений с другими скиллами.
- [ ] **Секция «Когда использовать»** — 2–5 конкретных сценариев.
- [ ] **Инструкции конкретны** — каждый шаг = одно действие; каждое правило объясняет «почему».
- [ ] **Нет воды** — каждое предложение несёт смысл.
- [ ] **Токен-бюджет** — body < 2 500 токенов.
- [ ] **Нет дублирования** с другими скиллами.

### 6. Частые ошибки

| Ошибка                     | Почему плохо                                                                         | Как правильно                                   |
| -------------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------- |
| Skill делает всё           | Агент теряет фокус — результат непредсказуем, потому что нет чёткого scope           | Разбей на узкие скиллы с явными границами       |
| Расплывчатые инструкции    | «Проанализируй код» даёт разный результат каждый раз — агент сам додумывает критерии | Опиши конкретные шаги и критерии оценки         |
| Description на 3 абзаца    | Агент тратит токены на парсинг — description грузится для всех скиллов при старте    | 1–2 предложения по формуле `что` + `когда`      |
| Голые правила без «почему» | Агент не адаптирует правило к граничному случаю — слепо следует или игнорирует       | Встрой обоснование: «X, потому что без этого Y» |

## Формат ответа

После создания skill'а выведи:

1. Путь к созданному файлу.
2. Краткое резюме: что делает, когда использовать (2–3 строки).
3. Результат чеклиста из шага 5.
