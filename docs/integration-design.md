# Общий профиль и независимые обновления

Первоначальная схема: 2026-10-20. Текущее размещение кода и порядок разработки:
[Работа с кодом Odysseus](development.md).

Odysseus объединяет пользовательские ресурсы двух существующих приложений.
Исходники, сборки, установки, версии и штатные обновления остаются отдельными.
Это композиция приложений, а не перенос двух разных агентных ядер в одно.

## Нативные точки подключения

Сначала проверены существующие механизмы:

- CLI: `packages/cli/src/config/mcpJson.ts` читает проектный `.mcp.json`
  и ставит `scope: project`; `packages/core/src/config/storage.ts` поддерживает
  `.agents/skills`; `subagents/subagent-manager.ts` читает `.nessy/agents`;
  `utils/rulesDiscovery.ts` читает `.nessy/rules`.
- Desktop: `packages/shared/src/capabilities/native-sources.ts` читает
  `.mcp.json`, `.agents/skills`, `.nessy-agent/agents` и `.nessy-agent/rules`
  только в доверенном проекте. Проверяет realpath: ссылки на внешний общий
  каталог не подходят. Поэтому используются обычные копии файлов.
- CLI: `utils/installationInfo.ts` и `utils/handleAutoUpdate.ts` уже отвечают
  за обновления. Desktop: `apps/electron/src/main/auto-update.ts` использует
  `electron-updater`. Odysseus их не заменяет и не запускает обновление соседа.

Форматы сверены с локальными читателями. Внешние контрактные страницы:
https://code.claude.com/docs/en/mcp.md,
https://code.claude.com/docs/en/skills.md,
https://code.claude.com/docs/en/sub-agents.md.
Попытка получить их в этой среде не удалась; внешняя актуальность не подтверждена.
Odysseus не меняет адаптеры форматов, схемы плагинов и рантаймы.

## Общие ресурсы

Единственный каталог: `shared/`. MCP — `mcp.json` с `mcpServers`;
skills — `skills/<slug>/SKILL.md` с соседними файлами;
агенты — `agents/<slug>.md`; правила/инструкции — `rules/**/*.md`.
Агенты используют общий базовый Markdown-формат с `name` и `description`.
Поля выбора модели, наборы инструментов и семантика hooks зависят от движка:
их эквивалентность не обещается. Хуки и разрешения сохраняют нативные механизмы.
Совместимые чаты, модели, настройки и учётные данные обслуживает отдельный
[личный профиль синхронизации](personal-sync-ru.md).

При подключении проект получает `.mcp.json`, `.agents/skills` и копии агентов/
правил в обе нативные директории. Локальные неуправляемые ресурсы сохраняются.
Новые локальные ресурсы включаются в общий каталог только явным `--import`.

MCP HTTP требует адаптации: CLI `tools/mcp-client.ts:createTransport` выбирает
Streamable HTTP по `httpUrl`, а Desktop — по `type: http` и `url`. Общий каталог
хранит `type`/`url`, проектные копии дополнительно несут `httpUrl` для HTTP.
При обратном чтении это поле нормализуется, противоречивые URL отклоняются.
Для SSE используется `type: sse`/`url`; для stdio — `type: stdio`/`command`.

## Запись и конфликты

Для каждого управляемого ресурса сохраняется SHA-256 последней успешной
синхронизации. Односторонняя правка или удаление распространяется на общий
каталог и все подключённые проекты. Несовместимые одновременные изменения
останавливают всю операцию до первой записи. MCP сравнивается по записям,
а не по файлу целиком; неизвестные поля документа сохраняются.

Сначала планируются все записи, затем выполняется транзакция с откатом при
ошибке ввода-вывода. Есть блокировка от параллельного sync. Это не файловая БД:
аварийное выключение питания между rename может оставить неполный sync;
перезапуск обнаружит расхождение. Не редактируйте файлы в момент sync.
Наблюдение — опрос раз в две секунды, конфликт не разрешается автоматически.

MCP не запускается менеджером; approval/trust остаются у приложений. Симлинки
в управляемых путях отклоняются. Секреты не выводятся в журнал. MCP-конфиг
создаётся с правами 0600. Данные приложений в домашнем каталоге не трогаются.

## Проверка

`npm test` проверяет общий профиль на временных проектах: обе раскладки,
импорт, независимые обновления компонентов, двусторонние изменения,
конфликты без частичной записи, удаления, symlink-границы и повторы sync.
`node tools/odysseus.mjs status` проверяет чтение реальных манифестов.

Живой acceptance требует установленных приложений: attach временного проекта,
доверие/approval в каждом приложении, видимость одного MCP и одного skill;
последовательное штатное обновление CLI и Desktop, повтор той же проверки.
Сборка и тесты исходных продуктов не заменяются тестами оболочки.
