## ФАЗА 1 — Статический анализ (Review)

**Ищи тесты, которые НИКОГДА не упадут при баге. Это хуже чем отсутствие тестов — они дают ложную уверенность.**

Смотри на **код тестов** критически. Для каждой проблемы указывай уровень серьёзности:

**Формат вывода:**
- **Критично** — блокирует мёрж: тест даёт ложную уверенность или никогда не упадёт при баге
- **Важно** — нужно исправить до мёржа: снижает надёжность или читаемость
- **Suggestion** — улучшение по желанию

### Чеклист качества

#### 1. Покрытие сценариев
- Покрыт ли happy path полностью?
- Есть ли тесты на отказ (невалидные данные, нарушение бизнес-правил, недостаток прав)?
- Проверяются ли граничные значения (лимиты, пустые поля, максимумы)?
- Нет ли явно пропущенных сценариев из требований?

#### 2. Качество проверок (assertions)
- Проверяется ли то, что важно для бизнеса (статус, данные, сообщение об ошибке)?
- Нет ли проверок «ответ пришёл» без проверки содержимого?
- Проверяются ли text сообщений об ошибках, а не только коды?
- Сообщения в assertions объясняют, что именно сломалось?

**❌ Слабые assertions (пройдут при любом баге):**
```typescript
expect(response).toBeDefined();         // пройдёт при 500 с error body
expect(response.status).toBeTruthy();   // 500 тоже truthy
expect(users).toBeTruthy();             // пустой массив тоже truthy в некоторых фреймворках
expect(result).not.toBeNull();          // любой non-null объект пройдёт
```

**✅ Точные assertions (упадут при конкретном баге):**
```typescript
expect(response.status).toBe(200);
expect(users).toHaveLength(3);
expect(users[0].email).toBe('expected@test.com');
expect(error.message).toContain('Email already exists');
```

#### 3. Читаемость
- Понятно ли из названия теста: что делает пользователь и что ожидает система?
- Можно ли понять тест без чтения кода приложения?
- Есть ли GIVEN/WHEN/THEN комментарии?
- Тест-код не перегружен техническими деталями?

#### 4. Надёжность (Flakiness)
- Тест не зависит от порядка запуска других тестов?
- Нет ли зависимости от времени, внешних сервисов или нестабильного окружения?
- Используются ли waitFor() вместо sleep()?
- Тест стабильно работает в CI?

#### 5. Поддерживаемость
- Тест не станет красным при правильном рефакторинге?
- Тестовые данные понятны и не будут конфликтовать с другими тестами?
- Нет ли дублирования сценариев между тестами?
- Используются ли shared fixtures для дублирующейся логики?

#### 6. Теги и CI-готовность
- Проставлены ли теги сьютов на каждый тест (@smoke, @regression, @sanity)?
- Критические бизнес-потоки помечены как smoke?
- Тесты можно запустить отдельно по тегу?
- URL не захардкожены — используется baseURL / env variable?
- Авторизация через shared fixture / конфиг / env, а не хардкод?
- Тесты готовы к параллельному запуску (нет shared state)?

#### 7. Adversarial Testing (Попытки сломать)

Думай как злоумышленник. Покрыты ли эти категории?

**Input Abuse:**
- Пустые строки, null, очень длинные значения?
- Спецсимволы, SQL/HTML-иньекции?
- Отрицательные числа, невалидные форматы (email без @)?

**Sequence Breaking:**
- Пропуск шагов флоу, переход напрямую к финалу?
- Повторная отправка формы, двойной клик?
- Действие после выхода из системы?

**Auth Boundary Testing:**
- Доступ к чужим ресурсам по ID?
- Действия без авторизации?
- Действия с недостаточной ролью?
- Использование устаревшего токена?

**State Corruption:**
- Параллельные запросы на одну операцию?
- Прерванные транзакции?

**Error Handling:**
- Что возвращает система при 500?
- При таймауте?
- Не раскрывает ли стектрейс или внутренние детали?

**API-специфично** (если это API тесты):
- Неверный Content-Type, отсутствующие headers?
- Rate limiting (429)?
- Large payloads (>10MB)?
- API versioning?

**E2E-специфично** (если это UI тесты):
- JavaScript errors in console?
- Network throttling (2G/3G)?
- Responsive design?
- Focus trap в модалях?
- Core Web Vitals (LCP, FID, CLS)?

**Database-специфично** (если есть DB тесты):
- Transaction isolation level?
- Constraint violations (unique, foreign key)?
- Connection pool issues?
- Concurrent operations?

Для каждой категории: либо подтверди что тесты покрывают её, либо укажи конкретный непокрытый сценарий.

## ФАЗА 2 — Динамический анализ (Verify + Mutation Testing)

**Вставь баг. Тест не упал? Значит тест не работает.**

### 2.1 Запуск всех тестов

Получи или спроси:
- Где лежат тесты (из CLAUDE.md)
- Где исходный код
- Какие окружения нужны

Запусти:
```bash
npm test           # или pytest / playwright test
```

**Результаты:**
```
Passed: 48
Failed: 2
Skipped: 3
Duration: 2m 15s

Покрытие:
  Statements: 85%
  Branches: 78%
  Functions: 90%
```

Если есть падения: спроси «это ожидаемо?»

### 2.2 Smoke suite

Запусти если есть:
```bash
npm run test:smoke   # или pytest -m smoke
```

**Результат:**
```
Smoke: 15 прошла (критические потоки работают)
```

### 2.3 Mutation Testing

**Идея:** Вставляем баг в код, проверяем упадут ли тесты.

**Примеры мутаций:**

```javascript
// Числа
if (age > 18) → if (age >= 18)  // Изменить оператор
if (age > 18) → if (age > 17)   // Изменить значение

// Строки
email.includes('@') → email.includes('_')

// Boolean
isAdmin && hasPermission → isAdmin || hasPermission  // Изменить оператор

// Возвращаемые значения
return user.email → return null
```

**Для каждой мутации:**
1. Вставь баг в код
2. Запусти тесты
3. Проверь результат:
   ```
   Тесты упали? Мутант убит (хорошо - тесты ловят баги)
   Тесты прошли? Мутант выжил (плохо - нужны новые тесты)
   ```

**Минимум:** 5-10 мутаций по разным функциям

### 2.4 Итоговый отчёт

```
## Динамический анализ (Verify + Mutation)

Запуск тестов:
  Passed: 48
  Smoke: 15
  Duration: 2m 15s

Покрытие:
  Statements: 85%
  Branches: 78%
  Lines: 85%

Mutation Testing:
  Всего мутаций: 15
  Убито (тесты поймали): 13
  Выжило (тесты упустили): 2
  Killed Rate: 87%

Выжившие мутанты (нужны тесты):
  [file]:45 — if (x > 5) → if (x >= 5) не поймана
  [file]:102 — return null не поймана

Интерпретация:
  >90% killed = Отличные тесты
  70-90% killed = Хорошие тесты
  <70% killed = Нужно добавить тестов
```
