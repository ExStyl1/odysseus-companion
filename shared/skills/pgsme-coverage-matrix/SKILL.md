# Процедура: тест-кейсы и матрицы покрытия для задач PGSME

## Когда применять
- Пользователь просит проанализировать Jira-задачи PGSME и вынести информацию для реализации
- Пользователь просит написать тест-кейсы по задачам
- Пользователь просит составить матрицу покрытия (по шаблону команды)
- Пользователь прикладывает файл «Матрица покрытия [название функционала].doc» (экспорт из Confluence)

## Шаг 1. Сбор контекста
1. Загрузить Jira-задачи через `dp_jira_issue`. Ключевые поля:
   - `customfield_169000` — описание/шаги воспроизведения
   - `customfield_169001` — тоглы, охват, «Для разработки», критерии приёмки
   - `customfield_11914` — эпик
   - комментарии (часто содержат уточнения и ссылки на порождённые задачи)
2. Загрузить связанные задачи: эпик, базовую постановку (например, PGSME-15513), связанные баги/фичи.
3. Загрузить Wiki-спеки по ссылкам из задач через `dp_wixie_get` (по pageId).
4. Найти связанные задачи через JQL: `project = PGSME AND summary ~ "<ключевое слово>"` — помогает найти автотест-таски, баги, эпики по теме.

## Шаг 2. Тест-кейсы — писать в чате, НЕ в Allure TestOps
- Пользователь хочет сначала увидеть тест-кейсы в чате структурированным текстом.
- Формат каждого ТК: таблица (Тип П/Н, Приоритет High/Medium/Low) + Предусловия + Шаги + Ожидаемый результат.
- Allure TestOps (dp_allure_create_testcase) — только после явного подтверждения пользователя.

## Шаг 3. Анализ классов эквивалентности
- Таблица: `Параметр | Класс эквивалентности | Значения | Ожидаемый результат | Покрытие`.
- Обязательно: граничные значения, негативные классы, «дыры» (когда проверка пропускается — например, отсутствие записи в справочнике).
- Открытые вопросы помечать ⚠️ (требуют уточнения аналитика) и выносить в раздел «Риски».
- После анализа добавить недостающие ТК (покрытие пробелов) и отдельно свести негативные ТК в таблицу.

## Шаг 4. Матрица покрытия по шаблону команды
Колонки (из шаблона Confluence «Матрица покрытия [название функционала].doc»):

| Приоритет | Функциональная область | Методы/Функционал/Кейс | env | Исполнитель | Статус проверки | Задача | Комментарий |

Правила заполнения:
- **Приоритет**: 1, 2, 3 (1 — критические сценарии приёмки).
- **Функциональная область**: уровень Epic (по карте функциональности QA MC, wiki pageId=6672887854).
- **Методы/Функционал/Кейс**: короткое описание тест-кейса (уровень Feature-Story), формат: провайдер, продукт, условие → ожидаемый результат.
- **env**: контур автоматизации (dev, zokii-mock и т.п.).
- **Исполнитель**: QA (ручная проверка) / Dev (автоматизация).
- **Статус проверки**: PLANNED / IN PROGRESS / DONE / UNREACHE (недостижимый сценарий).
- **Задача**: jira-таска Autotest (пусто, если ещё не заведена).
- **Комментарий**: ссылка на TC-код, критерий приёмки, открытые вопросы.

Подход **TCAAC** (Test Cases As a Code): тесты, которые нужно автоматизировать разработчикам, помечать исполнителем Dev.

## Шаг 5. Чтение .doc-файлов (экспорт Confluence)
Файлы «*.doc» из Confluence — это MIME-контейнер (multipart/related) с HTML в quoted-printable + base64-картинки. `read_file` их не отображает. На macOS:
```
textutil -convert txt -output /tmp/out.txt "<путь к файлу.doc>"
```
Затем читать через `read_file`. Нюансы:
- Имя файла может быть URL-encoded (например, `%D0%9C%D0%B0%D1%82%D1%80%D0%B8%D1%86%D0%B0+...`) — искать через `ls | grep`.
- В конце файла обычно base64-изображение — читать только текстовую часть (таблицы HTML).

## Шаг 6. Итоговый документ
- По запросу собрать всё в один .md: контекст и ссылки, общие предусловия, классы эквивалентности, ТК по задачам, матрицы покрытия, риски/открытые вопросы.
- Именование: `PGSME-<task1>_<task2>_test_cases.md` в домашней директории пользователя.

## Ключевые доменные факты (срочные платежи PGSME)
- Ошибка **-8880236** «Не сможем отправить срочный платеж с данного счета» — непереповторяемая (repeat_flag N, api_code pgFault).
- Разрешённые продукты отправителя: serno **3102, 3104, 3982**; продукты КК: **7159–7164** (ТПКК1–3, ТПККО1–3).
- Экспресс-комиссия: стандарт **299 ₽** (tcs_sme_fee_ext_tab, опция expressFee), индивидуализация — tcs_sme_client_individual_tab.express_comission_fee.
- Интерфейсы с комиссией: IBSME, MBSME, MB_PRT_US (+ OPENAPI после PGSME-22819).
- Провайдеры: contragent (комиссия в fee_amount), budget/taxes (в order_fee), fee (отдельный платёж).
- Консолидация/грейс-период: тип транзакции **787**, шаблон PGSME_COMMIS_EXT_BANK_TRANS.
- Экспресс-комиссия постируется всегда вместе с платежом (i028 на авторизации, i004AmtTrxn/TFEE на постинге); взимается только за межбанк.
