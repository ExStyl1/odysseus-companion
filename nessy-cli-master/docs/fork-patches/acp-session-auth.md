# acp-session-auth

## AIDT

AIDT-8409

## Зачем

ACP-клиент может создавать и восстанавливать сессии без предварительного
вызова `authenticate`, если способ авторизации уже выбран в CLI. Агент сам
вызывает `refreshAuth` с типом из конфигурации сессии.

В upstream эта проверка выполняется после инициализации сессии и MCP.
В форке `newSessionConfig` проверяет авторизацию до `config.initialize()` и
`waitForMcpReady()`, чтобы MCP запускались после входа. Порядок общий для
создания, загрузки и возобновления сессии. Существующая проверка после
инициализации сохраняется.

Если способ входа не выбран или `refreshAuth` завершился ошибкой, агент
возвращает `AuthRequired` и не создаёт сессию. Перед `session/prompt` агент
повторно проверяет авторизацию, если у конфигурации сессии нет активного
`authType`; сообщение передаётся дальше только после успешной проверки.

Подготовка Desktop при первом запуске описана отдельно в
[desktop-first-run-setup](./desktop-first-run-setup.md).

## Файлы

- `packages/cli/src/acp-integration/acpAgent.ts` — авторизация до инициализации
  сессии и проверка перед отправкой сообщения.

## Откат

1. Удалить вызов `ensureAuthenticated` перед `config.initialize()` в
   `newSessionConfig`, сохранив проверки в обработчиках создания и
   восстановления сессии.
2. Удалить проверку отсутствующего `authType` в `prompt`.
3. Удалить маркеры `[nessy-fork] acp-session-auth`, строку из реестра, ссылку
   из `desktop-first-run-setup.md` и этот файл.
