# Изменить правила ребрендинга

Работай в репозитории контроллера, где находится `scripts/rebrand/rebrand.mjs`.
Меняй правила там, а результат получай в отдельной чистой копии upstream.
Ручная правка итоговой ветки не исправляет следующий запуск движка.

## Перед изменением

- Прочитай `AGENTS.md`, `scripts/rebrand/README.md` и `scripts/rebrand/nessy.json`.
  Сверяй формат правил с текущим `rebrand.mjs`, а не с историей обсуждений.
- Проверь Git status контроллера и установи исходный ref/SHA. Не используй
  номер версии из примера как выбранный пользователем upstream.
- Найди исходный файл, его потребителей и ожидаемый результат. Различай бренд
  продукта и внешний контракт: ID моделей, OAuth, адреса провайдеров,
  заголовки протокола и авторство нельзя механически переименовывать.

## Куда добавить правило

Пути в таблице считаются от `scripts/rebrand/`; действующие подключения — в `nessy.json`.

| Изменение                                           | Файл                       | Важная особенность                                                                                                                    |
| --------------------------------------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Общее имя, путь, импорт, ENV                        | `config/replacements.json` | `from/to` — буквальные строки; более длинная замена применяется первой. Правило влияет и на имена файлов.                             |
| Ссылка или строка, которую иначе защитит исключение | `config/urls.json`         | Буквальная замена до исключений; `paths` — регулярное выражение для ограничения файлов.                                               |
| Неизбежный внешний идентификатор                    | `config/exceptions.json`   | Узкий `pattern`, при необходимости `paths`. Одного исключения недостаточно: новое остаточное упоминание также проверяет baseline.     |
| Изменение определённого фрагмента                   | `config/patches.json`      | `path/from/to/count`; вместо `to` можно `toFile`. Фрагмент ищется до массового переименования.                                        |
| Подмена файла, в том числе картинки                 | `config/assets.json`       | `path`, SHA256 исходных байтов и `replaceWith`. Подмена текста не проходит обычные массовые замены, но проверяется на остатки бренда. |
| Внешняя картинка или видео                          | `config/remote-media.json` | `path/from/to/count`; одинаковые `from/to` означают оставить. Проверка новых вставок ограничена распознаваемой разметкой.             |
| Разобранное остаточное упоминание                   | `nessy-mentions.json`      | `entries`: итоговый `file`, `scope`, обрезанная по краям строка `text`, число упоминаний `count`.                                     |

`replaceWith` и `toFile` считаются от каталога `nessy.json`.
В конфиге нет `reason`, `source` и `replacementSha256`; не возвращай их без задачи.

Сначала проверь, не заменяется ли файл целиком через `assets`: `remote-media`
и `patches` работают уже с подставленным содержимым. Например, картинка исходного
корневого README исчезает вместе с его заменой; правило для неё даст drift.

## Как менять

- Для фрагмента бери минимальный однозначный контекст. `count` должен совпадать
  с реальными вхождениями, а не увеличиваться ради прохождения проверки.
- При `Patch drift` сначала сравни новый исходник и его поведение. При
  `Asset drift` осмотри новый файл, затем пересчитай SHA256 именно исходника.
  Обновление hash без разбора изменения скрывает проблему.
- Графику бери из согласованного источника Nessy, по умолчанию из `master`.
  Проверь наличие и байтовое совпадение. Если нужного ассета нет — укажи пробел;
  не создавай, не конвертируй и не масштабируй картинку самостоятельно.
- Функциональные изменения относятся к fork-патчам. В текущем эксперименте
  допустима явно согласованная заглушка с `_comment`:
  `Заглушка. Вернуться к этому после анализа fork-патчей.`
  Не переноси функциональные изменения автоматически при задаче только на бренд.
- Baseline меняй после разбора каждого добавленного контекста: почему он должен
  остаться и какое исключение его защищает. Не копируй весь текущий отчёт в baseline
  и не расширяй регулярное выражение только ради зелёного CI.

## Проверка изменения

Используй процедуру [rebrand-verify](../rebrand-verify/SKILL.md): свежая копия
выбранного upstream, `plan → apply → check`, просмотр результата и нужные
проверки продукта. Для обычного правила достаточно затронутого сценария;
готовность новой версии требует полного прогона.

Запусти из корня контроллера на Node.js 22+:

```sh
node --test scripts/rebrand/rebrand.test.mjs scripts/rebrand/pipeline.test.mjs
```

Если меняешь алгоритм или исправляешь ошибку сопоставления, добавь регрессионный
тест на реальный сценарий: результат, повторный запуск и остановку на изменённом
исходнике. Для подстановки картинки проверь её отображение, для ссылки — реального
потребителя, для изменённого кода — его тесты. После сборки повтори `check`.

В ответе укажи изменённые правила, исходный SHA, проверенный результат и границы
проверки. Коммит, push и запуск публикующего CI выполняй только в пределах задачи.
