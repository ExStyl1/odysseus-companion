# Проверить ребрендинг upstream

Цель — определить, что выбранный upstream корректно превращается в Nessy,
и показать конкретные несовместимости. Зелёный поиск строк не доказывает,
что UI, сборка и установка работают.

## Установи вход и границы

- Найди контроллер с `scripts/rebrand/rebrand.mjs`. Прочитай его `AGENTS.md`,
  `scripts/rebrand/README.md`, `scripts/rebrand/nessy.json` и текущее состояние Git.
- Зафиксируй точный upstream SHA, ревизию контроллера и его локальные изменения.
  Если ветки нет локально или нужна актуальная удалённая версия, получи именно
  указанный ref и разреши его в SHA. При неоднозначном выборе upstream уточни его.
- Для уже готовой ветки сначала прочитай `.nessy-rebrand.json` и выполни `check`.
  Не применяй к ней правила другого профиля как исправление.
- Текущий CI начинает с чистого upstream; функциональные fork-патчи автоматически
  не накладываются. Если пользователь передал уже пропатченный вход, зафиксируй
  его отдельно. Не выдавай проверку чистого upstream за проверку полного Nessy.

## Локальный прогон

Для преобразования используй свежий detached worktree без `node_modules`,
пользовательских файлов и старого результата. Текущий движок не гарантирует
безопасное применение поверх произвольной рабочей директории.

Из корня контроллера, после задания `upstream_sha` выбранным полным SHA:

```sh
controller_root="$(git rev-parse --show-toplevel)"
rebrand_tmp="$(mktemp -d "${TMPDIR:-/tmp}/nessy-rebrand.XXXXXX")"
rebrand_source="$rebrand_tmp/source"
git worktree add --detach "$rebrand_source" "${upstream_sha:?Set the selected upstream SHA}"

node --test scripts/rebrand/rebrand.test.mjs scripts/rebrand/pipeline.test.mjs
node "$controller_root/scripts/rebrand/rebrand.mjs" \
  --root "$rebrand_source" --mode plan --report "$rebrand_tmp/plan.json"
```

Сначала разбери отчёт и код завершения. При ошибке не выполняй `apply` и проверки
его результата; независимый анализ исходников и охвата CI продолжай.
Если plan прошёл и преобразование входит в задачу:

```sh
node "$controller_root/scripts/rebrand/rebrand.mjs" \
  --root "$rebrand_source" --mode apply --report "$rebrand_tmp/apply.json"
node "$controller_root/scripts/rebrand/rebrand.mjs" \
  --root "$rebrand_source" --mode check --report "$rebrand_tmp/check.json"
git -C "$rebrand_source" status --short
git -C "$rebrand_source" diff --stat
```

Успешный `check` означает отсутствие повторных изменений и неожиданных остатков.
Проверь и новые файлы: Git diff не показывает содержимое untracked-файлов после
переименования. Для изучения diff можно добавить результат в индекс только этого
одноразового worktree, если он по-прежнему содержит исключительно исходники.
Отчёты храни снаружи дерева результата. Не коммить сборочные выходы и локальные ключи.

## Разбор остановок

| Сообщение или результат                            | Что проверить                                                                                                                       |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `Patch drift` / `Partially applied patch`          | Изменился исходный фрагмент, число вхождений или повторно используется изменённая копия. Сравнить код и начать со свежего worktree. |
| `Asset drift` / `Missing asset`                    | Новый hash, перенос или удаление ресурса; проверить содержимое и актуальный ассет Nessy.                                            |
| `Unclassified remote image` / `Remote image drift` | Новая вставка, изменённый адрес, текст или путь файла; решить, оставить её или заменить.                                            |
| `new-remaining-mention`                            | В `mentions.added` проверить итоговый файл, контекст и прирост `count`, даже если строку уже покрывает исключение.                  |
| `Path collision` / `Unsafe destination` / symlink  | Сопоставить реальные пути; не удалять конфликтующий файл, чтобы скрыть ошибку.                                                      |
| Нет JSON-отчёта                                    | Ранние ошибки plan могут произойти до записи отчёта; сохранить stderr и назвать первое препятствие.                                 |

При запросе только проверки остановись на перечне необходимых изменений.
Если адаптация разрешена, используй [rebrand-edit](../rebrand-edit/SKILL.md),
после изменения правил повтори прогон на чистом входе. Baseline не обновляй автоматически.

## Проверка продукта и новой версии

- Сверь `package.json`, lockfile, пакетный менеджер и workspaces нового upstream
  с `scripts/rebrand/verify.sh` и `scripts/rebrand/gitlab-ci.yml`. Списки пакетов
  и некоторые значения профиля привязаны к проверенной версии; новая версия
  не считается поддержанной только потому, что plan прошёл.
- Для полной проверки используй состав проверок из `verify.sh`: установка и
  сборка, типы, `verify-product.mjs`, unit-тесты, CLI smoke, упаковка и запуск
  установленного npm-архива. Также проверь lint. Переноси команды в отдельный
  worktree с учётом нового package manager и скриптов, не сокращая охват молча.
- `verify.sh` начинается с CI restore из `.rebrand/reports`; его нельзя просто
  запустить внутри произвольного локального результата. `ci.sh prepare` создаёт
  служебный коммит и артефакты, поэтому это не замена read-only проверке правил.
- После сборки повтори `check`, проверь неожиданные изменения отслеживаемых файлов.
  Новые изображения, inline SVG/ASCII-логотипы и внешнюю графику смотри отдельно:
  текстовый аудит не проверяет пиксели и не распознаёт всю разметку картинок.
- CLI, Web и Desktop проверяй как отдельные поверхности. Npm-сборка не собирает
  отдельный Desktop workspace и не доказывает работоспособность Electron,
  реальной модели или нативной упаковки. Используй изолированные тестовые профили.

## GitLab CI и результат

Перед запуском проверь текущие `.gitlab-ci.yml`, `.ci/rebrand-upstream.yml`
и `scripts/rebrand/ci.sh`. Сейчас выбирают ветку контроллера,
`PIPELINE_MODE=rebrand` и `REBRAND_UPSTREAM_REF=upstream/версия`.
Цепочка `prepare → verify → publish` автоматически создаёт `nessy/<версия>`
после проверок. Запрос на локальное ревью сам по себе не разрешает этот запуск.

В CI проверяется и публикуется один candidate SHA из metadata; не перегенерируй
кандидат между job и не создавай `verified.json` вручную. Compliance-файл
переносится из контроллера без правок. Существующую ветку не перезаписывай;
если для повторной публикации требуется удаление, выполняй его только при наличии
авторизации пользователя на это действие.

Сообщи: входной SHA и профиль, результат ребрендинга, новые остатки и изменения
upstream, выполненные build/test/lint/UI-проверки, непроверенные поверхности,
пути к результату и отчётам. Оставленный worktree явно укажи пользователю.
